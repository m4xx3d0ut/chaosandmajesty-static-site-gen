    <h2>TLDR;</h2>
<ul>
<li>Scaffold charts with <code>helm create</code>, keep configuration in <code>values.yaml</code>, and rely on MetalLB plus the ingress addon to expose services.</li>
<li>Push images to a local registry (<code>localhost:32000</code> or a bespoke registry) and update chart image references accordingly.</li>
<li>Debug registry exposure, MetalLB IP pools, and Helm templating with <code>kubectl edit</code>, address pools, and ConfigMap/ConfigMap-from-env workflows.</li>
</ul>
<h2>Working Notes... In Graphic Detail...</h2>
<h2>YouTube Integ API Helm Chart Creation</h2>
<h4><strong>1. Prepare the Helm Chart</strong></h4>
<ol>
<li><p><strong>Create a Helm Chart:</strong></p>
<pre><code class="language-bash">helm create youtube-integ-chart
cd youtube-integ-chart
</code></pre>
</li>
<li><p><strong>Organize Your Chart Structure:</strong>
Your chart will look like this:</p>
<pre><code>youtube-integ-chart/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    └── ingress.yaml  # Optional, for external access via domain
</code></pre>
</li>
<li><p><strong>Customize <code>values.yaml</code>:</strong>
Open <code>values.yaml</code> and define your Docker image and service details:</p>
<pre><code class="language-yaml">image:
  repository: your-dockerhub-username/youtube-integ
  tag: latest
  pullPolicy: IfNotPresent

service:
  type: NodePort
  port: 8000
  targetPort: 8000

replicaCount: 1
</code></pre>
</li>
<li><p><strong>Edit <code>templates/deployment.yaml</code>:</strong>
Configure the deployment to run your API container:</p>
<pre><code class="language-yaml">apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Chart.Name }}
  template:
    metadata:
      labels:
        app: {{ .Chart.Name }}
    spec:
      containers:
      - name: youtube-integ
        image: &quot;{{ .Values.image.repository }}:{{ .Values.image.tag }}&quot;
        ports:
        - containerPort: {{ .Values.service.targetPort }}
</code></pre>
</li>
<li><p><strong>Edit <code>templates/service.yaml</code>:</strong>
Expose the service on port 8000:</p>
<pre><code class="language-yaml">apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}
spec:
  type: {{ .Values.service.type }}
  selector:
    app: {{ .Chart.Name }}
  ports:
  - port: {{ .Values.service.port }}
    targetPort: {{ .Values.service.targetPort }}
    nodePort: 30000  # External port on Node
</code></pre>
</li>
<li><p><strong>Optional: Add an Ingress (for domain-based access):</strong>
If you want to use an ingress, create <code>templates/ingress.yaml</code>:</p>
<pre><code class="language-yaml">apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ .Release.Name }}
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
  - host: youtube-integ.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: {{ .Release.Name }}
            port:
              number: {{ .Values.service.port }}
</code></pre>
<p>Then enable MicroK8s ingress:</p>
<pre><code class="language-bash">microk8s enable ingress
</code></pre>
</li>
</ol>
<hr>
<h4><strong>2. Build and Push the Docker Image</strong></h4>
<ol>
<li><p>Build the Docker image for your API:</p>
<pre><code class="language-bash">docker build -t your-dockerhub-username/youtube-integ ./microservices/youtube_integ
</code></pre>
</li>
<li><p>Push the image to Docker Hub:</p>
<pre><code class="language-bash">docker push your-dockerhub-username/youtube-integ
</code></pre>
</li>
</ol>
<hr>
<h4><strong>3. Deploy the Helm Chart</strong></h4>
<ol>
<li><p>Package and deploy your chart:</p>
<pre><code class="language-bash">helm install youtube-integ ./youtube-integ-chart
</code></pre>
</li>
<li><p>Verify the deployment:</p>
<pre><code class="language-bash">microk8s kubectl get pods
microk8s kubectl get services
</code></pre>
</li>
<li><p>Access the service:</p>
<ul>
<li><p>If using a NodePort service, access it at <code>http://&lt;Node-IP&gt;:30000</code>. Get the Node IP:</p>
<pre><code class="language-bash">microk8s kubectl get nodes -o wide
</code></pre>
</li>
<li><p>If using an Ingress, add <code>youtube-integ.local</code> to your <code>/etc/hosts</code> file and access it at <code>http://youtube-integ.local</code>.</p>
</li>
</ul>
</li>
</ol>
<hr>
<h4><strong>4. Test Your API</strong></h4>
<p>Test the API externally to confirm it&#39;s working:</p>
<pre><code class="language-bash">curl http://&lt;Node-IP&gt;:30000/your-api-endpoint
</code></pre>

<h2>Values.yaml</h2>
<p>Yes, when using <code>helm create</code>, <strong>all configurable values in <code>templates/*.yaml</code> should ideally be pulled from <code>values.yaml</code></strong> instead of hardcoding them directly in the template files. This makes your Helm chart more flexible, reusable, and easy to manage. </p>
<p>By default, <code>helm create</code> generates a structure where most of the values are already parameterized and fetched from <code>values.yaml</code>. However, there might still be placeholders or hardcoded values that you should customize for your use case.</p>
<hr>
<h4><strong>Benefits of Using <code>values.yaml</code></strong></h4>
<ol>
<li><strong>Centralized Configuration:</strong> All user-configurable settings are stored in one place, making the chart easier to maintain and understand.</li>
<li><strong>Reusable Charts:</strong> You can reuse the same chart for multiple deployments by simply providing different <code>values.yaml</code> files or using <code>--set</code> for overrides.</li>
<li><strong>Separation of Code and Configuration:</strong> Reduces the risk of accidentally overwriting template logic when updating configurations.</li>
<li><strong>Overrides for Environments:</strong> You can define separate <code>values.yaml</code> files for staging, production, etc., without changing the templates.</li>
</ol>
<hr>
<h4><strong>How to Parameterize Values</strong></h4>
<p>In the <code>templates/*.yaml</code> files, replace hardcoded values with placeholders that reference <code>values.yaml</code>. For example:</p>
<h5><strong>Before: Hardcoded Values</strong></h5>
<pre><code class="language-yaml">apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  type: ClusterIP
  ports:
    - port: 80
      targetPort: 8080
  selector:
    app: my-app
</code></pre>
<h5><strong>After: Use Values from <code>values.yaml</code></strong></h5>
<pre><code class="language-yaml">apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-{{ .Values.service.name }}
spec:
  type: {{ .Values.service.type }}
  ports:
    - port: {{ .Values.service.port }}
      targetPort: {{ .Values.service.targetPort }}
  selector:
    app: {{ .Values.app.name }}
</code></pre>
<p>And in <code>values.yaml</code>:</p>
<pre><code class="language-yaml">app:
  name: my-app

service:
  name: my-service
  type: ClusterIP
  port: 80
  targetPort: 8080
</code></pre>
<hr>
<h4><strong>How to Use <code>values.yaml</code> Effectively</strong></h4>
<ol>
<li><p><strong>Keep Defaults in <code>values.yaml</code>:</strong>
Store default configurations for your chart in <code>values.yaml</code> so users don’t have to supply everything manually.</p>
</li>
<li><p><strong>Use Placeholders in <code>templates/*.yaml</code>:</strong>
Use the <code>{{ .Values.&lt;key&gt; }}</code> syntax to reference values from <code>values.yaml</code>.</p>
</li>
<li><p><strong>Use Default Fallbacks (Optional):</strong>
If a value is optional, you can provide a default using the <code>default</code> function:</p>
<pre><code class="language-yaml">type: {{ .Values.service.type | default &quot;ClusterIP&quot; }}
</code></pre>
</li>
<li><p><strong>Avoid Hardcoding Values in Templates:</strong>
Instead of embedding fixed values like names, ports, or replicas directly in <code>templates/*.yaml</code>, make them configurable.</p>
</li>
</ol>
<hr>
<h4><strong>Deploying with Custom Values</strong></h4>
<p>Users can override values at deployment time using either:</p>
<ol>
<li><p>A custom <code>values.yaml</code>:</p>
<pre><code class="language-bash">helm install my-app ./my-chart -f custom-values.yaml
</code></pre>
</li>
<li><p>Inline <code>--set</code> flags:</p>
<pre><code class="language-bash">helm install my-app ./my-chart --set service.type=LoadBalancer
</code></pre>
</li>
</ol>
<hr>
<h4><strong>Recommendation for Charts</strong></h4>
<ul>
<li>Ensure that <strong>all configurable fields</strong> (e.g., service type, port numbers, image repository, resource limits) are parameterized in <code>values.yaml</code>.</li>
<li>Use Helm’s built-in functions (e.g., <code>default</code>, <code>toYaml</code>) to handle optional or complex configurations.</li>
<li>Keep <code>values.yaml</code> well-documented with comments to explain each key.</li>
</ul>
<p>By following these practices, your Helm charts will be more robust, reusable, and easier to maintain. Let me know if you&#39;d like help improving a specific chart!</p>

<h2>Local Docker Image Registry</h2>
<p><a href="https://microk8s.io/docs/registry-private">https://microk8s.io/docs/registry-private</a></p>
<p>To push your Docker image to a <strong>local repository</strong> instead of Docker Hub, you can set up and use a private Docker registry or a container registry provided by MicroK8s. Here&#39;s how to do it:</p>
<hr>
<h4><strong>Option 1: Use the MicroK8s Built-in Docker Registry</strong></h4>
<p>MicroK8s comes with an optional built-in container registry that you can enable:</p>
<ol>
<li><p><strong>Enable the Registry:</strong></p>
<pre><code class="language-bash">microk8s enable registry
</code></pre>
<ul>
<li>This sets up a local Docker registry at <code>localhost:32000</code> (default port).</li>
</ul>
</li>
<li><p><strong>Tag Your Docker Image:</strong>
Tag your Docker image to point to the MicroK8s registry:</p>
<pre><code class="language-bash">docker tag your-dockerhub-username/youtube-integ localhost:32000/youtube-integ
</code></pre>
</li>
<li><p><strong>Push the Image to the Registry:</strong>
Push the image to the local registry:</p>
<pre><code class="language-bash">docker push localhost:32000/youtube-integ
</code></pre>
</li>
<li><p><strong>Use the Image in Kubernetes:</strong>
In your Helm chart&#39;s <code>values.yaml</code>, update the image repository to:</p>
<pre><code class="language-yaml">image:
  repository: localhost:32000/youtube-integ
  tag: latest
</code></pre>
<p>Kubernetes will pull the image from the local registry when deploying.</p>
</li>
</ol>
<hr>
<h4><strong>Option 2: Set Up a Standalone Local Docker Registry</strong></h4>
<p>If you want a standalone registry (not tied to MicroK8s), follow these steps:</p>
<ol>
<li><p><strong>Run a Local Docker Registry:</strong>
Launch a local registry container:</p>
<pre><code class="language-bash">docker run -d -p 5000:5000 --name local-registry registry:2
</code></pre>
<p>This runs a private registry accessible at <code>localhost:5000</code>.</p>
</li>
<li><p><strong>Tag Your Docker Image:</strong>
Tag your image to point to the local registry:</p>
<pre><code class="language-bash">docker tag your-dockerhub-username/youtube-integ localhost:5000/youtube-integ
</code></pre>
</li>
<li><p><strong>Push the Image to the Registry:</strong>
Push the image to the local registry:</p>
<pre><code class="language-bash">docker push localhost:5000/youtube-integ
</code></pre>
</li>
<li><p><strong>Configure MicroK8s to Use the Local Registry:</strong>
If MicroK8s runs in a VM (e.g., Multipass), you need to expose the registry to MicroK8s:</p>
<ul>
<li><p>Edit Docker&#39;s daemon configuration (on the machine running MicroK8s):</p>
<pre><code class="language-json">{
  &quot;insecure-registries&quot;: [&quot;localhost:5000&quot;]
}
</code></pre>
</li>
<li><p>Restart the Docker daemon:</p>
<pre><code class="language-bash">sudo systemctl restart docker
</code></pre>
</li>
</ul>
</li>
<li><p><strong>Update Your Helm Chart:</strong>
Update the <code>values.yaml</code> file to point to your local registry:</p>
<pre><code class="language-yaml">image:
  repository: localhost:5000/youtube-integ
  tag: latest
</code></pre>
</li>
<li><p><strong>Deploy Your Chart:</strong>
Helm will now pull the image from the local registry.</p>
</li>
</ol>
<hr>
<h4><strong>Option 3: Use Kind (<code>kind</code>) to Push Images for Local Kubernetes Testing</strong></h4>
<p>If you’re using <strong>Kind</strong> (Kubernetes-in-Docker), load the Docker image directly into the cluster:</p>
<ol>
<li><p>Build the image:</p>
<pre><code class="language-bash">docker build -t youtube-integ ./microservices/youtube_integ
</code></pre>
</li>
<li><p>Load the image into the cluster:</p>
<pre><code class="language-bash">microk8s ctr image import youtube-integ.tar
</code></pre>
</li>
<li><p>Deploy the Helm chart, referencing the local image:</p>
<pre><code class="language-yaml">image:
  repository: youtube-integ
  tag: latest
</code></pre>
</li>
</ol>

<h2>Configure the Local Registry</h2>
<p>In MicroK8s version 1.32.1, the built-in registry is deployed as a service within the Kubernetes cluster and is exposed as a NodePort service on port <code>32000</code> of the localhost. This means it&#39;s accessible via <code>localhost:32000</code> on the host machine. (<a href="https://microk8s.io/docs/registry-built-in?utm_source=chatgpt.com">microk8s.io</a>)</p>
<p>To make the registry accessible on all network interfaces (i.e., binding to <code>0.0.0.0</code>), you can modify the service&#39;s configuration to expose it externally. Here&#39;s how:</p>
<ol>
<li><p><strong>Edit the Registry Service:</strong></p>
<p>The registry is managed as a Kubernetes service named <code>registry</code>. You can edit this service to change its configuration:</p>
<pre><code class="language-bash">microk8s kubectl edit service registry -n container-registry
</code></pre>
</li>
<li><p><strong>Modify the Service Type:</strong></p>
<p>In the editor that opens, you&#39;ll see the service definition in YAML format. Locate the <code>spec</code> section and change the <code>type</code> from <code>NodePort</code> to <code>LoadBalancer</code>. This will provision an external IP address for the service, making it accessible from outside the cluster.</p>
<p>Before:</p>
<pre><code class="language-yaml">spec:
  type: NodePort
  ports:
    - port: 32000
      targetPort: 5000
      nodePort: 32000
  selector:
    app: registry
</code></pre>
<p>After:</p>
<pre><code class="language-yaml">spec:
  type: LoadBalancer
  ports:
    - port: 32000
      targetPort: 5000
  selector:
    app: registry
</code></pre>
<p>Save and exit the editor.</p>
</li>
<li><p><strong>Verify the External IP:</strong></p>
<p>After modifying the service, check its status to find the external IP address assigned:</p>
<pre><code class="language-bash">microk8s kubectl get service registry -n container-registry
</code></pre>
<p>The output will show an <code>EXTERNAL-IP</code> once it&#39;s assigned. This may take a few moments.</p>
</li>
<li><p><strong>Access the Registry:</strong></p>
<p>Once the external IP is available, you can push images to the registry using this IP address:</p>
<pre><code class="language-bash">docker tag your-image &lt;external-ip&gt;:32000/your-image
docker push &lt;external-ip&gt;:32000/your-image
</code></pre>
</li>
</ol>
<p><strong>Considerations:</strong></p>
<ul>
<li><p><strong>Security:</strong> Exposing the registry externally can pose security risks. Ensure that appropriate firewall rules and access controls are in place. For production environments, consider securing the registry with TLS and authentication.</p>
</li>
<li><p><strong>Networking:</strong> If your environment doesn&#39;t support automatic provisioning of external IPs (common in bare-metal setups), you might need to configure a MetalLB load balancer or adjust your network settings accordingly.</p>
</li>
</ul>
<p>By following these steps, you can configure the MicroK8s built-in registry to be accessible from external machines, effectively binding it to <code>0.0.0.0</code>. </p>

<h2>MetaLLB Load Balancer</h2>
<h4><strong>Steps to Debug and Fix</strong></h4>
<h5><strong>1. Ensure MetalLB Is Configured (For Bare-Metal)</strong></h5>
<ul>
<li>If your cluster is not on a cloud provider, you need to install and configure MetalLB to assign an external IP to the <code>LoadBalancer</code> service.</li>
</ul>
<p>   <strong>Enable MetalLB in MicroK8s:</strong></p>
<pre><code class="language-bash">microk8s enable metallb
</code></pre>
<p>   <strong>Provide an IP Range:</strong>
   During the setup, you’ll be prompted to input an IP range (e.g., <code>192.168.1.240-192.168.1.250</code>) that MetalLB will use to assign external IPs. Choose a range that’s within your local network.</p>
<p>   <strong>Check MetalLB Is Working:</strong>
   After enabling MetalLB, check if the registry service has an external IP assigned:</p>
<pre><code class="language-bash">microk8s kubectl get service registry -n container-registry
</code></pre>
<h5><strong>2. Check Firewall Rules</strong></h5>
<p>   Ensure that port <code>32000</code> is open on your node(s) for both incoming and outgoing traffic.</p>
<ul>
<li><p>On Linux, you can open the port with:</p>
<pre><code class="language-bash">sudo ufw allow 32000
</code></pre>
</li>
<li><p>Confirm the port is open:</p>
<pre><code class="language-bash">sudo ufw status
</code></pre>
</li>
</ul>
<h5><strong>3. Verify Service Configuration</strong></h5>
<p>   Reapply the updated service configuration to ensure all changes take effect:</p>
<pre><code class="language-bash">microk8s kubectl apply -f &lt;your-service-config.yaml&gt;
</code></pre>
<h5><strong>4. Check Logs and Events</strong></h5>
<p>   Inspect the logs and events for any issues related to the service:</p>
<pre><code class="language-bash">microk8s kubectl describe service registry -n container-registry
</code></pre>
<hr>
<h4><strong>Expected Outcome</strong></h4>
<p>After enabling MetalLB and ensuring your firewall is configured, the <code>status.loadBalancer</code> field should populate with an external IP. You can then push Docker images to the registry using that IP.</p>
<hr>
<h2>Build &amp; Tag the Image</h2>
<p>To tag your Docker image for use with your local MicroK8s registry, you need to include the registry address (which defaults to <code>localhost:32000</code>) in the image name. Here&#39;s how you should modify your <code>docker build</code> command:</p>
<h4><strong>Build and Tag the Image</strong></h4>
<pre><code class="language-bash">docker build -t localhost:32000/youtube_integ:latest -f ./microservices/youtube_integ/Dockerfile .
</code></pre>
<h4><strong>Explanation</strong></h4>
<ol>
<li><strong><code>localhost:32000</code></strong>: This points to the MicroK8s local container registry.</li>
<li><strong><code>youtube_integ</code></strong>: The name of your image.</li>
<li><strong><code>:latest</code></strong>: The tag for the image (optional but commonly used).</li>
</ol>
<h4><strong>Push the Image to the Registry</strong></h4>
<p>After building the image, you need to push it to the MicroK8s registry:</p>
<pre><code class="language-bash">docker push localhost:32000/youtube_integ:latest
</code></pre>
<hr>
<h4><strong>Additional Notes</strong></h4>
<ul>
<li><p>If the MicroK8s registry is configured with a different address (e.g., external IP or custom port), replace <code>localhost:32000</code> with the appropriate value.</p>
</li>
<li><p>Ensure that the local registry is enabled:</p>
<pre><code class="language-bash">microk8s enable registry
</code></pre>
</li>
<li><p>If you encounter issues with Docker authentication, ensure Docker is configured to use an insecure registry for <code>localhost:32000</code>:</p>
<ol>
<li><p>Edit the Docker daemon configuration file (<code>/etc/docker/daemon.json</code>):</p>
<pre><code class="language-json">{
  &quot;insecure-registries&quot;: [&quot;localhost:32000&quot;]
}
</code></pre>
</li>
<li><p>Restart Docker:</p>
<pre><code class="language-bash">sudo systemctl restart docker
</code></pre>
</li>
</ol>
</li>
</ul>
<p>Once the image is pushed, you can deploy it to your MicroK8s Kubernetes cluster using a <code>Helm</code> chart or <code>kubectl</code> manifest.</p>
<hr>
<h2>Local Registry Ops</h2>
<p>To manage and view the images in your local <strong>MicroK8s registry</strong>, here’s how you can list the stored images and delete any you no longer need:</p>
<hr>
<h4><strong>1. View Images in the Registry</strong></h4>
<p>The MicroK8s registry stores images as files within the container running the registry. By default, the registry uses a <strong>filesystem backend</strong>, and images can be listed using <code>microk8s ctr</code>.</p>
<h5><strong>List Images</strong></h5>
<p>Run the following command:</p>
<pre><code class="language-bash">microk8s ctr images list
</code></pre>
<p>This will display all images in the registry and their tags.</p>
<hr>
<h4><strong>2. Delete Images from the Registry</strong></h4>
<p>You can delete images by using the <code>microk8s ctr images remove</code> command.</p>
<h5><strong>Command to Remove an Image</strong></h5>
<pre><code class="language-bash">microk8s ctr images remove &lt;image-name&gt;:&lt;tag&gt;
</code></pre>
<p>For example:</p>
<pre><code class="language-bash">microk8s ctr images remove localhost:32000/youtube_integ:latest
</code></pre>
<p>This removes the specified image from the registry.</p>
<hr>
<h4><strong>3. Force Cleanup of Dangling Layers</strong></h4>
<p>If you’ve deleted images but still see storage being used, it may be due to orphaned layers or cache files. Clean up unused layers with:</p>
<pre><code class="language-bash">microk8s ctr content gc
</code></pre>
<hr>
<h4><strong>4. (Optional) Interact Directly with the Registry</strong></h4>
<p>If needed, you can access the MicroK8s registry directly to inspect or clean up manually:</p>
<ol>
<li><p><strong>Access the Registry Pod</strong>:</p>
<pre><code class="language-bash">microk8s kubectl -n container-registry get pods
</code></pre>
<p>Look for the registry pod (usually named <code>registry-xxxxx</code>).</p>
</li>
<li><p><strong>Enter the Pod</strong>:</p>
<pre><code class="language-bash">microk8s kubectl -n container-registry exec -it registry-xxxxx -- sh
</code></pre>
</li>
<li><p><strong>Inspect Stored Images</strong>:
The images are usually stored in <code>/var/lib/registry</code>. You can navigate and delete files manually if necessary:</p>
<pre><code class="language-bash">ls /var/lib/registry/docker/registry/v2/repositories
</code></pre>
</li>
</ol>
<hr>
<h4><strong>5. Clean All Registry Data (Optional)</strong></h4>
<p>If you want to reset the entire registry (delete all images), simply delete the registry storage volume:</p>
<pre><code class="language-bash">sudo rm -rf /var/snap/microk8s/common/var/lib/registry
</code></pre>
<p>This action will completely remove all images stored in the registry. Use it with caution!</p>
<hr>
<p>To create a <strong>ConfigMap</strong> in MicroK8s from an <code>.env</code> file, follow these steps:</p>
<h4>1. Prepare the <code>.env</code> file</h4>
<p>Ensure your <code>.env</code> file is formatted as key-value pairs:  </p>
<pre><code class="language-sh">## my-config.env
DB_HOST=db.example.com
DB_USER=admin
DB_PASS=securepassword
</code></pre>
<h4>2. Create the ConfigMap</h4>
<p>Use the following command to create a ConfigMap from the file:</p>
<pre><code class="language-sh">microk8s kubectl create configmap my-config --from-env-file=my-config.env
</code></pre>
<p>This creates a ConfigMap named <code>my-config</code> with the key-value pairs from <code>my-config.env</code>.</p>
<h4>3. Verify the ConfigMap</h4>
<p>Check if the ConfigMap was created successfully:</p>
<pre><code class="language-sh">microk8s kubectl get configmap my-config -o yaml
</code></pre>
<h4>4. Use the ConfigMap in a Pod</h4>
<p>Reference the ConfigMap in a Pod by mounting it as environment variables:</p>
<pre><code class="language-yaml">apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  containers:
    - name: my-container
      image: my-app:latest
      envFrom:
        - configMapRef:
            name: my-config
</code></pre>
<h4>Alternative: Using a Helm Chart</h4>
<p>If you’re using Helm, define the ConfigMap in your <strong>values.yaml</strong> and template it in your Helm chart:</p>
<pre><code class="language-yaml">config:
  DB_HOST: &quot;db.example.com&quot;
  DB_USER: &quot;admin&quot;
  DB_PASS: &quot;securepassword&quot;
</code></pre>
<p>Then, use a <strong>ConfigMap template</strong> in your chart:</p>
<pre><code class="language-yaml">apiVersion: v1
kind: ConfigMap
metadata:
  name: my-config
data:
  {{- range $key, $value := .Values.config }}
  {{ $key }}: &quot;{{ $value }}&quot;
  {{- end }}
</code></pre>
