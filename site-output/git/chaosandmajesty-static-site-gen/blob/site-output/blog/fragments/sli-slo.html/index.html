    <h2>TLDR;</h2>
<ul>
<li>Ground every subsystem in a user journey: document the indicator, objective, and slack, then capture it once via the shared Google Form for review.</li>
<li>Translate &quot;number of nines&quot; into budget minutes so product, ops, and finance can see the burn rate; 99.95% still allows ~20 minutes of downtime every 28 days.</li>
<li>Use a clean SLI equation—good events divided by valid events—to feed alerting, dashboards, and retros; filter noisy inputs before they eat the error budget.</li>
</ul>

<h3>Why SLIs And SLOs Matter</h3>
<p>SLIs, SLOs, and SLAs close the loop between engineering work and business outcomes.
Without them you cannot reason about availability, customer promises, or whether new
features are hurting your reliability posture.</p>
<ul>
<li>Define reliability via the specific experience the user cares about (often availability).</li>
<li>Measure success and failure rates so the SLI reflects reality.</li>
<li>Pick the lowest acceptable objective (SLO) to balance cost and delivery pace.</li>
<li>Keep SLAs looser than SLOs so you have wiggle room before contractual penalties.</li>
</ul>

<h3>The Core Equation</h3>
<p><code>SLI = (good events / valid events) * 100%</code></p>
<ol>
<li>SLIs live between 0% and 100%, matching percent-reliability SLOs and error budgets.</li>
<li>Consistent inputs (good events, valid events, threshold) allow shared alerting and reporting tooling.</li>
<li>Filter bogus traffic out of the denominator or explicitly mark good events in the numerator so noisy clients do not drain error budgets.</li>
</ol>

<h3>Availability SLIs</h3>
<p>Focus on the proportion of valid requests served successfully.</p>
<ul>
<li>What requests qualify as valid for the journey?</li>
<li>What constitutes a successful response (status code, payload, side effects)?</li>
</ul>
<h3>Latency SLIs</h3>
<p>Measure the percentage of valid requests that complete under a threshold.</p>
<ul>
<li>Define the timer start/stop points (client, LB, app) so dashboards agree.</li>
<li>Pick latency buckets that reflect user expectations (p95 vs p99).</li>
</ul>
<h3>Quality SLIs</h3>
<p>Quality tracks correctness of results rather than uptime.</p>
<ul>
<li>Identify the signal for correctness (checksum, validation pass, downstream acknowledgement).</li>
<li>Cap the sample window so slow drift does not silently violate the budget.</li>
</ul>
<h3>Error Budget Execution</h3>
<ul>
<li>Express the remaining budget as downtime minutes or request counts so stakeholders see trade-offs.</li>
<li>Pair product launches with a budget burn plan; freeze risky deploys if the budget drops below 50%.</li>
<li>Rotate reviews through the owning squads so SLIs stay current with architecture changes.</li>
</ul>
