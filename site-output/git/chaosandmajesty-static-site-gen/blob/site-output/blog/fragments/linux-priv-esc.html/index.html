<h5>Understanding Files and Users Privileges on Linux</h5>
<p>A defining feature of Linux/Unix is that most resources are represented in the FS:</p>
<ul>
<li>Files.</li>
<li>Directories.</li>
<li>Devices.</li>
<li>Network communication interfaces.</li>
<li>In essence &quot;everything is a file&quot;.</li>
</ul>
<p>Every file or element of a Linux system adheres to <a href="https://wiki.archlinux.org/index.php/users_and_groups">user and group</a> permissions with 3 primary properties:</p>
<ul>
<li>Read (r)</li>
<li>Write (w)</li>
<li>Execute (x)</li>
</ul>
<p>Each file/directory has permissions in 3 categories of users:</p>
<ul>
<li>Owner.</li>
<li>Owner group.</li>
<li>Others group.</li>
</ul>
<p>Each perm (rwx) allows authorized users to perform different actions dependent on if the resource is a file or directory.</p>
<p>For files:</p>
<ul>
<li>(r) allows reading file content.</li>
<li>(w) allows changing the content.</li>
<li>(x) allows file execution.</li>
</ul>
<p>Directories are handles differently:</p>
<ul>
<li>(r) right to list the contents.</li>
<li>(w) create or delete files.</li>
<li>(x) allows crossing through dir to access contents using CLI.</li>
<li>The ability to cross through a dir without read allows the user to access unknown entries, only by knowing their exact names.</li>
</ul>
<p>A simple example of these permissions on our local system:</p>
<pre><code class="language-bash">┌──(operator㉿labhost)-[~/OffSec/lin-priv-esc]
└─$ ls -l /etc/shadow               
-rw-r----- 1 root shadow 1510 Aug 26 18:13 /etc/shadow
</code></pre>
<ul>
<li>For each user category 3 different access perms are displayed.</li>
<li>The first <code>-</code> indicates file type and can be safely ignored.</li>
<li>The next 3 are <code>root</code><ul>
<li><code>rw-</code></li>
<li>Owner has read, write, no exec.</li>
</ul>
</li>
<li>The next <code>shadow</code> group owner.<ul>
<li><code>r--</code></li>
<li>Owner only has read access.</li>
</ul>
</li>
<li>The <code>others</code> group.<ul>
<li><code>---</code></li>
<li>Has no rights on the file.</li>
</ul>
</li>
</ul>

<p>Next we inspect firewall rules.  Generally we are interested in the firewall state, profile, and rules during the remote exploitation phase, but this info can also be useful during PrivEsc. <p>There are a few enumerations to be aware of that may provide a <strong>shortcut to PriveEsc</strong>.  Other than <code>rwx</code> file perms there are two <em>special rights</em> pertaining to exec files:</p>
<ul>
<li><code>setuid</code> and <code>setgid</code></li>
<li>Symbolized with upper or lower case <code>s</code></li>
<li>Allows current user to exec the file with rights of the owner (setuid) or the owner&#39;s group (setgid)</li>

<p>When run, an exec normally inherits the rights of the user that runs it.  If SUID perms are set, the bin will run with the perms of the file owner.</p>
<ul>
<li>If a bin has the SUID bit set and the owner is root.</li>
<li>Local user exec that bin with elevated priv.</li>
<li>When user or automate script launches SUID app.</li>
<li>It inherits the UID/GID of initiating script.</li>
<li>Known as the <strong>&quot;effective UID/GID&quot; or eUID/eGID</strong>.</li>
<li>Which is the user the OS verifies to grant perms for the action.</li>
<li>Manage to subvert a setuid root program to call a command of choice.</li>
<li>Effectively impersonate the root user.</li>
<li>Common method of PrivEsc.</li>
</ul>

<h5>Abusing Password Authentication</h5>
<p>Passwords are generally stored in <code>/etc/shadow</code> (not readable by normal user) when there are no centralized credential systems, such as AD or LDAP, in use.  Historically, hashes and account info were stored in the world readable <code>/etc/passwd</code>.  For backwards compatibility, if a password hash is present in the second column of an <code>/etc/passwd</code> user record it is valid for auth and takes precedence over the entry in <code>/etc/shadow</code> if present.  Therefore, if we can write into <code>/etc/passwd</code> we can set an arbitrary password for any account.</p>
<p>Previously we have seen that the Debian Vm may be vulnerable to PrivEsc due to <code>/etc/passwd</code> perms being improperly set.  We can PrivEsc by adding another superuser, <code>root2</code>, and corresponding password hash to <code>/etc/passwd</code>.</p>

<h5>Abusing Setuid Binaries and Capabilities</h5>
<p>As we saw earlier, <code>setuid</code> binaries can lead to PrivEsc when not properly secured.  Before we attempt the exploit let&#39;s review the purpose behind a setuid binary with an example.</p>
