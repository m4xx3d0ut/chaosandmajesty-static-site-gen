  102. <p>Credential attacks blend automation with context. The lab notes captured wordlists, hashcat rule tweaks, and relay nuances; this revision makes them explicit.</p>
  103. <h3>Online Guessing</h3>
  104. <ul>
  105. <li>Build user lists from LDAP, email headers, and OSINT; normalise casing and remove duplicates.</li>
  106. <li>Respect lockout thresholds: throttle attempts (<code>hydra -t 4 -W 30</code>) and log timings.</li>
  107. </ul>
  108. <pre><code># SSH brute force with delays

  113. </code></pre>
  114. <ul>
  115. <li>Capture successes with timestamp, source IP, account type, and password reuse indicators.</li>
  116. </ul>
  117. <h3>Hash Capture &amp; Cracking</h3>
  118. <ul>
  119. <li>Dump credentials responsibly (<code>secretsdump.py</code>, <code>impacket</code> relays, DPAPI extraction). Store raw files in encrypted containers.</li>
  120. <li>Use targeted wordlists plus rules:</li>
  121. </ul>
  122. <pre><code class="language-bash">hashcat -m 1000 hashes/ntlm.txt wordlists/rockyou.txt -r rules/dive.rule --session ntlm
  123. hashcat -m 5600 hashes/netntlmv2.txt wordlists/top20k.txt -r rules/leetspeak.rule --status
  124. </code></pre>
  125. <ul>
  126. <li>Leverage masks (<code>?u?l?l?l?d?d?d</code>) for seasonal patterns. Document masks used and cracked credentials for reporting.</li>
  127. </ul>
  128. <h3>Relay &amp; Pass-The-Hash</h3>
  129. <ul>
  130. <li><strong>Responder / Inveigh</strong> to capture Net-NTLMv2.</li>
  131. <li><strong>ntlmrelayx.py</strong> to target SMB/HTTP services lacking signing or enforcing Extended Protection.</li>
  132. </ul>
  133. <pre><code class="language-bash">python3 ntlmrelayx.py -tf targets.txt -smb2support --escalate-user supportsvc
  134. </code></pre>
  135. <ul>
  136. <li>After success, enumerate new privileges (<code>net localgroup administrators</code>, <code>Get-ADGroupMember</code>). Note lateral movement paths you unlocked.</li>
  137. </ul>
  138. <h3>SSH Key &amp; Password Manager Workflows</h3>
  139. <ul>
  140. <li>Convert private keys: <code>ssh2john id_rsa &gt; ssh.hash</code>, crack with <code>john --wordlist=... --rules=KoreLogic</code>.</li>
  141. <li>For KeePass/Password Safe artifacts, use <code>keepass2john</code> and mention key-file requirements in the notes.</li>
  142. </ul>
  143. <h3>Operational Hygiene</h3>
  144. <ul>
  145. <li>Segregate cracked credentials by sensitivity (user, service, privileged) and update the engagement tracker.</li>
  146. <li>Purge loot post-engagement per policy; document deletion commands for audit.</li>
  147. </ul>
  148. <h3>Defensive Recommendations</h3>
  149. <ul>
  150. <li>Enforce MFA, disable legacy auth protocols, and deploy account lockout alerting.</li>
  151. <li>Rotate captured credentials immediately; note whether the client already has PAM or SSPR solutions to support this.</li>
  152. <li>Roll out LAPS / gMSA to prevent local admin password reuse.</li>
  153. </ul>
  154. <p>Module 15 proves passwords remain the weakest link—apply these workflows carefully, log everything, and hand defenders a prioritized remediation list.</p>

  399. <h5>Introduction to Encryption, Hashes and Cracking</h5>
  400. <p>We will examine the difference between encryption and hash algorithms as well as discuss password cracking. We will review two popular password cracking tools:</p>
  401. <ul>
  402. <li><a href="https://hashcat.net/hashcat/">Hashcat</a></li>
  403. <li><a href="https://www.openwall.com/john/">John the Ripper (JtR)</a>
  404. Finally we will calculate the time it takes to crack specific hashes!</li>
  405. </ul>
  406. <p><strong>Encryption</strong> is a two-way function. Data is scrambled, i.e. encrypted, and unscrambled, i.e. decrypted with at least one key. The encrypted data is known as <a href="https://en.wikipedia.org/wiki/Ciphertext">ciphertext</a></p>
  407. <ul>
  408. <li><a href="https://en.wikipedia.org/wiki/Symmetric-key_algorithm">Symmetric Encryption</a></li>
  409. <li>Use the same key for enc and dec.</li>
  410. <li>To send a message to another person both sides need to know the key (password)</li>
  411. <li>If the key is sent via unsecure channel, it can be intercepted.</li>
  412. <li>In this case, the attacker can use a MitM attack to access the encrypted message between the two.</li>
  413. <li>With an intercepted key and access to the encrypted message the attacker can decrypt and read.</li>
  414. <li>This introduces risk as the comm sec is reliant on knowledge of the key, which must be known by both sides before starting the comm.
  415. - An example is <a href="https://en.wikipedia.org/wiki/Advanced_Encryption_Standard">AES (Advanced Encryption Standard)</a></li>
  416. <li><a href="https://en.wikipedia.org/wiki/Public-key_cryptography">Asymmetric Encryption</a></li>
  417. <li>Uses distinct key pairs.</li>
  418. <li>Private and public key.</li>
  419. <li>To recieve a message the user shares their pub key with the comm partner.</li>
  420. <li>The pub key is used for the comm partner to enc their message to the user.</li>
  421. <li>Only the corresponding priv key can dec the message.
  422. - An example is <a href="https://en.wikipedia.org/wiki/RSA_(cryptosystem)">RSA (Rivest-Shamir-Adleman)</a></li>
  423. </ul>
  424. <p><strong>Hash</strong>, or a digest, is the result of running var sized input data, such as a plaintext password, through a hash algorithm.</p>
  425. <ul>
  426. <li><a href="https://en.wikipedia.org/wiki/SHA-1">SHA1</a></li>
  427. <li><a href="https://en.wikipedia.org/wiki/MD5">MD5</a>
  428. The result is a fixed-len hexadecimal value which represents the original plaintext input. Plaintext run through the same hash algo always produces the same hash, which is statistically unique. The only exception being an extremely rare <a href="https://en.wikipedia.org/wiki/Hash_collision">hash collision</a>, where two input values result in the same hash value.</li>
  429. </ul>
  430. <p>The majority of common hash algos, i.e. SHA1 and MD5, are cryptographic hash functions. They are <a href="https://en.wikipedia.org/wiki/One-way_function">one-way finctions</a>, trivial to generate but prohibitively difficult to reverse to plaintext from the hash. We will focus on cryptographic hash functions primarily.</p>
  431. <p>Hashing is leveraged in infosec. When a user registers an account and sets a password, the password is typically hashed and stored in a DB. This prevents the site admin (or an attacker) from accessing the plaintext password.</p>
  432. <p>During login, the supplied password is hashed and compared to the hash in the DB. If the match, the password is correct.</p>
  433. <p>App and user passwords are more often than not encrypted or hashed for protection. To dec an enc password we need to determine the key used to enc. To determine the plaintext of a hash we must run plaintext passwords through the hash algo and compare the returned hash to the target hash. <strong>Password cracking</strong> attacks are typically performed on a dedicated system, it is time consuming and should run in parralell with other actions during a pentest.</p>
  434. <p>Unlike dict attacks, password cracking is quiet, doesn not lock accounts by failed attempts, and is unaffected by countermeasures.</p>

  599. <h5>Mutating Wordlists</h5>

  1052. <h3>Cracking NTLM</h3>
  1053. <p>Windows stores hased user passwords in the <a href="https://en.wikipedia.org/wiki/Security_Account_Manager">Security Account Manager (SAM)</a> DB file, used to auth local and remote accounts.</p>
  1054. <p><em>To deter offline SAM database password attacks, Microsoft introduced the SYSKEY feature in Windows NT 4.0 SP3, which partially encrypts the SAM file. The passwords can be stored in two different hash formats: LAN Manager (LM)2 and NTLM. LM is based on DES,3 and is known to be very weak. For example, passwords are case insensitive and cannot exceed fourteen characters. If a password exceeds seven characters, it is split into two strings, each hashed separately. LM is disabled by default beginning with Windows Vista and Windows Server 2008.</em></p>
  1055. <p>On modern systems, the SAM hashes are stored as NTLM. This hash fixes many of the weaknesses of LM, i.e. passwords are case sensitive and no longer split into smaller, weaker, hashes. However, NTLM hashes stored in the SAM DB are not salted.</p>
  1056. <p><a href="https://en.wikipedia.org/wiki/Salt_(cryptography)">Salts</a> are random buts appended to a password <em>before</em> it is hashed. They are used to prevent an attack in which attackers pre-compute a list of hashes and then perform lookups on these precomputed hashes to infer the plaintext password. A list or table of precomputed passwords is called a <a href="https://en.wikipedia.org/wiki/Rainbow_table">Rainbow Table</a>, the attack is known as a Rainbow Table Attack.</p>
  1057. <p><em>We use &quot;NTLM hash&quot; to refer to the formally correct NTHash. Since &quot;NTLM hash&quot; is more commonly used in our industry, we use it in this course to avoid confusion.</em></p>
  1058. <p>We cannot perform operations on the SAM DB (copy/rename/move) in <strong>C:\Windows\system32\config\sam</strong> while Win is running, the kernel keeps and exclusive file system lock on it. However, this restriction can be bypassed with a <a href="https://github.com/gentilkiwi/mimikatz">Mimikatz</a>.</p>
  1059. <p>Mimikatz provides functions to extract plain-text passwords and password hashes, from various Win sources, and further leverage them in attack vectors like <a href="https://en.wikipedia.org/wiki/Pass_the_hash">pass-the-hash</a>. Mimikatz <strong>sekurlsa</strong> module extracts hashes from the <a href="https://en.wikipedia.org/wiki/Local_Security_Authority_Subsystem_Service">Local Security Authority Subsystem (LSASS)</a>. LSASS is a Win process that handles auth, password change, and <a href="https://docs.microsoft.com/en-us/windows/win32/secauthz/access-tokens">access tokens</a>.</p>
  1060. <p>LSASS caches NTLM hashes and other creds, which can be extracted with Mimikatz <strong>sekurlsa</strong> module. We need to understand that LSASS runs under the SYSTEM user, with higher privs than Administrator. Therefore, we can only extract passwords if we are running Mimikatz as Administrator or higher, with <a href="https://devblogs.microsoft.com/oldnewthing/20080314-00/?p=23113">SeDebugPrivilege</a>. This access right allows the debugging of processes we own and those of other users.</p>
  1061. <p>We can elevate our privs to SYSTEM with tools like <a href="https://docs.microsoft.com/en-us/sysinternals/downloads/psexec">PsExec</a> or Mimikatz <a href="https://github.com/gentilkiwi/mimikatz/wiki/module-~-token">token elevation function</a>.
