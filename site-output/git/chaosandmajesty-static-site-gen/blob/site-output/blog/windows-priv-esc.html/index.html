<p>These notes upgrade the earlier summary with the lab’s full checklist: what to run, what to capture, and how to explain it back to defenders.</p>
<h3>Initial Enumeration</h3>
<pre><code>whoami /all
systeminfo | findstr /B /C:&quot;OS Name&quot; /C:&quot;OS Version&quot;
wmic qfe get HotFixID,InstalledOn

</code></pre>
<ul>
<li>Record logged-on users (<code>query user</code>, <code>Get-WmiObject Win32_LoggedOnUser</code>).</li>
<li>Document AV/EDR presence and application control (AppLocker, WDAC).</li>
</ul>
<h3>Credential Discovery</h3>
<ul>
<li>Search filesystem for configuration files: <code>dir /s *pass*</code> and <code>findstr /spin &quot;password&quot; *.ini *.xml</code>.</li>
<li>Dump registry keys: <code>reg query &quot;HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon&quot;</code> for auto-logon secrets.</li>
<li>Use <code>Seatbelt.exe</code> or <code>LaZagne</code> when permitted; log the tool version and detection status.</li>
</ul>
<h3>Service &amp; Task Abuse</h3>
<ul>
<li>Enumerate services: <code>sc query state= all</code>, <code>Get-Service | Where-Object {$_.PathName -like &#39;*\*&#39;}</code>.</li>
<li>Identify writable binaries:</li>
</ul>
<pre><code>accesschk.exe -uwcqv &quot;Authenticated Users&quot; * /accepteula
Get-CimInstance Win32_Service | Where-Object {$_.PathName -match &#39; &#39; -and $_.PathName -notmatch &#39;&quot;&#39;}
</code></pre>
<ul>
<li>Modify service path to point at payload (<code>sc config &lt;svc&gt; binPath= &quot;C:\Temp\shell.exe&quot;</code>).</li>
<li>Check scheduled tasks: <code>schtasks /query /fo LIST /v</code> → look for user-writable action scripts.</li>
</ul>
<h3>Token &amp; Privilege Abuse</h3>
<ul>
<li>Inspect token privileges: <code>whoami /priv</code>.</li>
<li>If <code>SeImpersonatePrivilege</code> present, run <code>PrintSpoofer.exe -i -c cmd.exe</code> or <code>RoguePotato</code> (document binary/version used).</li>
<li>For <code>SeBackupPrivilege</code>, use <code>diskshadow</code> or <code>reg save</code> to access SAM/LSA.</li>
</ul>
<h3>Automation &amp; Validation</h3>
<ul>
<li>Execute <code>winPEASany.exe</code> (record command, output location, and key findings). Treat results as leads; validate manually.</li>
<li>After escalation, capture proof: <code>whoami /groups</code>, <code>hostname</code>, <code>echo %USERNAME%</code>.</li>
<li>Clean up artifacts (restore service binaries, remove temporary files) and note cleanup actions.</li>
</ul>
<h3>Reporting &amp; Defense</h3>
<ul>
<li>For each finding, explain the root cause (misconfigured service ACL, weak registry permissions) and remediation (harden ACLs, enforce service isolation, enable UAC).</li>
<li>Suggest monitoring: Sysmon Event ID 7045 (service creation), 4688 (process creation), 4624 (logons), AppLocker logs.</li>
</ul>
<p>Windows privilege escalation is a game of disciplined enumeration. Follow this script, capture evidence, and deliver fixes the blue team can apply immediately.</p>

<h5>Understanding Windows Privileges and Access Control Mechanisms</h5>
<p>Win OS privs refer to the permissions of a specific account to perform system-related local operations, such as modding the FS or adding users.  Win needs a control mechanism to grant/deny those ops by determining if the user privs are sufficient for the op.  We will cover four different concepts/mechanisms:</p>
<ul>
<li><a href="https://docs.microsoft.com/en-us/windows/security/identity-protection/access-control/security-identifiers">Security Identifier (SID)</a></li>
<li>Win uses SID to identify entities.</li>
<li>A SID is a unique value assigned to each entity, or principal, that can auth.</li>
<li>Users.</li>
<li><em>Windows uses only the SID, not usernames, to identify principals for access control management.</em>.</li>
<li>Groups.<ul>
<li>SID for local accounts and groups is generated by <a href="https://docs.microsoft.com/en-us/windows-server/security/credentials-protection-and-management/configuring-additional-lsa-protection">Local Security Authority (LSA)</a></li>
<li>SID for domain users and domain groups is generated by the Domain Controller (DC)</li>
</ul>
</li>
<li>SID cannot be changed and is created at the time of User/Group creation.</li>
<li>Consists of segements delimited by <code>-</code>, structure like:
    - <code>S-R-X-Y</code><ul>
<li><code>S</code>: string is SID.
      - <code>R</code>: stands for revision, always set to <code>1</code> (overal structure of SID is v1)</li>
<li><code>X</code>: identifier authority that issues SID.</li>
<li>The most common identifier authority is <code>5</code> (NT Authority, local/domain users/groups)
     - <code>Y</code>: sub authorities of the identifier authority.</li>
<li>Every SID contains one or more sub authorities of the identifier authority.</li>
<li>Domain identifier.</li>
<li>Is the SID of the domain for domain users.</li>
<li>Is the SID of the local machine for local users.</li>
<li>Is <code>32</code> for built in principals.</li>
<li>Example SID of local user on Win sys:
                   - <code>S-1-5-21-1336799502-1441772794-948155058-1001</code>
                       - RID <code>1001</code><ul>
<li>RID starting at <code>1000</code> for majority principals, implys that this is the second local user created on the system, <code>1000</code> being the first.
                       -  SID with RID under <code>1000</code> are called <a href="https://docs.microsoft.com/en-us/windows/win32/secauthz/well-known-sids">well-known SIDs</a></li>
<li>generic and built in groups and users instead of specific groups and users.</li>
<li>Useful well-known SIDs for PrivEsc.</li>
</ul>
</li>
</ul>
</li>
</ul>
<pre><code>S-1-0-0                       Nobody        
S-1-1-0	                      Everybody
S-1-5-11                      Authenticated Users
S-1-5-18                      Local System
S-1-5-domainidentifier-500    Administrator
</code></pre>
<pre><code>  - Relative identifier (RID)
   - Determines principals such as users or groups.
</code></pre>
<p><em>Knowing how Win identifies principals is necessary for understanding access tokens and vital in Active Directory</em></p>
<ul>
<li><a href="https://docs.microsoft.com/en-us/windows/win32/secauthz/access-tokens">access token</a></li>
<li>On user auth Win generates and access token and assigns it to the user.</li>
<li>The token contains information that effectively describes the security context of a given user.</li>
<li>The security context is a set of rules/attributes currently in effect.</li>
<li>The security context of a token consists of:</li>
<li>SID of user.</li>
<li>SIDs of groups user is a member of.</li>
<li>The user groups and privs.</li>
<li>Further info describing the token.</li>
<li>When a user starts a process or thread a token is assigned to the object.</li>
<li>Known as a primary token.</li>
<li>Specifies the permissions the process/thread has when interacting with another object.</li>
<li>Is a copy of the access token of the user.</li>
<li>A thread can also have an <a href="https://docs.microsoft.com/en-us/windows/win32/secauthz/impersonation-tokens">impersonation token</a> assigned.</li>
<li>Provides a different security context than the owner process.</li>
<li>The thread interacts with objects on behalf of the impersonation token, not the primary.</li>
<li><a href="https://docs.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control">Mandatory Integrity Controls</a></li>
<li>Uses integrity levels to control access to securable objects.</li>
<li>The levels are akin to hierarchies of trust Win has in a running app or securable object.</li>
<li>When a proc starts or objects are created they receive the integrity level of the principal performing the op.</li>
<li>Exception being is an executable has low file integrity level the process integrity level will be low.</li>
<li>A principal with a lower integrity level cannot write to an object of a higher integrity level.</li>
<li>Even if permissions would normally allow them to do so.<ul>
<li>Since Win Vista processes run on five integraity levels:</li>
</ul>
</li>
</ul>
<pre><code>- System: SYSTEM (kernel, ...)
- High: Elevated users
- Medium: Standard users
- Low: Very restricted rights often used in sandboxed[^privesc_win_sandbox] processes or for directories storing temporary data
- Untrusted: Lowest integrity level with extremely limited access rights for processes or objects that pose the most potential risk
</code></pre>
<ul>
<li>We can display the integrity level of a proc with <a href="https://docs.microsoft.com/en-us/sysinternals/downloads/process-explorer">Process Explorer</a>:</li>
<li>Our current user with <code>whoami/groups</code></li>
<li>For files with <code>icacls</code>	.</li>
<li>The following example shows two PowerShell procs.</li>
<li>One started by reg <code>User</code></li>
<li>Another started as <code>Admin</code>
<img src="assets/static/resources/7ed11d3f9b98c2238c60a5a1d46c584c.png" alt="7ed11d3f9b98c2238c60a5a1d46c584c.png"></li>
<li>The PowerShell procs have the integrity levels of <code>High</code> and <code>Medium</code></li>
<li>We can infer that the <code>High</code> level proc was started by admin.</li>
<li>And the <code>Medium</code> level proc was started by the user.</li>
<li><a href="https://docs.microsoft.com/en-us/windows/security/identity-protection/user-account-control/user-account-control-overview">User Account Control (UAC)</a></li>
<li>Win security feature that protects the OS by running most applications and tasks with standard user privs.</li>
<li>Even if launched by an <code>Administrator</code></li>
<li>For this, and admin user is assigned two access tokens after successful logon.
- The first token is a standard user token.<ul>
<li>Aka filtered admin token.</li>
<li>Used to perform all non-priv ops.<ul>
<li>The second token is a regular admin token.</li>
</ul>
</li>
<li>Used to perform privileged ops.</li>
<li>Requires UAC prompt confirmation for use.</li>
</ul>
</li>
</ul>
<p>This introduction covers the basics of Win priv and access control mechanisms; SIDs, access tokens, integrity levels, and UAC.  Win offers numerous other mechanisms to control access to securable objects, several of which we will discuss and demonstrate in this module.</p>
<h5>Situational Awareness</h5>
<p>With our basic understanding of Win privs we will cover various methods to get situational awareness on a system.  Assume we used a client-side attack or exploited a vulnerability to access a Windows system as an unpriv user.  Before we attempt to elevate privs we must obtain info about the system we are on.</p>
<p>This step is crucial to understand the nature of the compromised system as well as discover possible PrivEsc vectors.  It is often skipped or minimized by inexperienced pen testers due to the nature of sifting through and interpreting large amounts of information.  Experienced pentesters know that by gathering as much as possible, they obtain valuable information about the target system, which they can use to create various actionable vectors to elevate their privs.</p>
<p>The key info we should always obtain:</p>
<pre><code>- Username and hostname
- Group memberships of the current user
- Existing users and groups
- Operating system, version and architecture
- Network information
- Installed applications
- Running processes
</code></pre>
<ul>
<li>Once we have performed enumeration and obtained this information we will have a solid understanding of our target sys.</li>

<h5>Service DLL Hijacking</h5>
<p>Replacing the binary of a service is a very effective way to attempt PrivEsc on Win systems.  Often our user does not have perms to replace the bins, we need to adapt to a more advanced method of Win service abuse.</p>
<ul>
<li><a href="https://docs.microsoft.com/en-us/troubleshoot/windows-client/deployment/dynamic-link-library">Dynamic Link Libraries (DLL)</a></li>
<li>Provide functionality to programs or the Win OS.</li>
<li>Contains code or resources.</li>
<li>Icon files.</li>
<li>Other exec files or objects.</li>
<li>Provide a way for devs to use and integrate existing functionality.</li>
<li>Win uses DLLs to store func needed by several components.</li>
<li>Otherwise each component would need the func in their own source.</li>
<li>On Unix systems these are called <a href="https://docs.oracle.com/cd/E19120-01/open.solaris/819-0690/6n33n7f8u/index.html">Shared Objects</a></li>
</ul>
<p>There are several ways to exploit how DLLs work on Win which can be effective for PrivEsc.</p>
<ul>
<li>Instead of overwriting the service bin we overwrite the DLL used by it.</li>
<li>The service may not function as expected because intended DLL func is missing.</li>
<li>Still lead to code exec of DLL code, allowing us to create a local admin for instance.</li>
<li>Another method, <a href="https://docs.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order">DLL search order</a></li>

    {

        break;
        case DLL_THREAD_ATTACH: // A process is creating a new thread.
        break;
        case DLL_THREAD_DETACH: // A thread exits normally.
        break;
        case DLL_PROCESS_DETACH: // A process unloads the DLL.

}

<h5>Unquoted Service Paths</h5>
<p>Another PrivEsc vector on Win OS is <a href="https://www.tenable.com/sc-report-templates/microsoft-windows-unquoted-service-path-vulnerability">unquoted service paths</a>.  This can be used when we have Write perms to a service main dir or sub dir but cannot replace the files directly.</p>
<p>Each Win service maps an exec file that runs when the service is started.  <em>If the path of this file contains one or more spaces and is NOT enclosed in quotes, we may be able to leverage into a PrivEsc attack</em>.</p>
<p>When a service is started and a proc is created:</p>
<ul>
<li>Func called <a href="https://docs.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessa">CreateProcess</a></li>
<li>The first param of the func is <code>IpApplicationName</code></li>
<li>Used to specify the name of exec.</li>
<li>Optionally the path of exec.</li>
<li>If the string contains spaces and is not enclosed in quotation marks.</li>
<li>It is not clear to the func where the file name ends and arg begins.</li>
<li>Allowing various interpretations.</li>
<li>The func starts interpreting the path from left to right until a space is reached.</li>
<li>At each space in the path the func uses the preceding part as the file name by adding <code>.exe</code> and the rest as args.
       - Example:</li>
</ul>
<pre><code class="language-powershell">C:\Program.exe
C:\Program Files\My.exe
C:\Program Files\My Program\My.exe
C:\Program Files\My Program\My service\service.exe
</code></pre>
<ul>
<li>This shows the order Win tries to interpret the service bin path to locate the exe.</li>
<li><strong>To exploit this:</strong>.</li>
<li>We must create a mal exec and place it in a corresponding interpreted path.</li>
<li>Matching its name to an interpreted name.</li>
<li>Once the service starts, our our mal exec gets executed with the same privs as the service that starts it.</li>
<li>Often the <code>LocalSystem</code>  account.</li>
<li>Resulting in successful PrivEsc.</li>
<li>In the example context our exec could be named <code>Program.exe</code></li>
<li>Place it in <code>C:\</code></li>
<li>Or names <code>My.exe</code></li>
<li>Place it in <code>C:\Program Files\</code> or <code>C:\Program Files\My Program\</code></li>
<li>The first two options would require perms we are unlikely to have.</li>
<li>The third options is more likely as it is the software&#39;s main dir.</li>
<li>If admin or dev set the perms for this dir too open we can place out mal bin there.</li>
</ul>

<h5>Scheduled Tasks</h5>
<p>Win uses Task Scheduler to automate various tasks.</p>
<ul>
<li>Clean-up activities.</li>
<li>Update management.</li>
</ul>
<p>Win terminology is <code>Schedule Tasks</code> or <code>Tasks</code> which are defined by one or more triggers.  A trigger is used as a condition, when met causing one or more actions to exec.  </p>
<ul>
<li>Example; a <code>trigger</code> can be set.</li>
<li>For a specific time and date.</li>
<li>At startup.</li>
<li>At log on.</li>
<li>On a Win event.</li>
</ul>
<p>There are 3 vital pieces of info for identifying possible PrivEsc vectors from a scheduled task.</p>
<ul>
<li>Which user account/Principal does the task get exec?</li>
<li>What triggers are specified for the task?</li>
<li>What actions are executed for the task when one or more triggers are met?</li>
</ul>
<p><strong>User Account/Principal</strong>
The first question helps us determine if we can abuse the task to lead to PrivEsc.</p>
<ul>
<li>If the task is exec in context of current user.</li>
<li>We cannot PrivEsc.</li>
<li>If the task runs as NT AUTHORITY\SYSTEM or an admin user.</li>
<li>A successful attack could lead to PrivEsc.</li>
</ul>
<p><strong>Specified Triggers</strong>
The second question tells us if the trigger was met in the past.</p>
<ul>
<li>If the trigger was met.</li>
<li>it will not run again, meaning it is not a viable target.</li>
<li>if the task would run in the future beyond the duration of the engagement.</li>
<li>we should search for another vector.</li>
<li>we should however note this in our findings.</li>
</ul>
<p><strong>Actions Executed When Triggers Met</strong>
The answer to this determines how we can potentially perform a PrivEsc attack.  In the majority of cases we can leverage familiar tactics:</p>
<ul>
<li>Replacing the binary.</li>
<li>Placing a missing DLL.
There are no service binaries with scheduled tasks, we do have programs and scripts specified by the actions.</li>
</ul>

<h5>Using Exploits</h5>
<p>We have seen how to leverage sensitive info and abuse Win components to achieve PrivEsc, we&#39;ll now explore three different exploits that can lead to PrivEsc and show an example of one.</p>
<ul>
<li><ol>
<li>application-based vulnerabilities.</li>
</ol>
</li>
<li><p>Apps installed on Win systems may contain vulns.</p>
</li>
<li><p>As learned in &quot;Locating Public Exploits&quot;.</p>
</li>
<li><p>If apps run with administrative perms we can exploit a vuln that leads to code exec.</p>
</li>
<li><p>Which would successfully achieve PrivEsc.</p>
</li>
<li><ol start="2">
<li>exploit vulns in <a href="https://en.wikipedia.org/wiki/Architecture_of_Windows_NT">Windows Kernel</a></li>
</ol>
</li>
<li><p>The vulns and research are very advanced.</p>
</li>
<li><p>Require extensive knowledge of the Win OS.</p>
</li>
<li><p>For our purpose, it is enough to know they can be used to achieve PrivEsc.</p>
</li>
<li><p>BEFORE using these exploits.</p>
</li>
<li><p>Consider they can easily crash a system.</p>
</li>
<li><p>Depending on engagement this may not be allowed.</p>
</li>
<li><p>Always have a clear understanding of assessment rules.</p>
</li>
<li><ol start="3">
<li>Win priv abuse.</li>
</ol>
</li>
<li><p>Non-priv users with key assigned privs can abuse to perform PrivEsc.
 - <code>SeImpersonatePrivilege</code></p>
<ul>
<li>Possible to leverage a token with a different security context.</li>
<li>Perform ops in the context of another account.</li>
</ul>
</li>
<li><p>Assigned by default to:</p>
</li>
<li><p>Local Administrators.</p>
</li>
<li><p>LOCAL SERVICE.</p>
</li>
<li><p>NETWORK SERVICE.</p>
</li>
<li><p>SERVICE accounts.</p>
</li>
<li><p>MS implemented to prevent.</p>
</li>
<li><p>Unauthed user from creating a service or server app.</p>
</li>
<li><p>Server apps impersonating clients connecting to it.</p>
<ul>
<li>Example:<ul>
<li><a href="https://docs.microsoft.com/en-us/windows/win32/rpc/rpc-start-page">Remote Procedure Call (RPC)</a></li>
<li><a href="https://docs.microsoft.com/en-us/windows/win32/ipc/named-pipes">named pipes</a></li>
</ul>
</li>
</ul>
</li>
</ul>
<p><em>Other privileges that may lead to privilege escalation are SeBackupPrivilege, SeAssignPrimaryToken, SeLoadDriver, and SeDebug. In this section, we&#39;ll closely inspect privilege escalation vectors in the context of SeImpersonatePrivilege.</em></p>
<ul>
<li>IRL it is rare to find standard users with this priv.</li>
<li>However, we often find it when exploiting vulns in ISS we server apps.</li>
<li>ISS will run as LocalService, LocalSystem, NetworkService, or ApplicationPoolIdentity.</li>
<li>All having <code>SeImpersonatePrivilege</code> assigned.</li>
<li>Also applies to other Win service.</li>
</ul>
<p>Let&#39;s briefly discuss named pipes and how to leverage SeImpersonatePrinilege to impersonate a priv user account!</p>
<ul>
<li><code>named pipe</code> are one method for local or remote <a href="https://en.wikipedia.org/wiki/Inter-process_communication">Inter-Process Communication (IPC)</a></li>
<li>Offer func of two unrelated procs sharing/transfering data.</li>
<li>A named pipe server can create a named pipe that a named pipe client can connect to via specified name.</li>
<li>Server/client do not need to be on the same sys.</li>
<li>Once a client connects to a named pipe.</li>
<li>Server can leverage SeImpersonatePrivilege to impersonate this client.</li>
<li>After capturing auth from the connection proc.</li>
<li>To abuse, we need to coerce a priv proc to connect to a controlled named pipe.</li>
<li>We can them impersonate the account connecting to the named pipe.</li>
<li>Performing actions in its security context.</li>
</ul>
