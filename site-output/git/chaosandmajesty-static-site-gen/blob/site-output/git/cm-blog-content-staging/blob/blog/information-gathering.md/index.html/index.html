  29. <h1>PEN-200 Module 6 — Information Gathering Playbook</h1>
  30. <h2>TLDR;</h2>
  31. <p>Recon sets the tempo for every engagement. This second pass keeps the methodology tight but adds the gritty detail from the lab notebook so you can copy/paste a full workflow the moment scope is approved.</p>
  32. <h3>Kick-Off Checklist</h3>
  33. <ul>
  34. <li>Confirm scope, out-of-bounds hosts, and rate limits; log the ticket number in your notes.</li>
  35. <li>Stand up a <code>screen</code> or <code>tmux</code> session with panes for passive OSINT, active probes, and a Markdown scratchpad.</li>
  36. <li>Create a loot directory (<code>mkdir -p engagements/acme/recon</code>) and initialize a timeline file to capture timestamps.</li>
  37. </ul>
  38. <h3>Passive Discovery (Stay Quiet First)</h3>
  39. <ol>
  40. <li><strong>WHOIS &amp; Registrars</strong><ul>
  41. <li>Identify registrars, name servers, and contact emails.</li>
  42. <li><code>whois megacorpone.com</code></li>

  45. </li>

  88. <h3>Notes and Reporting Artifacts</h3>
  89. <ul>
  90. <li>Maintain a CSV of discovered hosts with fields for IP, hostname, service, credential status, and notes.</li>
  91. <li>Paste full command outputs into per-host files—future you will need them for exploitation and the appendix.</li>

  96. <h4>6 Information Gathering</h4>
  97. <p>Learn how to methodically map such an attack surface using both passive and active means, and understand how to leverage this information during the entire penetration test lifecycle.</p>
  98. <h5>6.1 The Penetration Testing Lifecycle</h5>
  99. <ul>
  100. <li>Understand the stages of a Penetration Test.</li>
  101. <li>Learn the role of Information Gathering inside each stage.</li>
  102. <li>Understand the differences between Active and Passive Information Gathering.</li>
  103. </ul>
  104. <p>To keep a company&#39;s security posture as tightly controlled as possible, we should conduct penetration testing on a regular cadence and after every time there&#39;s a significant shift in the target&#39;s IT architecture.</p>
  105. <p>A typical penetration test comprises the following stages:</p>
  106. <ul>
  107. <li>Defining the Scope.</li>
  108. <li>Information Gathering.</li>
  109. <li>Vulnerability Detection.</li>
  110. <li>Initial Foothold.</li>
  111. <li>Privilege Escalation.</li>
  112. <li>Lateral Movement.</li>
  113. <li>Reporting/Analysis.</li>
  114. <li>Lessons Learned/Remediation.</li>
  115. </ul>
  116. <p>The scope of a penetration test engagement defines which IP ranges, hosts, and applications should be test subjects during the engagement, as compared to out-of-scope items that should not be tested.</p>
  117. <p>To begin information gathering, we typically perform reconnaissance to retrieve details about the target organization&#39;s infrastructure, assets, and personnel. This can be done either passively or actively. While the former technique aims to retrieve the target&#39;s information with almost no direct interaction, the latter probes the infrastructure directly. Active information gathering reveals a bigger footprint, so it is often preferred to avoid exposure by gathering information passively.</p>
  118. <h5>6.2 Passive Information Gathering</h5>
  119. <ul>
  120. <li>Understand the two different Passive Information Gathering approaches.</li>
  121. <li>Learn about Open Source Intelligence (OSINT)</li>
  122. <li>Understand Web Server and DNS passive information gathering.</li>
  123. </ul>
  124. <p><a href="https://en.wikipedia.org/wiki/Open-source_intelligence">Open-source Intelligence (OSINT)</a> the process of collecting openly-available information about a target, generally without any direct interaction with that target.</p>
  125. <p><strong>Strict interpretation</strong> we never communicate with the target directly. For example, we could rely on third parties for information, but we wouldn&#39;t access any of the target&#39;s systems or servers. Using this approach maintains a high level of secrecy about our actions and intentions, but can also be cumbersome and may limit our results.</p>
  126. <p><strong>Loose</strong> interpretation, we might interact with the target, but only as a normal internet user would. For example, if the target&#39;s website allows us to register for an account, we could do that. However, we would not test the website for vulnerabilities during this phase.</p>
  127. <ul>
  128. <li>Cyclical process rather than linear.</li>
  129. <li>&quot;next step&quot; depends on &quot;previous step&quot;.</li>
  130. <li>Obtain info that clarifies/expands <a href="https://en.wikipedia.org/wiki/Attack_surface">attack surface</a></li>
  131. <li>Help conduct phishing campaign.</li>
  132. <li>Supplements other steps, i.e. password guessing which can lead to account compromise.</li>
  133. </ul>
  134. <p><strong>Real World Example:</strong>
  135. Several years ago, the team at OffSec was tasked with performing a penetration test for a small company. This company had virtually no internet presence and very few externally-exposed services, all of which proved to be secure. There was practically no attack surface to be found. After a focused passive information gathering campaign that leveraged various Google search operators, connected bits of information &quot;piped&quot; into other online tools, and a bit of creative and logical thinking, we found a forum post made by one of the target&#39;s employees in a stamp-collecting forum:</p>
  136. <pre><code>Hi!
  137. I&#39;m looking for rare stamps from the 1950&#39;s - for sale or trade.
  138. Please contact me at david@company-address.com
  139. Cell: 999-999-9999
  140. </code></pre>
  141. <p>We used this information to launch a semi-sophisticated client-side attack. We quickly registered a stamps-related domain name and designed a landing page that displayed various rare stamps from the 1950&#39;s, which we found using Google Images. The domain name and design of the site definitely increased the perceived reliability of our stamp trading website.</p>
  142. <p>Next, we embedded some nasty client-side attack exploit code in the site&#39;s web pages, and called &quot;David&quot; during the workday. During the call, we posed as a stamp collector that had inherited their Grandfather&#39;s huge stamp collection.</p>
  143. <p>David was overjoyed to receive our call and visited the malicious website to review the &quot;stamp collection&quot; without hesitation. While browsing the site, the exploit code executed on his local machine and sent us a reverse shell.</p>
  144. <p>This is a good example of how some innocuous passively-gathered information, such as an employee engaging in personal business with his corporate email, can lead to a foothold during a penetration test. Sometimes the smallest details can be the most important.</p>
  145. <p>While &quot;David&quot; wasn&#39;t following best practices, it was the company&#39;s policy and lack of a security awareness program that set the stage for this breach. Because of this, we avoid casting blame on an individual in a written report. Our goal as penetration testers is to improve the security of our client&#39;s resources, not to target a single employee. Simply removing &quot;David&quot; wouldn&#39;t have solved the problem.</p>

  232. <h6>Google Hacking</h6>
  233. <p>The term &quot;Google Hacking&quot; was popularized by Johnny Long in 2001.</p>
  234. <ul>
  235. <li><a href="https://en.wikipedia.org/wiki/Google_hacking">Wiki</a></li>
  236. <li><a href="https://www.amazon.com/Google-Hacking-Penetration-Testers-Johnny/dp/0128029641/ref=dp_ob_image_bk">Google Hacking for Penetration Testers</a></li>
  237. <li>How search engines, like Google, can be used to uncover crit info, vulns, and misconfigured websites.</li>
  238. <li>Utilizes clever search string and <a href="https://support.google.com/websearch/answer/2466433?hl=en">operators</a></li>
  239. <li>Most of which work with a variety of search engines.</li>
  240. <li>Iterative process.</li>
  241. <li>Begin with broad search.</li>
  242. <li>Narrow using operators to sift out irrelevant results.</li>
  243. </ul>
  244. <p><strong>Common Operators</strong></p>
  245. <ul>
  246. <li><p>The <strong>site</strong> operator limits searches to a single domain.</p>
  247. </li>
  248. <li><p>Used to gather a rough idea of org web presence.</p>
  249. </li>
  250. <li><p>Example: <code>site:megacorpone.com</code></p>
  251. </li>
  252. <li><p>Additional operators used to narrow results.</p>
  253. </li>
  254. <li><p>Locate txt files.</p>
  255. </li>
  256. <li><p>Example: <code>filetype:txt</code></p>
  257. </li>
  258. <li><p><strong>Example:</strong> <code>site:megacorpone.com filetype:txt</code></p>
  259. </li>
  260. <li><p>Returns interesting result, <code>robots.txt</code></p>
  261. </li>
  262. </ul>
  263. <pre><code>User-agent: *
  264. Allow: /
  265. Allow: /nanites.php
  266. </code></pre>
  267. <p>The robots.txt file instructs web crawlers, such as Google&#39;s search engine crawler, to allow or disallow specific resources. In this case, it revealed a specific PHP page (/nanities.php) that was otherwise hidden from the regular search, despite being listed allowed by the policy.</p>
  268. <ul>
  269. <li><p>The <strong>ext</strong> operator.</p>
  270. </li>
  271. <li><p>Examples: <code>ext:php</code>, <code>ext:xml</code>, <code>ext:py</code></p>
  272. </li>
  273. <li><p>Will find indexed PHP Pages, XML, and Python pages, respectively.</p>
  274. </li>
  275. <li><p>Operators can be modified with <strong>-</strong> to exclude results.</p>
  276. <ul>
  277. <li>Example <code>site:megacorpone.com -filetype:html</code></li>
  278. </ul>
  279. </li>
  280. <li><p>Excludes HTML pages from results! <strong>Very interesting!</strong>.</p>
  281. </li>
  282. <li><p>May return web directory indices.</p>
  283. </li>
  284. <li><p>The <strong>intitle</strong> operator.</p>
  285. </li>
  286. <li><p>Find pages that return a string in title.</p>
  287. </li>
  288. <li><p>Example: <code>intitle:&quot;index of&quot; &quot;parent directory&quot;</code></p>
  289. </li>
  290. <li><p>Find pages that contain &quot;index of&quot; in title and &quot;parent directory&quot; in page.</p>
  291. </li>
  292. <li><p>The output refers to <a href="https://cwe.mitre.org/data/definitions/548.html">directory listing</a> pages.</p>
  293. </li>
  294. <li><p>List the file contents of the directories without index pages.
  295. - Misconfigurations like this can reveal interesting files and sensitive information.</p>
  296. </li>
  297. </ul>

  350. <h6>Security Headers and SSL/TLS</h6>
  351. <ul>
  352. <li>Several other specialty websites that we can use to gather information about a website or domain&#39;s security posture.</li>
  353. <li>Some blur the line between passive and active information gathering.
  354. - <strong>key point</strong> for our purposes is that a <strong>third-party is initiating any scans or checks</strong>.</li>
  355. <li><a href="https://securityheaders.com/">Security Headers</a></li>
  356. <li>Search <code>www.megacorpone.com</code></li>
  357. <li>Missing several defensive headers.</li>
  358. <li>Content-Security-Policy.</li>
  359. <li>An effective measure to protect your site from XSS attacks. By whitelisting sources of approved content, you can prevent the browser from loading malicious assets.</li>
  360. <li>X-Frame-Options.</li>
  361. <li>Tells the browser whether you want to allow your site to be framed or not. By preventing a browser from framing your site you can defend against attacks like clickjacking. Recommended value &quot;X-Frame-Options: SAMEORIGIN&quot;.</li>
  362. <li>X-Content-Type-Options.</li>
  363. <li>Stops a browser from trying to MIME-sniff the content type and forces it to stick with the declared content-type. .
  364. - The only valid value for this header is <code>X-Content-Type-Options: nosniff</code></li>

  370. - Server hardening is the overall process of securing a server via configuration.   388. <h6>DNS Enumeration</h6>
  389. <p>The <a href="https://en.wikipedia.org/wiki/Domain_Name_System">Domain Name System (DNS)</a> is a distributed database responsible for translating user-friendly domain names into IP addresses.</p>
  390. <p>Common types of DNS records include:</p>
  391. <ul>
  392. <li>NS: Nameserver records contain the name of the authoritative servers hosting the DNS records for a domain.</li>
  393. <li>A: Also known as a host record, the &quot;a record&quot; contains the IPv4 address of a hostname (such as <a href="http://www.megacorpone.com">www.megacorpone.com</a>).</li>
  394. <li>AAAA: Also known as a quad A host record, the &quot;aaaa record&quot; contains the IPv6 address of a hostname (such as <a href="http://www.megacorpone.com">www.megacorpone.com</a>).</li>
  395. <li>MX: Mail Exchange records contain the names of the servers responsible for handling email for the domain. A domain can contain multiple MX records.</li>
  396. <li>PTR: Pointer Records are used in reverse lookup zones and can find the records associated with an IP address.</li>
  397. <li>CNAME: Canonical Name Records are used to create aliases for other host records.</li>
  398. <li>TXT: Text records can contain any arbitrary data and be used for various purposes, such as domain ownership verification.</li>
  399. </ul>

  568. <h6>TCP/UDP Port Scanning Theory</h6>
  569. <p>The process of inspecting TCP or UDP ports on a remote machine with the intention of detecting what services are running on the target and what potential attack vectors may exist.</p>
  570. <ul>
  571. <li><p>Please note that port scanning is not representative of traditional user activity and could be considered illegal in some jurisdictions. Therefore, it should not be performed outside the labs without direct, written permission from the target network owner.</p>
  572. </li>
  573. <li><p>Implications of port scanning.</p>
  574. </li>
  575. <li><p>Large amount of traffic.</p>
  576. </li>
  577. <li><p>Intrusive nature.</p>
  578. </li>
  579. <li><p>Running them blindly can have adverse effects on systems/network.</p>
  580. </li>
  581. <li><p>Overloading switch/servers/links.</p>
  582. </li>
  583. <li><p>Trigger IDS/IPS.</p>
  584. </li>
  585. </ul>
  586. <p><strong>Proper Port Scanning Methodology</strong></p>
  587. <ul>
  588. <li>Do not run full scan against network.</li>
  589. <li>Scan for ports 80, 443.</li>
  590. <li>Return web servers.</li>
  591. <li>Run full port scan against web servers.</li>
  592. <li>Dynamic and iterative process.</li>
  593. </ul>
  594. <p><strong>TCP Scanning Techniques</strong></p>
  595. <ul>
  596. <li>Simplest form, the CONNECT scan.<ul>
  597. <li>Takes advantage of <a href="http://support.microsoft.com/kb/172983">3-way TCP handshake</a></li>
  598. <li>Host sends TCP SYN packet to server on dest port.</li>
  599. <li>If dest port is open, the server responds with SYN-ACK packet.</li>
  600. <li>Closed ports actively reject the connection attempt via a RST-ACK packet.</li>
  601. <li>Client responds with ACK to complete handshake.</li>
  602. </ul>
  603. </li>
  604. <li>If the 3-way handshake completes successfully the port is considered open.</li>
  605. </ul>
  606. <p>Demonstrate by running a <strong>TCP Netcat port scan</strong> on ports 3388-3390. We&#39;ll use the -w option to specify the connection timeout in seconds, as well as -z to specify zero-I/O mode, which is used for scanning and sends no data. Netcat closes successful connection by sending a FIN-ACK packet</p>
  607. <pre><code class="language-bash">kali@kali:~$ nc -nvv -w 1 -z 192.168.50.152 3388-3390
  608. (UNKNOWN) [192.168.50.152] 3390 (?) : Connection refused
  609. (UNKNOWN) [192.168.50.152] 3389 (ms-wbt-server) open
  610. (UNKNOWN) [192.168.50.152] 3388 (?) : Connection refused
  611. sent 0, rcvd 0
  612. </code></pre>
  613. <p><strong>UDP Scanning</strong></p>
  614. <ul>
  615. <li>UDP is stateless and does not involve a three-way handshake, the mechanism behind UDP port scanning is different from TCP.</li>
  616. <li>Simple UDP scan.</li>
  617. <li>Send empty UDP packet to port.</li>
  618. <li>If port is open, packet will be passed to application layer.</li>
  619. <li>Response depends on on the application is programmed.</li>
  620. <li>If port is closed, target should respond with ICMP Port unreachable.</li>
  621. <li>Sent by UDP/IP stack of target system.</li>
  622. <li>Most scanners rely on ICMP Port unreachable to infer status of target port.</li>
  623. <li>Often unreliable, firewalls/routers may drop ICMP packets.</li>
  624. <li>This can lead to false positives.</li>
  625. <li>Using protocol specific UDP port scanners yield better results.</li>
  626. <li>UDP scans generate less traffic than TCP scans.</li>
  627. </ul>

  754. <li><p>Stealth SYN scan.</p>
  755. </li>
  756. <li><p>Option <code>-sS</code></p>
  757. </li>
  758. <li><p>Default method when no scan option is specified.</p>
  759. </li>
  760. <li><p>Requires raw socket privs.</p>
  761. </li>
  762. <li><p>SYN scanning is a TCP port scanning method that involves sending SYN packets to various ports on a target machine without completing a TCP handshake.</p>
  763. </li>
  764. <li><p>If TCP port is open, a SYN-ACK will be send back, and the scanner does not send the final ACK.</p>
  765. </li>
  766. <li><p>The three-way handshake is never completed, the information is not passed to the application layer and as a result, will not appear in any application logs.</p>
  767. </li>
  768. <li><p><strong>NOTE:</strong> Please note that term &quot;stealth&quot; refers to the fact that, in the past, firewalls would fail to log incomplete TCP connections. This is no longer the case with modern firewalls and although the stealth moniker has stuck around, it could be misleading.</p>

  1322. <h6>SNMP Enumeration</h6>
  1323. <p><strong>Treasure Trove of Easy Data</strong></p>
  1324. <ul>
  1325. <li>Simple Network Management Protocol (SNMP) is not well-understood by many network administrators.</li>
  1326. <li>Results in SNMP misconfigurations.</li>
  1327. <li>Result in significant information leaks.</li>
  1328. <li>SNMP is based on UDP.</li>
  1329. <li>Stateless proto.</li>
  1330. <li>Susceptible to IP spoofing and replay attacks.</li>
  1331. <li>Proto 1, 2, 2c offer no traffic encryption.</li>
  1332. <li>SNMP info can be easily intercepted over a local network.</li>
  1333. <li>Weak auth schemes.</li>
  1334. <li>Commonly left configured with default public and private community strings.
  1335. - Until recently, SNMPv3, which provides authentication and encryption, has been shipped to support only DES-56, proven to be a weak encryption scheme that can be easily brute-forced. A more recent SNMPv3 implementation supports the AES-256 encryption scheme.</li>
  1336. <li><strong>Main Feature:</strong> SNMP MIB Tree.</li>
  1337. <li>SNMP Management Information Base (MIB) is a database containing information usually related to network management.</li>
  1338. <li>Tree structure.</li>
  1339. <li>Branches represent different organizations or network functions.</li>
  1340. <li>Leaves (final endpoints) correspond to specific variable values.
  1341. - Accessible and can be probed by external user.
  1342. - <a href="https://www.ibm.com/support/knowledgecenter/ssw_aix_71/commprogramming/mib.html">IBM Knowledge Center on MIB Tree</a></li>
  1343. </ul>
