## 24.1 Enumerating the Public Network
 
- Enumerate machines on a public network
- Obtain useful information to use for later attacks

### MAILSRV1

Before starting a pentest we want to setup and structure our environment as we will collect a huge amount of information in due course.

*Structuring and isolating data and settings for multiple penetration tests can be quite the challenge. By reusing a Kali VM we could accidentally expose previous-client data to new networks. Therefore, it is recommended to use a fresh Kali image for every assessment.*

We will create our main directory `/home/$USER/OffSec/beyond` and two sub-directories for each target we currently have access to.  We will also create a `creds.txt` file to keep track of valid creds and users.
```bash
┌──(m4xx3d0ut㉿h4ckt0p)-[~/OffSec/beyond]
└─$ tree ../beyond
../beyond
├── creds.txt
├── mailsrv1
└── websrv1
```

Now that we setup our work env, we are ready to enum our first target MAILSRV1.

*Documenting our findings is a crucial process for every penetration test. For this Module, we'll store results in the basic work environment we just set up. However, Markdown editors, such as Obsidian, have become quite popular for documenting findings and data in real assessments as they are application-independent and contain functions that will simplify report writing and collaboration.*

Start with a portscan of MAILSRV1 using Nmap, this is often the first active info gathering method we perform to get an overview of ports/services accessible to us.

*In a real penetration test, we would also use passive information gathering techniques such as Google Dorks and leaked password databases to obtain additional information. This would potentially provide us with usernames, passwords, and sensitive information.*

Use option `-sV` to enable service/version detection and `-sC` to use the default Nmap scripts.  Generate an output file with `-oN` to save the scan results.

- the output confirms the page uses `WordPress 6.0.2`

The WordPress core often has vulns, but their dev team is quick to patch.  This version was released in August of 2022.

WordPress plugins and themes, often written by the community, often feature improperly patched vulnerabilities or ones that are simply never fixed.  This makes themes and plugins a prime target.

We can perform a scan on these components with `WPScan`, a vuln scanner for WordPress that requires an API token.  A limited API key can be obtained for free by registering an account on the WPScan homepage.  It can still be used effectively without an API key to enumerate WP instances.

To perform a scan without an API key:
- target URL `--url`
- plugin detection `aggressive`
- enum popular plugins `--enumerate p`
- output file `-o`
```bash
┌──(m4xx3d0ut㉿h4ckt0p)-[~/OffSec/beyond]
└─$ wpscan --url http://192.168.247.244 --enumerate p --plugins-detection aggressive -o websrv1/wpscan
```

## 24.2 Attacking a Public Machine

- Use vulnerabilities in WordPress Plugins 
- Crack the passphrase of an SSH private key
- Elevate privileges using sudo commands
- Leverage developer artifacts to obtain sensitive information

### Initial Foothold

### Services and Sessions

In the prior section we performed basic enum to gain an understanding of the AD env, now we will further enum the target net to identify potential attack vectors.
- We'll review all active user sessions on machines
- We'll examine user accounts for [SPNs](https://learn.microsoft.com/en-us/windows/win32/ad/service-principal-names)
- leverage Nmap and CrackMapExec via SOCKS5 proxy to identify accessible services

We will again use a custom query in BloodHound to review active sessions.  In the Cypher Query Language we can build a [relationship query](https://neo4j.com/developer/cypher/querying/) with syntax:
```
(NODES)-[:RELATIONSHIPS]->(NODES)
```

The relationship for this case is `[:HasSession]`, the first node specified by a property is `(c:Computer)`, and the second is `(m:User)`.  Meaning the edge between the two nodes source is the computer object.  We'll use `p` to store and display the data.
```
MATCH p = (c:Computer)-[:HasSession]->(m:User) RETURN p
```
![3bfbfb23582551875d2c6cf2272f53c9.png](../_resources/3bfbfb23582551875d2c6cf2272f53c9.png)
- our query shows 3 active sessions
	- CLIENTWK1 has an active session with user `marcus`
		- as expected
	- MAILSRV1 has an active session with user `beccy`
		- previously unknown admin account
		- if we get privileged access to this machine we can potentially extract the NTLM hash of this user
	- INTERNALSRV1 shows an active session as an SID
		- BloodHound uses this representation of a principal when domain ID of the SID is from a local machine

## 24.5 Attacking an Internal Web Application

- Perform Kerberoasting

### Speak Kerberoast and Enter

Based on the info we gathered thus far, the web app on INTERNALSRV1 is the most promising target we have.  We can use WPScan or a password attack to log in to the WP dashboard.

Each time we gain new intel, we reassess what we already know.  We know that `daniela` has an http SPN mapped to INTERNALSRV1, we may assume `daniela` is able to log in to the WP app.

We know that `daniela` is kerberoastable so we can attempt to retrieve their password.  If we crack the TGS-REP password hash, we can try the creds against INTERNALSRV1.

Let's pause for a moment and plan our next steps, we have two viable attack vectors at this point.

First, we can upload a maliscious WordPress plugin to gain a reverse shell on INTERNALSRV1.

Second, we must review the BloodHound results again and make some assumptions.  We know that the local admin account has an active session on INTERNALSRV1.  From this we can infer that the user account is used to run the WP instance.

Also, it's not uncommon for the local admin to use the same password across computers in a domain.  We can assume this it true for the target env.

We also learned that `beccy` has an active session on MAILSRV1, therefore domain admin creds may be cached on the system.

Since SMB signing is disabled on MAILSRV1 and INTERNALSRV1 we may be able to execute a relay attack if we can force auth.

Based on this we can define a plan for the second attack vector.  First we can attempt to force an auth request by abusing the backup directory path of the Backup Migration WP plugin on INTERNALSRV1.  If we set the destination path to our Kali machine, we can use `impacket-ntlmrelayx` to [relay](https://www.kali.org/tools/impacket-scripts/) the incoming connection to MAILSRV1.  If our assumtion is correct, the auth request is made in the context of local Admin on INTERNALSRV1, which may have the same password as the local Admin account on MAILSRV1.

If successful, we will achieve privileged code exec on MAILSRV1, which we can leverage to extract the NTLM hash for `beccy`, which would meet one of the primary goals of the pentest.

Since the second attack vector not only yeilds code exec on a single system, but achieves a primary test goal, we will perform the relay attack first.
