  14. <h1>Platform Config: MicroK8s + Gitea (+ Actions) → Export → GitOps</h1>
  15. <p>This repo captures how we deploy Gitea on MicroK8s, add a Gitea Actions runner, create our configuration repo in Gitea, and export the cluster/node config back into this repo (with Secrets encrypted). It also outlines the next steps toward GitOps, including Flux wiring, ValidatingAdmissionPolicy-based guardrails, and our <strong>capacitor-next</strong> admin &amp; read‑only service accounts.</p>
  16. <blockquote>
  17. <p><strong>Assumes</strong></p>
  18. <ul>
  19. <li>MicroK8s with <code>ingress</code>, <code>dns</code>, and <code>metallb</code> (or equivalents) enabled.</li>
  20. <li><code>helm</code> (or <code>microk8s helm3</code>) available.</li>
  21. <li>cert-manager installed and a <strong>selfsigned Issuer</strong> in <code>git-local</code>.</li>
  22. <li><code>ingress-nginx</code> present and listening for <strong>TCP services</strong> (SSH on <code>32222</code>).</li>
  23. <li>Tools on the node/admin box: <code>jq</code>, <code>yq</code> (v4), <code>sops</code> (v3.10+), <code>age</code>.</li>
  24. <li>Repo layout already initialized (this repo) with <code>tools/export-all.sh</code>.</li>
  25. </ul>
  26. <p><strong>Tip:</strong> we export <em>live</em> state. That’s great for disaster‑recovery and drift audit. For GitOps, we later carve out <strong>intent</strong> manifests/values from those exports.</p>
  27. </blockquote>

  138. <h2>7) Deploy the Gitea Actions runner</h2>
  139. <p>The runner uses a separate chart. We register with the instance token from the Gitea UI.</p>
  140. <pre><code class="language-bash"># In the Gitea UI: Site Admin → Actions → Runners → Registration Token (instance-level)
  141. export GITEA_INSTANCE_REG_TOKEN=&quot;&lt;paste-from-ui&gt;&quot;
  142. ​
  143. # Secret for runner registration
  144. kubectl -n git-local create secret generic gitea-runner-token \
  145. --from-literal=GITEA_RUNNER_REGISTRATION_TOKEN=&quot;$GITEA_INSTANCE_REG_TOKEN&quot; \
  146. --dry-run=client -o yaml | kubectl apply -f -
  147. </code></pre>
  148. <p>Create values for the runner (includes optional CA mount for TLS):</p>
  149. <pre><code class="language-bash">cat &gt; actions.values.yaml &lt;&lt;&#39;EOF&#39;
  150. enabled: true
  151. existingSecret: &quot;gitea-runner-token&quot;
  152. existingSecretKey: &quot;GITEA_RUNNER_REGISTRATION_TOKEN&quot;
  153. giteaRootURL: &quot;https://gitea.core.home.arpa&quot;
  154. ​
  155. statefulset:
  156. actRunner:
  157. # remove &#39;insecure: true&#39; once CA trust is wired
  158. config: |
  159. log:
  160. level: info
  161. cache:
  162. enabled: false
  163. runner:
  164. # insecure: true
  165. ​
  166. # Ensure the DinD sidecar trusts the same CA before dockerd starts
  167. dind:
  168. command:
  169. - sh
  170. - -c
  171. - |
  172. update-ca-certificates
  173. exec dockerd-entrypoint.sh &quot;$@&quot;
  174. - --
  175. ​
  176. # Trust the same certificate the ingress serves
  177. extraVolumes:
  178. - name: gitea-cert
  179. secret:
  180. secretName: gitea-tls
  181. items:
  182. - key: ca.crt
  183. path: gitea-root.crt
  184. extraVolumeMounts:
  185. - name: gitea-cert
  186. mountPath: /etc/ssl/certs/gitea-root.crt
  187. subPath: gitea-root.crt
  188. readOnly: true
  189. EOF
  190. </code></pre>
  191. <p>Install runner:</p>
  192. <pre><code class="language-bash">git clone https://gitea.com/gitea/helm-actions.git
  193. helm -n git-local upgrade --install gitea-actions ./helm-actions -f actions.values.yaml
  194. ​
  195. kubectl -n git-local rollout status sts/gitea-actions-act-runner
  196. </code></pre>
  197. <p>Runner should show up in Gitea UI under <strong>Site Admin → Actions → Runners</strong>.</p>

  210. <h2>9) Export live cluster state back into this repo</h2>
  211. <h3>9.1 SOPS setup (Age)</h3>
  212. <p>Generate an age key (one time):</p>
  213. <pre><code class="language-bash">mkdir -p ~/.config/sops/age
  214. age-keygen -o ~/.config/sops/age/keys.txt
  215. grep &quot;# public key:&quot; ~/.config/sops/age/keys.txt
  216. </code></pre>
  217. <p>Put the <strong>public</strong> key into <code>.sops.yaml</code> at repo root:</p>
  218. <pre><code class="language-yaml">creation_rules:
  219. - path_regex: ^live-export/secrets/.+\.ya?ml$
  220. encrypted_regex: &#39;^(data|stringData)$&#39;
  221. age: &#39;age1your_public_key_here&#39;
  222. </code></pre>
  223. <blockquote>
  224. <p><strong>Important:</strong> <code>age:</code> should be a <strong>single string</strong>, not a YAML list.</p>
  225. </blockquote>
  226. <h3>9.2 Run the exporter</h3>
  227. <p>From repo root:</p>
  228. <pre><code class="language-bash">chmod +x tools/export-all.sh
  229. ./tools/export-all.sh --helm --include-crds --encrypt-secrets
  230. </code></pre>
  231. <p>What it does:</p>
  232. <ul>
  233. <li>Exports <strong>cluster‑scoped</strong> and <strong>namespaced</strong> objects (cleaned of server‑managed fields) under <code>live-export/kubernetes/...</code></li>
  234. <li>Exports Helm <code>values.yaml</code>, <code>values-all.yaml</code>, and rendered <code>manifest.yaml</code> under <code>live-export/helm/&lt;ns&gt;/&lt;release&gt;/</code></li>
  235. <li>Exports all CRDs into <code>live-export/kubernetes/cluster-scoped/crds/all-crds.yaml</code></li>
  236. <li>Moves all Secrets to <code>live-export/secrets/&lt;ns&gt;/&lt;name&gt;.yaml</code> and <strong>SOPS‑encrypts</strong> them</li>
  237. <li>Prints a summary and cleans <code>.tmp/</code></li>
  238. </ul>
  239. <p>Verify Secrets are encrypted:</p>
  240. <pre><code class="language-bash">grep -RIn --include=&#39;*.yaml&#39; &#39;^sops:&#39; live-export/secrets &amp;&amp; echo &quot;OK: encrypted&quot;
  241. </code></pre>
  242. <p>Commit the export:</p>
  243. <pre><code class="language-bash">git add -A
  244. git commit -m &quot;Live export: k8s + helm (+crds); secrets encrypted&quot;
  245. git push
  246. </code></pre>

  248. <h1>Part 2 — Flux GitOps wiring</h1>
  249. <p>We manage the cluster via Flux, with a tidy <strong>root → folder of child Kustomizations → per‑area Kustomizations</strong> pattern.</p>
  250. <h2>10) Bootstrap Flux to this repo</h2>
  251. <pre><code class="language-bash">flux bootstrap git \
  252. --url=ssh://git@gitea.core.home.arpa:32222/&lt;ORG_OR_USER&gt;/platform-config.git \
  253. --branch=main \
  254. --path=gitops/clusters/microk8s-prod
  255. </code></pre>
  256. <p>This creates <code>GitRepository/platform-config</code> and a starter <code>Kustomization</code>. We then layer our own structure.</p>
  257. <h2>11) Root Kustomization that <em>tracks the folder of child CRs</em></h2>
  258. <blockquote>
  259. <p>Flux won’t “discover” a new Kustomization CR from git unless the CR itself is applied once or a parent already manages that folder. We use a one‑time <code>kubectl apply</code> for the parent CR below.</p>
  260. </blockquote>
  261. <pre><code class="language-yaml"># gitops/clusters/microk8s-prod/flux-system/cluster-root.yaml
  262. apiVersion: kustomize.toolkit.fluxcd.io/v1
  263. kind: Kustomization
  264. metadata:
  265. name: cluster-root
  266. namespace: flux-system
  267. spec:
  268. interval: 10m
  269. prune: true
  270. wait: true
  271. path: ./gitops/clusters/microk8s-prod/kustomizations
  272. sourceRef:
  273. kind: GitRepository
  274. name: platform-config
  275. namespace: flux-system
  276. </code></pre>
  277. <p>Apply once and reconcile:</p>
  278. <pre><code class="language-bash">kubectl apply -f gitops/clusters/microk8s-prod/flux-system/cluster-root.yaml
  279. flux reconcile source git platform-config -n flux-system
  280. flux reconcile kustomization cluster-root -n flux-system
  281. </code></pre>
  282. <h2>12) Index of child Kustomizations</h2>
  283. <pre><code class="language-yaml"># gitops/clusters/microk8s-prod/kustomizations/kustomization.yaml
  284. apiVersion: kustomize.config.k8s.io/v1beta1
  285. kind: Kustomization
  286. resources:
  287. - apps.yaml
  288. - infra-core.yaml
  289. - infra-crds.yaml
  290. - infra-policies.yaml
  291. </code></pre>
  292. <p>Each of the above files is a <strong>Flux Kustomization CR</strong> that points at a repo sub‑path. Example for <strong>infra‑policies</strong>:</p>
  293. <pre><code class="language-yaml"># gitops/clusters/microk8s-prod/kustomizations/infra-policies.yaml
  294. apiVersion: kustomize.toolkit.fluxcd.io/v1
  295. kind: Kustomization
  296. metadata:
  297. name: infra-policies
  298. namespace: flux-system
  299. spec:
  300. interval: 10m
  301. prune: true
  302. wait: true
  303. path: ./gitops/infra-policies
  304. sourceRef:
  305. kind: GitRepository
  306. name: platform-config
  307. namespace: flux-system
  308. dependsOn:
  309. - name: infra-core # if your policies depend on core infra existing first
  310. </code></pre>
  311. <blockquote>
  312. <p>If a child isn’t showing up in <code>kubectl -n flux-system get kustomizations</code>, either the <strong>root CR isn’t applied</strong> yet or the <strong>index file</strong> above doesn’t list it.</p>
  313. </blockquote>

  315. <h1>Part 3 — Admission guardrails (ValidatingAdmissionPolicy)</h1>
  316. <p>We use a ValidatingAdmissionPolicy (VAP) to ensure the <strong>read‑only</strong> capacitor service account cannot perform write‑like or attach/exec operations, even if RBAC appears permissive.</p>
  317. <blockquote>
  318. <p><strong>Prereq:</strong> Your API server must expose <code>ValidatingAdmissionPolicy</code> (K8s ≥1.30). Check:</p>
  319. <pre><code class="language-bash">kubectl api-resources | grep -i ValidatingAdmissionPolicy
  320. </code></pre>
  321. </blockquote>
  322. <h2>13) Policy and Binding (scoped to write‑like ops)</h2>
  323. <pre><code class="language-yaml"># gitops/infra-policies/deny-capacitor-ro-writes.yaml
  324. apiVersion: admissionregistration.k8s.io/v1
  325. kind: ValidatingAdmissionPolicy
  326. metadata:
  327. name: deny-capacitor-ro-writes
  328. spec:
  329. failurePolicy: Fail
  330. matchConstraints:
  331. operations: [&quot;CREATE&quot;,&quot;UPDATE&quot;,&quot;DELETE&quot;,&quot;CONNECT&quot;]
  332. resourceRules:
  333. - apiGroups: [&quot;&quot;, &quot;apps&quot;, &quot;batch&quot;]
  334. apiVersions: [&quot;*&quot;]
  335. resources:
  336. - pods
  337. - pods/exec
  338. - pods/ephemeralcontainers
  339. - pods/attach
  340. - deployments
  341. - replicasets
  342. - statefulsets
  343. - daemonsets
  344. - jobs
  345. - cronjobs
  346. validations:
  347. - expression: request.userInfo.username != &quot;system:serviceaccount:flux-system:capacitor-next-ro&quot;
  348. message: &quot;capacitor-next-ro is view-only; write-like operations are blocked by policy.&quot;
  349. </code></pre>
  350. <pre><code class="language-yaml"># gitops/infra-policies/deny-capacitor-ro-writes-binding.yaml
  351. apiVersion: admissionregistration.k8s.io/v1
  352. kind: ValidatingAdmissionPolicyBinding
  353. metadata:
  354. name: deny-capacitor-ro-writes-binding
  355. spec:
  356. policyName: deny-capacitor-ro-writes
  357. validationActions: [Deny]
  358. # Optional namespace scoping:
  359. # matchResources:
  360. # namespaceSelector:
  361. # matchLabels:
  362. # kubernetes.io/metadata.name: flux-system
  363. </code></pre>
  364. <p>Apply (via Flux or directly for a first test):</p>
  365. <pre><code class="language-bash">kubectl apply -f gitops/infra-policies/deny-capacitor-ro-writes.yaml
  366. kubectl apply -f gitops/infra-policies/deny-capacitor-ro-writes-binding.yaml
  367. </code></pre>
  368. <p>Verify:</p>
  369. <pre><code class="language-bash">kubectl get validatingadmissionpolicies
  370. kubectl get validatingadmissionpolicybindings
  371. </code></pre>
  372. <h2>14) Test the policy with impersonation</h2>
  373. <pre><code class="language-bash">POD=$(kubectl -n flux-system get pod -o name | head -n1)
  374. ​
  375. # should be DENIED by the policy
  376. kubectl -n flux-system delete $POD \
  377. --as=system:serviceaccount:flux-system:capacitor-next-ro \
  378. --as-group=system:serviceaccounts \
  379. --as-group=system:serviceaccounts:flux-system \
  380. --as-group=system:authenticated
  381. </code></pre>
  382. <blockquote>
  383. <p><code>kubectl auth can-i</code> may still say <strong>yes</strong> (RBAC) — <em>admission</em> is what blocks the actual call.</p>
  384. </blockquote>

  386. <h1>Part 4 — Capacitor service accounts &amp; test deployments</h1>
  387. <p>We keep two identities in <code>flux-system</code>:</p>
  388. <ul>
  389. <li><strong><code>capacitor-next</code></strong> – admin/service identity (broad write access). Start with <code>cluster-admin</code> for simplicity; scope down later.</li>
  390. <li><strong><code>capacitor-next-ro</code></strong> – read‑only identity. Gets <code>view</code> cluster‑role; admission policy above prevents write/exec even if something sneaks through.</li>
  391. </ul>
  392. <h2>15) RBAC</h2>
  393. <pre><code class="language-yaml"># gitops/infra-core/capacitor-rbac.yaml
  394. apiVersion: v1
  395. kind: ServiceAccount
  396. metadata:
  397. name: capacitor-next
  398. namespace: flux-system
  399. ---
  400. apiVersion: v1
  401. kind: ServiceAccount
  402. metadata:
  403. name: capacitor-next-ro
  404. namespace: flux-system
  405. ---
  406. # Admin: broad access (start with cluster-admin; refine later)
  407. apiVersion: rbac.authorization.k8s.io/v1
  408. kind: ClusterRoleBinding
  409. metadata:
  410. name: capacitor-next-admin
  411. roleRef:
  412. apiGroup: rbac.authorization.k8s.io
  413. kind: ClusterRole
  414. name: cluster-admin
  415. subjects:
  416. - kind: ServiceAccount
  417. name: capacitor-next
  418. namespace: flux-system
  419. ---
  420. # Read-only: standard view across cluster
  421. apiVersion: rbac.authorization.k8s.io/v1
  422. kind: ClusterRoleBinding
  423. metadata:
  424. name: capacitor-next-ro-view
  425. roleRef:
  426. apiGroup: rbac.authorization.k8s.io
  427. kind: ClusterRole
  428. name: view
  429. subjects:
  430. - kind: ServiceAccount
  431. name: capacitor-next-ro
  432. namespace: flux-system
  433. </code></pre>
  434. <blockquote>
  435. <p>To scope admin more tightly, swap <code>cluster-admin</code> for a custom <code>ClusterRole</code> granting only what the workload needs (configmaps/secrets in <code>flux-system</code>, etc.).</p>

  489. <h1>Troubleshooting</h1>
  490. <ul>
  491. <li><p><strong>SOPS error <code>cannot unmarshal !!seq into string</code></strong>
  492. In <code>.sops.yaml</code>, make <code>age:</code> a <strong>string</strong>:</p>
  493. <pre><code class="language-yaml">age: &#39;age1...&#39;
  494. </code></pre>
  495. <p>not a YAML list.</p>
  496. </li>
  497. <li><p><strong>Runner TLS verification fails</strong>
  498. Ensure your cert contains <code>gitea.core.home.arpa</code> SAN and the runner trusts the CA:</p>
  499. <ul>
  500. <li>Create a cert‑manager <code>Certificate</code> with the right DNS names.</li>
  501. <li>Mount the CA into the runner (<code>extraVolumes</code>/<code>extraVolumeMounts</code>).</li>
  502. <li>Remove <code>insecure: true</code> from runner config once CA is trusted.</li>
  503. </ul>
  504. </li>
  505. <li><p><strong>Ingress SSH (32222) not reachable</strong>
  506. Confirm <code>ingress-nginx-tcp</code> ConfigMap has <code>32222: &quot;git-local/gitea-ssh:22&quot;</code> and the controller has <code>--tcp-services-configmap</code> arg.</p>
  507. </li>
  508. <li><p><strong>VAP resources show “No resources found”</strong>
  509. Your API server doesn’t expose VAP; either upgrade Kubernetes/MicroK8s or fall back to stricter RBAC with admission‑webhook alternatives.</p>
  510. </li>
  511. <li><p><strong><code>infra-policies</code> missing in Flux</strong>
  512. Ensure the <strong>root</strong> <code>cluster-root.yaml</code> was applied once, and that <code>gitops/clusters/microk8s-prod/kustomizations/kustomization.yaml</code> lists <code>infra-policies.yaml</code>.</p>
  513. </li>
  514. </ul>
