        <h1>1) Image build (multi-stage)</h1>
<p>Create <code>docker/capacitor-next/Dockerfile</code>:</p>
<pre><code class="language-Dockerfile"># docker/capacitor-next/Dockerfile
# Build a small image that embeds the Capacitor Next binary (next-v0.5.0)

FROM debian:bookworm-slim AS builder
ARG CAP_VERSION=next-v0.5.0
RUN apt-get update &amp;&amp; apt-get install -y --no-install-recommends \
    ca-certificates wget curl bash &amp;&amp; rm -rf /var/lib/apt/lists/*
WORKDIR /work
# The official installer drops a binary named &quot;next&quot; into the CWD
RUN curl -fsSL https://gimlet.io/install-capacitor | bash -s -- ${CAP_VERSION}

# ---
FROM gcr.io/distroless/base-debian12
COPY --from=builder /usr/local/bin/next /usr/local/bin/next
USER 65532:65532
EXPOSE 3333
ENTRYPOINT [&quot;/usr/local/bin/next&quot;]
CMD [&quot;--port&quot;,&quot;3333&quot;,&quot;--auth&quot;,&quot;static&quot;]
</code></pre>
<p>Optional <code>.dockerignore</code> (same folder):</p>
<pre><code class="language-gitignore"># docker/capacitor-next/.dockerignore
*
!Dockerfile
</code></pre>
<p><strong>Build &amp; push</strong> (from repo root):</p>
<pre><code class="language-bash"># If you use buildx already:
docker buildx build --platform linux/amd64 \
  -f docker/capacitor-next/Dockerfile \
  -t reg.microk8s.core.home.arpa:32000/capacitor-next:next-v0.5.0 \
  --build-arg CAP_VERSION=next-v0.5.0 \
  .

docker push reg.microk8s.core.home.arpa:32000/capacitor-next:next-v0.5.0
</code></pre>
<blockquote>
<p>If your registry is <strong>HTTP</strong> (MicroK8s default), ensure your build host and nodes trust it as an <em>insecure registry</em> (containerd <code>hosts.toml</code> / Docker daemon <code>insecure-registries</code>).</p>
</blockquote>

<h2>2a) ServiceAccount &amp; RBAC</h2>
<p>By default we bind <strong>read-only</strong> (ClusterRole <code>view</code>). Change to <code>admin</code> if you want full control.</p>
<pre><code class="language-yaml"># gitops/apps/capacitor-next/sa-rbac.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: capacitor-next
  namespace: flux-system
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: capacitor-next-view
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: view
subjects:
  - kind: ServiceAccount
    name: capacitor-next
    namespace: flux-system
</code></pre>
<blockquote>
<p><strong>Why RBAC?</strong> In <code>auth=static</code> mode, Capacitor Next serves the UI and proxies requests using the pod’s ServiceAccount. Binding to <code>view</code> keeps it safe in a homelab; bump to <code>edit</code>/<code>admin</code> if you want write actions.</p>
</blockquote>

<h2>Notes &amp; toggles</h2>
<ul>
<li><strong>Role scope</strong>: switch the binding from <code>view</code> → <code>admin</code> by changing the <code>ClusterRole</code> in <code>sa-rbac.yaml</code> if you want full control from the UI.</li>
<li><strong>Port</strong>: change the container args and Service/Ingress ports if you prefer <code>9000</code>.</li>
<li><strong>Registry</strong>: if your registry is TLS-enabled with a self-signed cert, add a Node trust step (containerd <code>hosts.toml</code> with the CA) or push to the built-in MicroK8s registry (<code>localhost:32000</code>).</li>
<li><strong>Zero-auth warning</strong>: this endpoint has no login—keep it on your LAN-only homelab.</li>
</ul>

<h1>1) Create the Secret (SOPS-friendly)</h1>
<p><code>gitops/apps/capacitor-next/secret-auth.yaml</code></p>
<pre><code class="language-yaml">apiVersion: v1
kind: Secret
metadata:
  name: capacitor-next-auth
  namespace: flux-system
type: Opaque
stringData:
  AUTH: static
  # One user per line: email:bcrypt-hash
  USERS: |
    admin@example.com:$2y$12$REPLACE.ME.REPLACE.ME.REPLACE.ME
    # viewer1@example.com:$2y$12$REPLACE.ME.REPLACE.ME.REPLACE.ME
</code></pre>
<p>Generate a bcrypt hash (example command you shared):</p>
<pre><code class="language-bash">htpasswd -bnBC 12 x &#39;mypassword&#39; | cut -d: -f2
</code></pre>
<p>Paste the hash(s) into the <code>USERS:</code> block (one <strong>email:hash</strong> per line).
Then encrypt in-place with SOPS (age):</p>
<pre><code class="language-bash">sops -e -i gitops/apps/capacitor-next/secret-auth.yaml
</code></pre>
<blockquote>
<p>YAML tip: using a <strong>block scalar</strong> (<code>|</code>) avoids any quoting issues with <code>:</code> and <code>$</code> in bcrypt.</p>

<h1>3) How to model “admin” vs “view-only” in static mode</h1>
<p>In <code>auth=static</code>, <strong>every logged-in user ultimately acts with the Deployment’s ServiceAccount RBAC</strong>, since there’s no per-user impersonation. So:</p>
<ul>
<li><p>If you want different privileges, run <strong>two instances</strong>:</p>
<ul>
<li><strong>Admin UI</strong>: SA bound to <code>admin</code> (or a narrow set you choose), Secret has your admin(s).</li>
<li><strong>Viewer UI</strong>: SA bound to <code>view</code>, Secret has viewer accounts.</li>
<li>Give each a distinct host (e.g., <code>cap-next.core.home.arpa</code> and <code>cap-next-view.core.home.arpa</code>), or keep the viewer instance internal only.</li>
</ul>
</li>
</ul>
<p>This keeps RBAC enforcement server-side and avoids relying on just “hiding buttons” in the UI.</p>
<p>If later you want <strong>true per-user RBAC</strong>, switch that instance to the OIDC/impersonation setup we sketched before.</p>

<h1>4) Operational tips</h1>
<ul>
<li><strong>Rotation</strong>: generate a new bcrypt and update the SOPS secret → commit → <code>rollout restart</code>.</li>
