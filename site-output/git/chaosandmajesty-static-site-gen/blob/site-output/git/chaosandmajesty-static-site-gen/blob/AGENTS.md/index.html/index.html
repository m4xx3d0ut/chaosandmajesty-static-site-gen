  14. <h1>Repository Guidelines</h1>
  15. <h2>Project Structure &amp; Module Organization</h2>
  16. <p>The static generator lives in <code>static-sitegen/</code> (ES modules in <code>lib/</code>, CLI at <code>bin/sitegen.js</code>, EJS templates under <code>templates/</code>). YAML configs such as <code>smoke-test.yaml</code> describe the site and render into <code>site-output/</code>. Designers&#39; assets belong in <code>cm-source/</code>; run <code>prepare-cm-files.sh</code> to hydrate <code>static-sitegen/assets/</code> with JS, CSS, images, and partials. Helper scripts (<code>build-site.sh</code>, <code>prepare-cm-files.sh</code>) pair with Docker artifacts (<code>Dockerfile</code>, <code>docker-compose.yml</code>, <code>Makefile</code>) for local or container builds.</p>
  17. <h2>Build, Test, and Development Commands</h2>
  18. <ul>
  19. <li><code>./build-site.sh</code>: invokes <code>static-sitegen/bin/sitegen.js</code> with <code>smoke-test.yaml</code> and validates <code>site-output/</code>.</li>
  20. <li><code>make build-local</code> mirrors the script; <code>make build</code>, <code>make up</code>, <code>make down</code>, <code>make logs</code> cover Docker workflows.</li>
  21. <li><code>make serve-local</code> serves <code>site-output/</code> on <code>http://localhost:8080</code>.</li>
  22. <li><code>make test</code> runs the Node 18 smoke container and calls <code>npm test</code>; expand it as coverage grows.</li>
  23. </ul>
  24. <h2>Coding Style &amp; Naming Conventions</h2>
  25. <p>Code is modern ES module JavaScript with 2-space indentation, single quotes, and small focused helpers in <code>lib/</code>. Keep CLI argument parsing in <code>bin/sitegen.js</code>; templates follow the <code>cm-*.ejs</code> pattern. Assets, configs, and generated files should stay kebab-case to match copy logic. No linter is enforced, so mirror the existing style and double-check imports remain sorted by dependency weight.</p>
  26. <h2>Testing Guidelines</h2>
  27. <p><code>npm test</code> is a stub today; replace it with unit or smoke checks when you add modules. Always rerun <code>./build-site.sh</code> after code, template, or YAML edits and inspect <code>site-output/</code> for regressions. Future tests can live beside the modules (e.g., <code>generateSite.spec.js</code>) with fixture YAML under <code>tests/fixtures/</code>. When templates change, load <code>make serve-local</code> and confirm terminal interactions still render as expected.</p>
  28. <h2>Commit &amp; Pull Request Guidelines</h2>
  29. <p>Use the <code>&lt;scope&gt;: &lt;present-tense summary&gt;</code> convention from history (<code>cicd: configure buildkit for insecure reg.</code>). Keep commits focused, include generated assets only when reviewers need them, and call out new configuration knobs. Pull requests should describe the scenario, link issues, and paste the latest <code>./build-site.sh</code> or <code>make test</code> output. Add screenshots or terminal recordings whenever UI or console behavior shifts.</p>
  30. <h2>Asset &amp; Configuration Notes</h2>
  31. <p>Never store secrets in YAML. Keep reusable defaults in <code>cm-source/</code> and introduce new config files for project-specific variants. For 3D logo support ensure <code>cmLogo.js</code> and SVG assets stay in sync, updating <code>prepare-cm-files.sh</code> if more paths must be copied. Favor additive configuration keys so existing builds remain compatible.</p>
