  1. # Repository Guidelines
  2. ​
  3. ## Project Structure & Module Organization
  4. - `gitops/` contains Kustomize bundles for apps, shared infra, clusters, and guardrails; adjust overlays here before exporting live state.
  5. - `helm/` maintains chart values (`helm-gitea/`) and runner packaging (`helm-actions/`); keep overrides in sync with `gitops/`.
  6. - `docker/` holds CI build contexts (e.g., `capacitor-next/`); align images with the Helm values that reference them.
  7. - `tools/` offers automation (`./tools/export-all.sh`, `./tools/export-helm.sh`) and `bootstrap/` stores sensitive keys—keep decrypted copies local and out of Git.
  8. ​
  9. ## Build, Test, and Development Commands
  10. - `./tools/export-all.sh` snapshots Kubernetes objects into the repo; run after cluster updates to refresh manifests.
  11. - `./tools/export-k8s.sh namespace/name` exports a targeted resource tree when iterating on a single workload.
  12. - `helm lint helm/helm-gitea` and `helm template helm/helm-gitea` validate chart edits before pushing.
  13. - `kustomize build gitops/apps` (or a subdirectory) verifies overlays render cleanly; pipe to `kubectl apply --dry-run=server -f -` for schema checks.
  14. ​
  15. ## Coding Style & Naming Conventions
  16. - Prefer YAML with two-space indentation and sorted keys; keep filenames kustomize-friendly (`kustomization.yaml`, `<component>.yaml`).
  17. - Shell scripts stay `bash`-compatible and use lowercase-with-dashes names.
  18. - Enforce SOPS encryption on secrets via `sops -e file.yaml`; commit only the encrypted result.
  19. ​
  20. ## Testing Guidelines
  21. - Validate Kustomize bundles via `kustomize build` + `kubectl apply --dry-run=server` per environment (`gitops/clusters/<cluster>`).
  22. - For Helm releases, run `helm diff upgrade --install` (via plugin) against the target namespace to catch drift before applying.
  23. - Keep encryption intact by running `sops -d file.yaml >/dev/null` as a quick decryption check when reviewing secrets.
  24. ​
  25. ## Commit & Pull Request Guidelines
  26. - Follow the conventional-ish prefixes seen in history (`feat(component):`, `fix:`, `wip:`) and keep subject lines under 80 characters.
  27. - Group related manifest, chart, and script changes in a single commit; include before/after context or exported command output in the body when relevant.
  28. - PRs should cite the driving issue, describe rollout steps (e.g., scripts run, helm commands), and attach validation evidence (lint output, dry-run snippets, screenshots for UIs).
  29. ​
  30. ## Security & Configuration Tips
  31. - Store age keys only in `bootstrap/`; never embed plaintext credentials in manifests.
  32. - When adding new exports, ensure `tools/gitea-enc-secrets-sops.sh` covers them so nightlies do not fail due to unencrypted secrets.
  33. - Keep ingress hostnames, ports, and PVC names consistent with `helm-gitea-test/` templates to avoid breaking SSH and TLS automation.
