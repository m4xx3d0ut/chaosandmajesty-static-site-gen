  26. <h2>TL;DR</h2>
  27. <ul>
  28. <li>The working branch <code>feat-doom-audio</code> now boots DOOM with WebAudio-driven sound effects, closing the silence we lived with in the first wasm drops.</li>
  29. <li>We expose <code>js_audio_init</code>, <code>js_audio_play_sfx</code>, and <code>js_audio_shutdown</code> so the wasm module treats our browser runtime like a soundcard.</li>
  30. <li>8-bit PCM lumps are cached, resampled, and mixed per-channel before they hit an <code>AudioBufferSourceNode</code>, keeping overlapping shots from crackling.</li>
  31. <li>We gate autoplay rules by resuming the <code>AudioContext</code> on key, click, and pointer-lock events, while scheduling buffers against <code>currentTime</code> to stay in sync.</li>
  32. </ul>
  33. <h2>Bringing the old soundcard back online</h2>
  34. <p>The first integration of DOOM (commit <code>866c611</code>, what you see on the site as of today) got DOOM sitting pretty in the terminal screen, but the build stayed mute. The past week on <code>feat-doom-audio</code> moved the shareware soundboard into the browser. The opening salvo:</p>
  35. <ul>
  36. <li><code>b52c11e</code> introduced a JavaScript bridge that let the wasm runtime push raw samples into our memory view.</li>
  37. <li><code>6d7d067</code> rewired playback, converting 8-bit lumps to floating point and scheduling them against a shared gain node so multiple SFX can play cleanly.</li>
  38. <li><code>23971cd</code> tightened the pipeline with buffer caching, pitch-aware resampling, and guard rails for browsers that suspend audio contexts.</li>
  39. </ul>
  40. <p>Each pass kept the terminal commands intact—<code>play doom</code> still deploys the overlay, <code>exit doom</code> tears it down—while giving us room to iterate on audio without breaking the UI shell.</p>
  41. <h2>WebAssembly wants a soundcard</h2>
  42. <p><code>instantiateDoom()</code> now provisions a 96 MiB <code>WebAssembly.Memory</code> block and wires a custom import object:</p>
  43. <pre><code class="language-js">js: {
  44. js_audio_init(sampleRate) { initDoomAudio(sampleRate); },
  45. js_audio_play_sfx(ptr, length, sampleRate, left, right, pitch) {
  46. playDoomSfx(ptr, length, sampleRate, left, right, pitch);
  47. },
  48. js_audio_shutdown() { shutdownDoomAudio(); }
  49. }
  50. </code></pre>
  51. <p>The game still thinks it is talking to a DOS-era mixer. We translate that conversation into WebAudio primitives. <code>initDoomAudio</code> spins up an <code>AudioContext</code>, seeds a master gain node, records the wasm-provided sample rate (11025 Hz by default), and marks the engine live. <code>shutdownDoomAudio</code> flips the switch, clears the cache, and closes the context so re-entry stays clean.</p>
  52. <h2>Resampling the shareware lumps</h2>
  53. <p>Every sound effect the shareware WAD ships (door slides, plasma bolts, the cyberdemon&#39;s roar) arrives as unsigned 8-bit PCM. <code>playDoomSfx</code> pulls the bytes directly from the wasm memory buffer, normalises them to the <code>[-1, 1]</code> range, and caches the result in <code>doomAudioState.bufferCache</code>. The cache key ties the pointer and length, so repeated shots reuse decoded data instead of hammering the GC.</p>
  54. <p>Pitch adjustments from the engine arrive as a single byte. We convert that to an exponential ratio (<code>Math.pow(2, (pitch - 128) / 64)</code>) and scale the effective playback rate before shoving frames into a stereo buffer. Volume is handled per-channel (left/right gain derived from the game&#39;s 0-127 range) so directional audio survives intact. By feeding the finished <code>AudioBuffer</code> through a shared gain node we can add future master controls without rewriting the wasm side.</p>
  55. <h2>Keeping the browser happy</h2>
  56. <p>Modern browsers refuse to autoplay audio until a user interacts. <code>resumeDoomAudio()</code> tackles that rule by listening for keydown, keyup, click, focus, and pointer-lock events on the DOOM canvas. The first interaction calls <code>context.resume()</code> and subsequent inputs keep the context warm. We also schedule each <code>AudioBufferSource</code> against a <code>nextTime</code> cursor tracked in <code>doomAudioState</code>, ensuring overlapping shotgun blasts queue seamlessly even when a frame drops.</p>
  57. <p>Mouse capture still works the way the earlier branch taught us: clicking the canvas requests pointer lock, Esc releases it, and the overlay&#39;s status area tells you where you stand. The only new behaviour is that every exit path calls <code>shutdownDoomAudio()</code> so leaving the game stops the hum instantly.</p>
  58. <h2>Memory and performance guard rails</h2>
  59. <p>The wasm module now receives a 1,536-page (≈96 MiB) memory block. Audio lumps and texture tables chew through headroom fast—a smaller heap led to hard faults once we added streaming samples. The buffer cache tracks the active memory buffer and flushes itself if the wasm heap relocates, defending against stale <code>ArrayBuffer</code> references. Combined with the shared <code>masterGain</code> node and sequential scheduling, we minimise garbage collection churn and keep the terminal responsive while the game screams in the background.</p>
  60. <h2>What&#39;s next</h2>
  61. <p>Part II will chase the remaining gaps:</p>
  62. <ol>
  63. <li>Stream the music subsystem (the shareware IWAD ships MUS data that needs a MIDI-to-WAV bridge or an FM synth shim).</li>
  64. </ol>
  65. <p>For now, we can boot the branch, run <code>play doom</code>, and enjoy the return of E1M1&#39;s soundscape—silence is officially dead.</p>
  66. <p>But head our warning: &quot;thar be dragons&quot;. I&#39;m still thinking through the approach and testing stability, this is my first foray into WebAudio and WebAssembly. I&#39;m sure there are better ways to do this, but it&#39;s a start. And it works... for now. If/when I&#39;m happy with the state of audio, I&#39;ll push the project to a public repo and put a little more time into it, there are a few other features I&#39;d like to see before calling it done!</p>
