<pre><code>nltest /dsgetdc:corp.local
nltest /dclist:corp.local
net config workstation
net accounts /domain
Get-ADDomain | Select-Object Name,DomainMode,ForestMode
</code></pre>
<ul>
<li>Document domain functional level, FSMO roles, and trust relationships.</li>
<li>Capture DNS zone transfers (<code>dnstool.py</code>) and GPO links.</li>
</ul>
<h3>LDAP &amp; SMB Recon</h3>
<pre><code>ldapsearch -x -H ldap://dc01.corp.local -D &#39;corp\ldapsvc&#39; -w &#39;Passw0rd!&#39; -b &#39;DC=corp,DC=local&#39; &#39;(objectClass=user)&#39; sAMAccountName userAccountControl
ldapsearch -x -H ldap://dc01.corp.local -b &#39;DC=corp,DC=local&#39; &#39;(servicePrincipalName=*)&#39; sAMAccountName servicePrincipalName

smbmap -H fileserver.corp.local -u backupuser -p &#39;Passw0rd!&#39;
net view \\fileserver /all
</code></pre>
<ul>
<li>Track accounts with <code>adminCount=1</code>, disabled status, or interesting descriptions.</li>
<li>Enumerate shares, permissions, and accessible directories.</li>
</ul>

<pre><code># Collectors
Invoke-BloodHound -CollectionMethod All,GPOLocalGroup -Domain corp.local -ZipFile .\loot\bh.zip
bloodhound-python -c All -u analyst -p &#39;Passw0rd!&#39; -d corp.local -gc dc01.corp.local
</code></pre>
<ul>
<li>Import into BloodHound, run queries (“Shortest path to Domain Admins”, “Find all Kerberoastable Accounts”).</li>
<li>Screenshot key graphs for the report and log collection timestamps.</li>
</ul>
<h3>Credential Hygiene Checks</h3>
<ul>
<li><code>Get-ADUser -Filter {PasswordNeverExpires -eq $true}</code>.</li>
<li><code>Get-ADFineGrainedPasswordPolicy</code> to see if weak policies exist.</li>
<li>Identify unconstrained/ constrained delegation: <code>Get-ADComputer -Filter {TrustedForDelegation -eq $true}</code>.</li>
<li>Note service accounts with weak SPNs and tier-0 group members.</li>
</ul>
<h3>Reporting Data Points</h3>
<ul>
<li>Build a table of high-risk findings: missing SMB signing, outdated functional level, excessive Domain Admin membership.</li>
<li>Provide remediation guidance: enforce LDAP signing, enable Protected Users group, rotate service account passwords to gMSA.</li>
</ul>
<p>Comprehensive AD enumeration now will save you hours when you start roasting, relaying, and moving laterally in Modules 22–24.</p>

<h4>21.1 Active Directory - Introduction</h4>
<ul>
<li>Introduction to Active Directory.</li>
<li>Define our enumeration goals.</li>
</ul>
<p>AD contains critival info about the env, reffered to as objects.</p>
<ul>
<li>User info.</li>
<li>Groups.</li>
<li>Computers.</li>
</ul>
<p>Configuring/maintaining an AD instance can be daunting, the wealth of info creates a large attack surface.</p>
<p>The first step in AD config is creating a domain name, <code>corp.com</code> for instance, which is often the name of the org itself.  Within the domain, admins can add various objects associated with the org.</p>
<p><em>An AD environment has a critical dependency on the Domain Name System (DNS) service. As such, a typical domain controller will also host a DNS server that is authoritative for a given domain.</em></p>
<p>To ease object and system management, admins organize the objects into <a href="https://en.wikipedia.org/wiki/Organizational_unit_(computing)">Organizational Units (OUs)</a>.</p>
<p>OUs are like file system folders, they are containers used to store objects within a domain.  Computer objects represent actual servers and workstations that are domain-joined and user objects represent accounts that can be used to log into domain-joined computers.  AD objects contain attributes which will vary depending on the type of object.  A user object may include attributes such as first name, last name, username, phone number, etc.</p>
<p>AD relies on several components and communication services.  When a user logs in, a request is sent to a Domain Controller (DC), that checks if the user is allowed to log in to the domain.  One or more DCs act as the core of the domain and store all OUs, objects, and their attributes.  Since the DC is a central component, we pay close attention to it while we enumerate AD.</p>
<p>Objects can be assigned to AD groups so that admins can manage them as a single unit.  Users in a group can be given access to a file server share or granted admin access to various clients in the domain.  Attackers often target high-priv groups.</p>
<p>Domain Admin members are among the highest priv objects in the domain.  If an attacker compromises a member of this group, often reffered to as &quot;domain administrators&quot;, they essentially gain full control over the domain.</p>
<p>This vector could extend beyond a single domain since an AD instance can host more than one domain in a domain tree or multiple domain trees in a domain forest.  There are Domain Admin groups for each domain in the forest, members of the Enterprise Admins group are granted full control over all the domains in the forest and have Admin privs on all DCs, making them a high value target.</p>
<p>We will leverage these and other concepts in this moduleas we focus on the important aspects of AD enumeration.  This important discipline can improve our success during the attack phase.  We will leverage a variety of tools to manually enumerate AD, most rely on the <a href="https://en.wikipedia.org/wiki/Lightweight_Directory_Access_Protocol">Lightweight Directory Access Protocol (LDAP)</a>.  Once we&#39;ve introduced foundational techniques, we&#39;ll leverage automation to perform enumeration at scale.</p>
<h5>Enumeration - Defining our Goals</h5>
<p>In this scenario we will enumerate <code>corp.com</code> domain.  We&#39;ve obtained user credentials to a domain user through a successful phishing attack.  Alternatively, the org may have provided us with user creds so that we can perform a pentest base on an assumed breach. This would speed up the process and give the org insight into how easily attackers can move within their enc once they have gained initial access.</p>
<p>the user we have is <code>stephanie</code> who has RDP perms on a Win 11 machine that is part of the domain.  the user is not a local admin on the machine, which we take into account as we proceed.</p>
<p>During a real-world, the org may also define the scope and goals of the pentest.  In our case, we are restricted to the <code>corp.com</code> domain with the PWK labs.  Our goal will be to enumerate the full domain, including ways to achieve the highest priv possible, domain admin in this case.</p>
<p>In this module, we will perform the enumeration from a client machine with the low priv <code>stephanie</code> user.  Once we start performing attacks and we are able to gain access to additional users/systems, we may have to repeat parts of the enumeration process from the new postiion.  Perspective shift, or pivot, is critical during the enum process considering the complexity of permissions across the domain.  Each pivot may give us an opportunity to advance our attack.</p>
<p>For example, if we gain another low priv user account that has the seems to have the same access as <code>stephanie</code> we shouldn&#39;t dismiss it.  Instead, we should repeat enumeration with the new account since the admins often grant individual users increased perms based on their role in the org.  This &quot;rinse and repeat&quot; process is key to success in enumeration and works extremely well, particularly in large orgs.</p>

<h5>Enumerating Active Directory using PowerShell and .NET Classes</h5>
<p>We have several tools for AD enum.  PowerShell cmdlets like <a href="https://learn.microsoft.com/en-us/powershell/module/activedirectory/get-aduser?view=windowsserver2022-ps">Get-ADUser</a> work well but are only installed by default on domain controller as part of the <a href="https://learn.microsoft.com/en-us/troubleshoot/windows-server/system-management-components/remote-server-administration-tools">Remote Server Administration Tools (RSAT)</a>.  RSAT is rarely present on domain clients and we need admin privs to install them.  We can, in principal, impor the DLL required for enum ourselves, but we will look into other options.</p>
<p>We&#39;ll develop a tool that requires only basic privs and is flexible enough to use in real-world.  We will mimic the queries AD uses under regular operation.  This will help us understand the basic concepts used in pre-built tools we&#39;ll use later.</p>
<p>We&#39;ll use PowerShell and .NET classes to create a script that enums the domain.  Although PS development can be complex, we will take it one step at a time.</p>
<p>To enum AD, we first need to understand how to comm with the service.  Before we start writing our script, we will discuss some theory.</p>
<p>AD enum relies on LDAP.  When a domain machine searches for an object, like a printer, or when we query user/group objects, LDAP is used as the comm channel for the query.  In other words, LDAP is the proto used to comm with AD.</p>
<p><em>LDAP is not exclusive to AD. Other directory services use it as well.</em></p>
<p>LDAP comm with AD is not always straight-forward, but we can leverage <a href="https://learn.microsoft.com/en-us/windows/win32/adsi/active-directory-service-interfaces-adsi">Active Directory Services Interface (ADSI)</a> as an LDAP provider.</p>
<p>According to MS docs, we need a specific LDAP ADsPath to comm with AD service.  LDAP path prototype looks like:</p>
<pre><code>LDAP://HostName[:PortNumber][/DistinguishedName]
</code></pre>
<ul>
<li>We need 3 params for the full LDAP path.</li>
<li>HostName.</li>
<li>PortNumber.</li>
<li>DistinguishedName.</li>
</ul>
<p>Hostname can be a computer name, IP address, or a domain name.  In our case, we are working with the <code>corp.com</code> domain, so we can simply add that to our LDAP path and likely obtain info.  Note that a domain may have multiple DCs, so setting the domain name could resolve to the IP address of any DC in the domain.</p>
<p>While this will return valid info, it may not be the optimal approach.  In fact, to make out enum as accurate as possible, we should look for the DC that holds the most current info.  This is know as the <a href="https://learn.microsoft.com/en-GB/troubleshoot/windows-server/identity/fsmo-roles">Primary Domain Controller (PDC)</a>.  There can only be one PDC in a domain.  To find the PDC, we need to find the DC holding the <code>PdcRoleOwner</code> property.  We&#39;ll use PowerShell and a specific .NET class to find this.</p>
<p>The PortNumber for LDAP conn is options per MS docs.  In this case, we will not add the port number since it will auto choose the port based on if we are using SSL or not.  It is worth noting that if we come across a domain using non-default ports, we may need to manually add this to the script.</p>
<p>The <a href="https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ldap/distinguished-names">DistinguishedName (DN)</a> is part of the LDAP path.  A DN is a name that uniquely identifies an object in AD, including the domain itself.  If we aren&#39;t familiar with LDAP, this may be confusing so let&#39;s go into greater detail.</p>
<p>For LDAP to function, objects in AD must be formatted according to a specific naming standard.  To show an example of a DN, we can use our <code>stephanie</code> domain user.  We know that <code>stephanie</code> is a user object in <code>corp.com</code> domain.  The DN may, though we cannot be sure yet, look like this:</p>
<pre><code>CN=Stephanie,CN=Users,DC=corp,DC=com
</code></pre>
<ul>
<li>CN (Common Name)</li>
<li>Specifies the identifier of an object in the domain.</li>
<li>DC (Domain Component)</li>
<li>In AD terms DC is Domain Controller, but when refereing to a DN, DC means Domain Component.</li>
<li>Represents the top of an LDAP tree, in this case it is the DN of the domain itself.</li>
</ul>
<p>When reading a DN, we start with the DC objects on the right side and move to the left.  In this case, we have 4 components, starting with two components names <code>DC=corp</code>, <code>DC=com</code>.  The Domain Component objects mentioned above are the top of an LDAP tree following the required naming standard.</p>
<p>The next DN field, <code>CN=Users</code> respresents the common name for the container where user object is stored, aka the parent container.</p>
<p>The left most field <code>CN=Stephanie</code> represents the common name for the user object itself, which is lowest in the hierarchy.</p>
<p>In the case of the LDAP path we are interested in the Domain Component object, <code>DC=corp</code> and <code>DC=com</code>.  If we add <code>CN=Users</code> to our LDAP path we would be restricted to searching onjects within the given container.</p>

<h5>Adding Search Functionality to our Script</h5>
<p>Now that our script builds the LDAP path we can build in our search function.</p>
<p>We need two .NET classes located in the <code>System.DiretoryServices</code> namespace.</p>
<ul>
<li><a href="https://learn.microsoft.com/en-us/dotnet/api/system.directoryservices.directoryentry?view=dotnet-plat-ext-6.0">DirectoryEntry</a></li>
<li><a href="https://learn.microsoft.com/en-us/dotnet/api/system.directoryservices.directorysearcher?view=dotnet-plat-ext-6.0">DirectorySearcher</a></li>

<p><code>DirectoryEntry</code> class encapsulates an object in the AD service hierarchy.  In our case we will search from the top of the AD heirarchy by providing the LDAP path to the <code>DirectoyEntry</code> class.</p>
<p><em>One thing to note with DirectoryEntry is that we can pass it credentials to authenticate to the domain. However, since we are already logged in, there is no need to do that here.</em></p>
<p>The <code>DirectorySearcher</code> class queries against AD using LDAP, we must specify the AD service to query in the <a href="https://learn.microsoft.com/en-us/dotnet/api/system.directoryservices.directorysearcher.searchroot?view=dotnet-plat-ext-6.0">SearchRoot</a> prop.  According to MS docs, this prop indicated where search starts in AD hierarchy.  Since the <code>DirectoryEntry</code> class encapsulates the LDAP path pointing to the top of the hierarchy we can pass that as a var to <code>DirectorySearcher</code>.</p>
<p>The <code>DirectorySearcher</code> docs list <code>FindAll()</code> which returns all entries found in AD.</p>
<p>Implement the two classes in our script.</p>

$direntry = New-Object System.DirectoryServices.DirectoryEntry($LDAP)

$dirsearcher = New-Object System.DirectoryServices.DirectorySearcher($direntry)
$dirsearcher.FindAll()
</code></pre>
<ul>
<li>We added the <code>$direntry</code> var.</li>
<li>Encapsulates our LDAP path.</li>
<li><code>$dirsearcher</code> var contains the <code>$direntry</code> var and uses the info as <code>SearchRoot</code> .</li>
<li>Pointing to the top of the hierarchy where <code>DirectorySearcher</code> will run the <code>FindAll()</code> method.</li>
</ul>

<pre><code>function LDAPSearch {

        [string]$LDAPQuery
    )

    return $DirectorySearcher.FindAll()

}

<li>The <code>DirectoryEntry</code> and our <code>$LDAPQuery</code> param is fed into the <code>DirectorySearcher</code></li>
<li>The search is run and output is added into an array.</li>
<li>Displayed in terminal depening on our needs.</li>
</ul>

<h5>Getting an Overview - Permissions and Logged on Users</h5>
<p>Now that we have a clear list of computers, users, and groups in the domain we continue enum focusing on the relationships between as many objects as possible.  These relationships often play a key role during attack and our goal is to build a map of the domain to find attack vectors.</p>
<p>Example, when a user logs in to the domain their creds are cached in mem on the computer they logged in from.</p>
<p>If we can steal those creds we may be able to use them to auth as the domain user and potentially escalate our domain privs.</p>
<p>However during an AD assessment we may not always want to escalate privs right away.</p>
<p>It is more important to establish a good foothold and our goal is to maintain access.  If we are able to compromise other users with the same perms as the user we already have access to, this allows us to maintain our foothold.  Example, if the password is reset for the user we originally obtained access to or sys admin notices suspicious activity and disable the account, we would still have access to the domain via other users we compromised.</p>
<p>When it is time for PrivEsc we don&#39;t immediatly need domain admin because there may be other accounts that have higher privs than regular user even if they aren&#39;t part of Domain Admin group.  Service Accounts, which we will discuss later, are a good example of this.  Although they may not have the highest privs, they may have more perms than regular domain user, such as local admin privs on specific servers.</p>
<p>In addition an orgs most sensitive and important data may be stored in locations that do not require domain admin privs, a DB or file server for instance.  Due to this, domain admin privs should not always be the end goal during an assesment since we may be able to reach the &quot;crown jewels&quot; for an org via other users in the domain.</p>
<p><em>Nevertheless, in our Challenge Labs the goal is to achieve domain administrator privileges.</em></p>
<p>When an attacker improves access through multiple higher-level accounts to reach the goad, it is known as &quot;chained compromise&quot;.</p>
<p>To find possible attack paths we need to learn more about our initial user and see what domain access they have.  We also need to find out where other users are logged in.</p>
<p>PowerView&#39;s <code>Find-LocalAdminAccess</code> command scans the network in an attempt to determine if our current user has admin perms on any computers in the domain.  The command relies on <code>OpenServiceW</code> <a href="https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-openservicew">function</a>, which connects to Service Control Manager (SCM) of the target machines.  The SCM maintains a DB of installed services and drivers on Win computers.  PowerView will attempt to open this DB with the SC_MANAGER_ALL_ACCESS access right, wich requires admin privs, and if successful PowerView will deem that our current user has admin privs on the target.</p>
<p>Run <code>Find-LocalAdminAccess</code> against <code>corp.com</code>.  The command supports params like <code>Computername</code> and <code>Credentials</code> but we will run it without params in this case since we are interested in enum all computers and we are already logged in as <code>stephanie</code>.  Essentially, we are spraying the env to find possible local admin access on computers under our current context.</p>
<p><em>Depending on the size of the environment, it may take a few minutes for Find-LocalAdminAccess to finish.</em></p>

<p>According to NetSessionEnum docs there are five query levels: <code>0,1,2,10,502</code>.</p>
<ul>
<li>Level 0 only returns the name of the computer establishing the session.</li>
<li>Level 1,2 return more info but require admin privs.</li>
<li>Level 10,502 return info such as name of the computer and name of the user establishing the connection.</li>
</ul>
<p>By default PowerView uses query level 10 with NetSessionEnum, which should return this info.</p>
<p>The perms required to enum sessions with <code>NetSessionEnum</code> are defined in the <code>SrvsvcSessionInfo</code> reg key located in the <code>HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\LanmanServer\DefaultSecurity</code> hive.</p>

<h5>Enumeration Through Service Principal Names</h5>
<p>At this point we have obtained a good bit of info and are starting to see how things are connected together within the domain.  To complete our discussion on enum, we will shift our focus to <a href="https://learn.microsoft.com/en-us/azure/active-directory/fundamentals/service-accounts-on-premises">Service Accounts</a>, which can also be members of high priv groups.</p>
<p>Apps must exec inthe context of an OS user.  If a user launches an app, the user account defines the context.  Service launched by the system itself run in the context of a Service Account.</p>
<p>Isolated apps ca use a set of predefined service accounts.</p>
<ul>
<li><a href="https://learn.microsoft.com/en-us/windows/win32/services/localsystem-account">LocalSystem</a></li>
<li><a href="https://learn.microsoft.com/en-us/windows/win32/services/localservice-account">LocalService</a></li>
<li><a href="https://learn.microsoft.com/en-us/windows/win32/services/networkservice-account">NetworkService</a></li>

<p>For more complex apps a domain user account may be used, providing the context while maintaining access to domain resources.</p>
<p>When apps like Exchange, MS SQL, or IIS are integrated into AD a unique Service Principal Name (SPN) associates a service to a specific service account in AD.</p>
<p><em>Managed Service Accounts, introduced with Windows Server 2008 R2, were designed for complex applications, which require tighter integration with Active Directory.</em></p>
<p><em>Larger applications like MS SQL and Microsoft Exchange often required server redundancy when running to guarantee availability, but Managed Service Accounts did not support this. To remedy this, Group Managed Service Accounts were introduced with Windows Server 2012, but this requires that domain controllers run Windows Server 2012 or higher. Because of this, some organizations may still rely on basic Service Accounts.</em></p>

<h5>Enumerating Object Permissions</h5>
<p>Next we will enum specific perms associated with AD objects.  The technical details of those perms are complex and beyond the scope of this module, but it is important that we discuss the basics.</p>
<p>Objects in AD can have a set of perms applied to them with multiple <a href="https://learn.microsoft.com/en-us/windows/win32/secauthz/access-control-entries">Access Control Entries (ACE)</a>, which make up the <a href="https://learn.microsoft.com/en-us/windows/win32/secauthz/access-control-lists">Access Control List (ACL)</a>.  Each ACE defines if access to an object is allowed or denied.</p>
<p>Example, a domain user attempts to access a domain share, which is an object.  The targeted object, the share in this case, will go through a validation check based on the ACL to determine if the user has perms to the share.  ACL validation involves two main steps.</p>
<ul>
<li>The user sends an access token.</li>
<li>Consists of user identity and permissions.</li>
<li>Target object validates the token against the list of perms (ACL)</li>
<li>If the ACL allows the user to access the share, access is granted.</li>
<li>Otherwise request is denied.</li>
</ul>
<p>AD includes numerous permission types which can be used to configure an ACE.  From the attacking standpoint, we are mainly interested in several key permission types.  Here is a short list of the interesting ones</p>
<pre><code>GenericAll: Full permissions on object
GenericWrite: Edit certain attributes on the object
WriteOwner: Change ownership of the object
WriteDACL: Edit ACE&#39;s applied to object
AllExtendedRights: Change password, reset password, etc.
ForceChangePassword: Password change for object
Self (Self-Membership): Add ourselves to for example a group
</code></pre>
<ul>
<li>Other permissions are described in the <a href="https://learn.microsoft.com/en-us/windows/win32/secauthz/access-rights-and-access-masks">MS Docs</a></li>
</ul>

<h4>5. Active Directory - Automated Enumeration</h4>
<ul>
<li>Collect domain data using SharpHound.</li>
<li>Analyze the data using BloodHound.</li>
</ul>
<p>Some automated tools, like <a href="https://www.pingcastle.com/">PingCastle</a>, generate gorgeous reports although most require paid licenses for commercial use. In our case, we will focus on <a href="https://bloodhound.readthedocs.io/en/latest/">BloodHound</a>, an excellent free tool that&#39;s extremely useful for analyzing AD environments.</p>
<p>It&#39;s worth noting that automated tools generate a great deal of network traffic and many administrators will likely recognize a spike in traffic as we run these tools.</p>
<h5>Collecting Data with SharpHound</h5>
<p>In the next section we will use BloodHound to analyze, sort, and present data, and us the companion tool <a href="https://bloodhound.readthedocs.io/en/latest/data-collection/sharphound.html">SharpHound</a> to collect the data.  Sharphound is written in C# and uses Windows API functions with LDAP namespace functions similar to those we manually used in prior sections.  Example, SharpHound will attempt to use <code>NetWkstaUserEnum</code> and <code>NetSessionEnum</code> to enum logged-on sessions, as we did earlier.  It will also run queries agains the Remote Registry service, that we leveraged earlier.</p>
<p><em>It&#39;s often best to combine automatic and manual enumeration techniques when assessing Active Directory. Even though we could theoretically gather the same information with a manual approach, graphical relationships often reveal otherwise unnoticed attack paths.</em></p>
<p>First we need to get SharpHound up and running, it is available in several formats.  We can compile it ourselves, use a precompiled bin, or use it as a PowerShell script.  In this case, we will use the PowerShell script located in <code>C:\Tools</code> of CLIENT75.  Let&#39;s open a PowerShell session and import the script.</p>
<p>We can now start collecting domain data.  In order to run SharpHound, we must first run <code>Invoke-BloodHound</code>, which isn&#39;t intuitive since we&#39;re only running SharpHound.  Use <code>Get-Help</code> to learn more about the command.</p>
