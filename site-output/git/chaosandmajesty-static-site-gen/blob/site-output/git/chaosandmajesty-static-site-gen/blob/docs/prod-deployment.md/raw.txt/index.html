  1. # Production Deployment Playbook
  2. ​
  3. A reference for promoting Chaos & Majesty builds into production via a `prod` branch, a Docker-based GitHub Action, and an SSH-accessible VPS that currently serves `/var/www` behind Nginx.
  4. ​
  5. ## Goals & Constraints
  6. - Keep the existing VPS and Nginx footprint while introducing a containerized site service.
  7. - Automate builds from the repository so production only ever serves committed assets.
  8. - Avoid storing secrets in the repo; rely on CI/CD secrets and the VPS keyring.
  9. - Support quick rollbacks and minimal downtime when promoting new releases.
  10. ​
  11. ## Implementation Snapshot
  12. - Docker image now builds via a multi-stage `Dockerfile`, compiling the static bundle inside the build context before handing it to `nginxinc/nginx-unprivileged`.
  13. - Ansible playbook (`ansible/deploy.yml`) provisions `/opt/chaosandmajesty`, templates the Compose project, pulls the tagged image, and verifies health over `http://127.0.0.1:80/health`.
  14. - `.gitea/workflows/prod-deploy.yml` runs on every `prod` push, performing a smoke build, pushing the `prod`/`prod-<sha>` tags, and invoking the Ansible deploy through the CI runner.
  15. - Subdomain reverse-proxying is no longer automatic; extend `nginx/default.conf`
  16. if you need additional upstreams beyond the primary site + WebDAV share.
  17. ​
  18. ## Branching & Promotion Flow
  19. 1. Continue feature development on short-lived branches; merge to `main` after review.
  20. 2. Cut release candidates from `main` into `prod` via a fast-forward merge (no direct commits on `prod`).
  21. 3. Protect `prod` with branch rules (status checks, linear history) so only the GitHub Action can deploy.
  22. 4. Tag deployments (e.g., `prod-2024-07-01`) to map VPS state to repository history.
  23. ​
  24. > For the full bring-up procedure (stopping host nginx, mounting Let's Encrypt,
  25. > and running the first playbook), see `docs/prod-first-run.md`.
  26. ​
  27. ## CI/CD Overview
  28. On every push to `prod`, a dedicated GitHub Action should:
  29. 1. Check out the repo with full history for tag support.
  30. 2. Set up Node 18, install dependencies, and run `./build-site.sh` to regenerate `site-output/`.
  31. 3. Run smoke tests (today `./build-site.sh` already validates HTML; expand when unit tests exist).
  32. 4. Build a production Docker image using the root `Dockerfile` (which expects a pre-populated `site-output/`).
  33. 5. Tag and push the image to a registry (GitHub Container Registry is the path of least resistance).
  34. 6. Connect to the VPS over SSH, pull the new image, and restart the container via Docker Compose or `docker run`.
  35. 7. Post deployment status, including the image digest and the `./build-site.sh` output, to the workflow summary.
  36. ​
  37. ### GitHub Action Skeleton
  38. ```yaml
  39. name: Deploy prod
  40. ​
  41. on:
  42. push:
  43. branches: [prod]
  44. ​
  45. jobs:
  46. deploy:
  47. runs-on: ubuntu-latest
  48. permissions:
  49. contents: read
  50. packages: write
  51. steps:
  52. - uses: actions/checkout@v4
  53. with:
  54. fetch-depth: 0
  55. - uses: actions/setup-node@v4
  56. with:
  57. node-version: 18
  58. - run: npm ci
  59. - run: ./prepare-cm-files.sh
  60. - run: ./build-site.sh
  61. - name: Build and push image
  62. uses: docker/build-push-action@v5
  63. with:
  64. context: .
  65. tags: ghcr.io/chaosandmajesty/site:${{ github.sha }}
  66. push: true
  67. - name: Tag latest prod
  68. run: |
  69. docker buildx imagetools create \
  70. ghcr.io/chaosandmajesty/site:${{ github.sha }} \
  71. --tag ghcr.io/chaosandmajesty/site:prod
  72. - name: Deploy over SSH
  73. uses: appleboy/ssh-action@v1
  74. with:
  75. host: ${{ secrets.VPS_HOST }}
  76. username: ${{ secrets.VPS_USER }}
  77. key: ${{ secrets.VPS_SSH_KEY }}
  78. script: /opt/chaosandmajesty/bin/deploy.sh ghcr.io/chaosandmajesty/site:prod
  79. ```
  80. ​
  81. > Swap in your namespace, and tighten permissions/secrets before enabling prod.
  82. ​
  83. ## Container Image Strategy
  84. - The current `Dockerfile` expects `site-output/` to exist; ensure the Action runs `./build-site.sh` before `docker build` so the static bundle is in place.
  85. - Stick with the unprivileged Nginx base image; it listens on 8080 internally, which plays well with an upstream Nginx reverse proxy on the host. Mount `/var/www/html/dav` into `/usr/share/nginx/html/dav` when deploying so WebDAV remains on the host filesystem.
  86. - Use image labels (`org.opencontainers.image.*`) for traceability; they surface in GHCR UI and `docker inspect`.
  87. - Consider a second build stage (FROM node:18-alpine) to compile `site-output/` inside the Docker build for reproducibility. If you switch to that, `docker build` no longer depends on CI running `./build-site.sh` first.
  88. ​
  89. ## Registry & Secrets Checklist
  90. - `CR_PAT`: a GitHub personal access token or GitHub Actions OIDC with `packages:write` to push to GHCR.
  91. - `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`: credentials for SSH access. Use a deploy-only user on the server.
  92. - Optional `NGINX_RELOAD_CMD` secret (e.g., `sudo systemctl reload nginx`) if you want the Action to refresh Nginx after updating upstreams.
  93. - Store environment-specific toggles (e.g., basic auth) as Action secrets; never commit them to `smoke-test.yaml`.
  94. ​
  95. ## VPS Preparation
  96. 1. Install Docker Engine + Compose plugin (`apt-get install docker-ce docker-compose-plugin`).
  97. 2. Create a non-root `deploy` user, add to the `docker` group, and secure SSH access with the CI public key.
  98. 3. Lay down a runtime directory, e.g., `/opt/chaosandmajesty/`, containing:
  99. - `docker-compose.prod.yml`
  100. - `nginx/default.conf` (for reference)
  101. - `bin/deploy.sh` – a script that pulls the image, runs `docker compose up -d`, prunes old images, and emits a health check.
  102. 4. Keep `/var/www` as the Nginx document root but proxy traffic into the container.
  103. 5. Ensure outbound traffic from the VPS can reach GHCR (`docker login ghcr.io`).
  104. ​
  105. ### Example `docker-compose.prod.yml`
  106. ```yaml
  107. services:
  108. site:
  109. image: ghcr.io/chaosandmajesty/site:prod
  110. container_name: cm-prod
  111. restart: unless-stopped
  112. ports:
  113. - "127.0.0.1:8080:8080"
  114. healthcheck:
  115. test: ["CMD", "wget", "--no-verbose", "--tries=1", "--spider", "http://localhost:8080/health"]
  116. interval: 30s
  117. timeout: 5s
  118. retries: 3
  119. ```
  120. ​
  121. ### Example `/opt/chaosandmajesty/bin/deploy.sh`
  122. ```bash
  123. #!/usr/bin/env bash
  124. set -euo pipefail
  125. IMAGE_NAME=${1:?"Usage: deploy.sh <image>"}
  126. ​
  127. /usr/bin/docker login ghcr.io -u chaosandmajesty -p "$CR_PAT"
  128. /usr/bin/docker compose -f /opt/chaosandmajesty/docker-compose.prod.yml pull
  129. /usr/bin/docker compose -f /opt/chaosandmajesty/docker-compose.prod.yml up -d
  130. /usr/bin/docker image prune -f --filter label=chaosandmajesty.prod=true
  131. /usr/bin/curl --fail http://127.0.0.1:80/health
  132. ```
  133. Add execution permissions (`chmod +x`). Inject the token via an environment file or SSH agent forwarding; avoid hard-coding secrets.
  134. ​
  135. ## Nginx Integration on the VPS
  136. - Keep `/etc/nginx/sites-available/default` (or your site block) as the public entry point.
  137. - Proxy to the container listening on localhost:8080:
  138. ```nginx
  139. server {
  140. listen 80;
  141. server_name chaosandmajesty.com;
  142. ​
  143. location / {
  144. proxy_pass http://127.0.0.1:8080;
  145. proxy_set_header Host $host;
  146. proxy_set_header X-Real-IP $remote_addr;
  147. proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  148. proxy_set_header X-Forwarded-Proto $scheme;
  149. }
  150. }
  151. ```
  152. - Reload Nginx after the first successful container start: `sudo systemctl reload nginx`.
  153. - Keep TLS termination on the host (e.g., Certbot) so certificate renewals remain unchanged.
  154. ​
  155. ## Deployment Options
  156. ​
  157. ### Option A – GitHub Action + SSH (recommended)
  158. - **Flow:** Action builds/pushes the image, uses `appleboy/ssh-action` (or `rschwoebel/ssh-exec`) to run the deploy script.
  159. - **Pros:** No additional infrastructure, auditable; reuse Compose health checks, easy rollback via `docker compose up -d IMAGE=previous-tag`.
  160. - **Cons:** Requires SSH key distribution; CI must reach the VPS.
  161. ​
  162. ### Option B – Self-hosted Runner on the VPS
  163. - **Flow:** Install a GitHub Actions runner on the VPS. The workflow builds the image locally and runs `docker compose up -d` without SSH.
  164. - **Pros:** Avoids SSH keys; large artifacts never leave the server.
  165. - **Cons:** Runner downtime blocks deploys; runner needs system updates and isolation to avoid interfering with the live container.
  166. ​
  167. ### Option C – Pull-Based Deployment (Watchtower or Cron)
  168. - **Flow:** CI pushes the image and tags `prod`. The VPS runs Watchtower or a cron job (`docker compose pull && docker compose up -d`) that polls GHCR.
  169. - **Pros:** Decouples release initiation from CI connectivity; easier blue/green experiments.
  170. - **Cons:** Adds latency between `git push` and release; relies on server-side automation you must monitor.
  171. ​
  172. ## Rollback Plan
  173. 1. List images: `docker images ghcr.io/chaosandmajesty/site`.
  174. 2. Re-run the deploy script with a prior tag (e.g., `prod-2024-07-01`).
  175. 3. If the container fails health checks, `docker compose logs -f` and keep the previous container running (`docker compose up` keeps the last healthy container until the new one passes).
  176. 4. As a last resort, revert the Nginx proxy to serve the legacy `/var/www` build while triaging the container.
  177. ​
  178. ## Operational Tips
  179. - Run `./build-site.sh` locally before tagging a release; stash the output for PR reviewers.
  180. - Set up uptime monitoring against `https://chaosandmajesty.com/health` (proxying to container `/health`).
  181. - Rotate SSH keys and GHCR tokens quarterly; document expiration dates alongside the secrets in 1Password or Vault.
  182. - Capture the workflow URL and container digest in release notes for traceability.
  183. ​
  184. With these pieces in place, the `prod` branch becomes the single source of truth for what runs in production, while the VPS keeps its existing networking footprint.
