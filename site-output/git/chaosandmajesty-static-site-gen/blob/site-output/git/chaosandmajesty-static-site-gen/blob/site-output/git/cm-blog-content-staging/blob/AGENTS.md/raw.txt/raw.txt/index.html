  1. # Repository Guidelines
  2. ​
  3. ## Project Structure & Module Organization
  4. - `sources/` stores research notes grouped by topic (for example `sources/OffSec/`). Keep supporting images in `sources/_resources/` so they ship with the draft that references them.
  5. - `content/` holds publish-ready Markdown ready to be formated for the static site generator, you can derive our "tone" and writing style from these works; place final posts under `blog/<slug>.md` and keep working copies elsewhere until the metadata is complete.
  6. - `templates/blog-model.md` documents the downstream layout, required front matter, and generator inputs—treat it as the source of truth and update it if the build contract changes.
  7. ​
  8. ## Content Conversion Workflow
  9. - Structure posts derived from `sources/` notes with a concise `## TLDR;` section followed by `## Working Notes... In Graphic Detail...` that preserves the primer detail.
  10. - Sanitize workstation identifiers (`m4xx3d0ut`, `h4ckt0p`, etc.) and private addresses such as `192.168.29.0/24`, swapping in neutral stand-ins like `operator@labhost` or `192.0.2.0/24` before publishing.
  11. - Trim the working notes before the final `#### Exercises` block unless the exercise content is intentionally part of the post.
  12. - While polishing the working notes, expand shorthand lists into readable sentences and fix spelling/grammar where context makes the intention clear; leave ambiguous fragments untouched and flag them for review.
  13. ​
  14. ​
  15. ## Build, Test, and Development Commands
  16. - `npx markdownlint-cli "sources/**/*.md" "content/**/*.md"` — run before every PR to catch heading levels, spacing, and trailing whitespace; install `markdownlint-cli` globally if you prefer.
  17. - `make preview` (in the sibling `chaosandmajesty-static-site-gen` project) — launches the static-site preview with HTMX routing so you can validate navigation against your updates.
  18. - `./build-site.sh` (same project) — produces the deployable HTML bundle; use it for pre-release smoke checks.
  19. ​
  20. ## Coding Style & Naming Conventions
  21. - Front matter must follow the contract in `templates/blog-model.md`: include `title`, `slug`, `author`, `summary`, ISO 8601 `publishedAt`/`updatedAt`, `readingMinutes`, and optional `tags`/`heroImage`.
  22. - Final filenames use lowercase, hyphenated slugs (e.g. `content/blog/offsec-labs-week-01.md`); avoid spaces or uppercase characters once a post leaves `sources/`.
  23. - Prefer ATX headings (`##`), wrap prose near 100 characters, and annotate fenced code blocks with language hints to improve highlighted output.
  24. ​
  25. ## Testing Guidelines
  26. - Linting plus preview clicks are the primary quality gates; there are no automated unit tests for this repository.
  27. - Verify the generated list, article fragment, and hero media render correctly when running `make preview`.
  28. - Use `<!-- TODO -->` markers only for short-lived follow-ups and convert them to tracked issues before merge.
  29. ​
  30. ## Commit & Pull Request Guidelines
  31. - Write commits in imperative present tense ("Add OffSec chapter summaries") and group related asset updates with the content change they support.
  32. - PRs should link the driving issue, summarise reader impact, and attach a screenshot or preview URL for visual tweaks.
  33. - Request review from another content maintainer and note any deferred follow-up tasks in the PR description checklist.
