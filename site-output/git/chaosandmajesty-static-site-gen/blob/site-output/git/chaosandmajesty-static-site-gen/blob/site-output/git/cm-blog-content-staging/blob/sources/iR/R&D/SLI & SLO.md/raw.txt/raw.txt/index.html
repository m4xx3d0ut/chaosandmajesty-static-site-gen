  23. # Service Level Indicators & Service Level Objectives
  24. ​
  25. SLIs, SLOs and SLAs aren’t just useful abstractions. Without them you cannot know if your system is reliable, available, or even useful. If they don’t tie explicitly back to your business objectives then you have no idea if the choices you make are helping or hurting your business. You also can’t make honest promises to your customers. If you’re building a system from scratch, make sure that SLIs, SLOs and SLAs are part of your system requirements. If you already have a production system but don’t have them clearly defined then that’s your highest priority work.
  26. ​
  27. - If you want to have a reliable service, you must first define “reliability.” In most cases that actually translates to availability.
  28. - If you want to know how reliable your service is, you must be able to measure the rates of successful and unsuccessful queries; these will form the basis of your SLIs.
  29. - The more reliable the service, the more it costs to operate. Define the lowest level of reliability that you can get away with, and state that as your Service Level Objective (SLO).
  30. - Without an SLO, your team and your stakeholders cannot make principled judgements about whether your service needs to be made more reliable (increasing cost and slowing development) or less reliable (allowing greater velocity of development).
  31. - If you’re charging your customers money you'll probably need an SLA, and it should be a little bit looser than your SLO.

  60. ## SLI Equation
  61. ​
  62. `SLI = (good events / valid events) * 100%`
  63. ​
  64. 1. SLIs fall between 0% and 100%.
  65. 0% means nothing works, 100% means nothing is broken.
  66. This scale is intuitive and directly translates to percentagereliability SLOs and error budgets.
  67. 2. SLIs have a consistent format.
  68. Consistency allows common tooling to be built around SLIs.
  69. Alerting logic, error budget calculations, and SLO analysis
  70. and reporting tools can all be written to expect the same
  71. inputs: good events, valid events, and an SLO threshold.
  72. ​
  73. Events can be prevented from counting against an error budget either by
  74. including them in the numerator or by excluding them from the denominator. The former is achieved by classifying some events good, the
  75. latter by classifying some events invalid.

  98. ## SLI Types
  99. ​
  100. ### Availability
  101. ​
  102. #### Request / Response
  103. ​
  104. The proportion of valid requests served successfully.
  105. ​
  106. What requests this system serves are valid for the SLI?
  107. What makes a response successful?
  108. ​
  109. ​
  110. ### Latency
  111. ​
  112. #### Request / Response
  113. ​
  114. The proportion of valid requests served faster than a threshold.
  115. ​
  116. What requests this system serves are valid for the SLI?
  117. When does the timer measuring the request latency start and stop?
  118. ​
  119. ​
  120. ### Quality
  121. ​
  122. #### Request / Response
  123. ​
  124. The proportion of valid requests served without degrading quality.
  125. ​
  126. What requests this system serves are valid for the SLI?
  127. How to determine whether the response was served with degraded quality?
  128. ​
  129. ​
  130. ### Freshness
  131. ​
  132. #### Data Processing
  133. ​
  134. The proportion of valid data updated more recently than a threshold.
  135. ​
  136. What data this system processes are valid for the SLI?
  137. When does the timer measuring the freshness of data start and stop?
  138. ​
  139. ​
  140. ### Coverage
  141. ​
  142. #### Data Processing
  143. ​
  144. The proportion of valid data processed successfully.
  145. ​
  146. What data this system processes are valid for the SLI?
  147. How to determine whether the processing of a particular piece of data was successful?
  148. ​
  149. ​
  150. ### Correctness
  151. ​
  152. #### Data Processing
  153. ​
  154. The proportion of valid data producing correct output.
  155. ​
  156. What data this system processes are valid for the SLI?
  157. How to determine the correctness of output records?
  158. ​
  159. ​
  160. ### Throughput
  161. ​
  162. #### Data Processing
  163. ​
  164. The proportion of time where the data processing rate is faster than a threshold.
  165. ​
  166. What is the units of measurement for your data processing rate?
  167. ​

  173. ## Example SLO
  174. ​
  175. <br>
  176. ​
  177. **User Journey:** Home Page Load
  178. ​
  179. **SLI Type:** Latency
  180. ​
  181. **SLI Specification:**
  182. - Proportion of home page requests served in < 100ms
  183. - SLI equation; `Requests served in < 100ms / Requests`
  184. ​
  185. **SLI Implementations:**
  186. - Proportion of home page requests served in < 100ms
  187. - Measured from server log request latency values
  188. - This will miss requests that don't reach the backend
  189. - Proportion of home page requests served in < 100ms
  190. - Measured by probe executing JS in VM browser
  191. - This will catch errors when requests cannot reach our network, but may miss issues affecting a subset of users
  192. ​
  193. **SLO:**
  194. 99% of home page request in the past 28 days served in < 100ms.
