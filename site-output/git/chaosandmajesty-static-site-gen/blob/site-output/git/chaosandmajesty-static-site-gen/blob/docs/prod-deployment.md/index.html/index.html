  14. <h1>Production Deployment Playbook</h1>
  15. <p>A reference for promoting Chaos &amp; Majesty builds into production via a <code>prod</code> branch, a Docker-based GitHub Action, and an SSH-accessible VPS that currently serves <code>/var/www</code> behind Nginx.</p>
  16. <h2>Goals &amp; Constraints</h2>
  17. <ul>
  18. <li>Keep the existing VPS and Nginx footprint while introducing a containerized site service.</li>
  19. <li>Automate builds from the repository so production only ever serves committed assets.</li>
  20. <li>Avoid storing secrets in the repo; rely on CI/CD secrets and the VPS keyring.</li>
  21. <li>Support quick rollbacks and minimal downtime when promoting new releases.</li>
  22. </ul>
  23. <h2>Implementation Snapshot</h2>
  24. <ul>
  25. <li>Docker image now builds via a multi-stage <code>Dockerfile</code>, compiling the static bundle inside the build context before handing it to <code>nginxinc/nginx-unprivileged</code>.</li>
  26. <li>Ansible playbook (<code>ansible/deploy.yml</code>) provisions <code>/opt/chaosandmajesty</code>, templates the Compose project, pulls the tagged image, and verifies health over <code>http://127.0.0.1:80/health</code>.</li>
  27. <li><code>.gitea/workflows/prod-deploy.yml</code> runs on every <code>prod</code> push, performing a smoke build, pushing the <code>prod</code>/<code>prod-&lt;sha&gt;</code> tags, and invoking the Ansible deploy through the CI runner.</li>
  28. <li>Subdomain reverse-proxying is no longer automatic; extend <code>nginx/default.conf</code>
  29. if you need additional upstreams beyond the primary site + WebDAV share.</li>
  30. </ul>
  31. <h2>Branching &amp; Promotion Flow</h2>
  32. <ol>
  33. <li>Continue feature development on short-lived branches; merge to <code>main</code> after review.</li>
  34. <li>Cut release candidates from <code>main</code> into <code>prod</code> via a fast-forward merge (no direct commits on <code>prod</code>).</li>
  35. <li>Protect <code>prod</code> with branch rules (status checks, linear history) so only the GitHub Action can deploy.</li>
  36. <li>Tag deployments (e.g., <code>prod-2024-07-01</code>) to map VPS state to repository history.</li>
  37. </ol>
  38. <blockquote>
  39. <p>For the full bring-up procedure (stopping host nginx, mounting Let&#39;s Encrypt,
  40. and running the first playbook), see <code>docs/prod-first-run.md</code>.</p>
  41. </blockquote>
  42. <h2>CI/CD Overview</h2>
  43. <p>On every push to <code>prod</code>, a dedicated GitHub Action should:</p>
  44. <ol>
  45. <li>Check out the repo with full history for tag support.</li>
  46. <li>Set up Node 18, install dependencies, and run <code>./build-site.sh</code> to regenerate <code>site-output/</code>.</li>
  47. <li>Run smoke tests (today <code>./build-site.sh</code> already validates HTML; expand when unit tests exist).</li>
  48. <li>Build a production Docker image using the root <code>Dockerfile</code> (which expects a pre-populated <code>site-output/</code>).</li>
  49. <li>Tag and push the image to a registry (GitHub Container Registry is the path of least resistance).</li>
  50. <li>Connect to the VPS over SSH, pull the new image, and restart the container via Docker Compose or <code>docker run</code>.</li>
  51. <li>Post deployment status, including the image digest and the <code>./build-site.sh</code> output, to the workflow summary.</li>
  52. </ol>
  53. <h3>GitHub Action Skeleton</h3>
  54. <pre><code class="language-yaml">name: Deploy prod
  55. ​
  56. on:
  57. push:
  58. branches: [prod]
  59. ​
  60. jobs:
  61. deploy:
  62. runs-on: ubuntu-latest
  63. permissions:
  64. contents: read
  65. packages: write
  66. steps:
  67. - uses: actions/checkout@v4
  68. with:
  69. fetch-depth: 0
  70. - uses: actions/setup-node@v4
  71. with:
  72. node-version: 18
  73. - run: npm ci
  74. - run: ./prepare-cm-files.sh
  75. - run: ./build-site.sh
  76. - name: Build and push image
  77. uses: docker/build-push-action@v5
  78. with:
  79. context: .
  80. tags: ghcr.io/chaosandmajesty/site:${{ github.sha }}
  81. push: true
  82. - name: Tag latest prod
  83. run: |
  84. docker buildx imagetools create \
  85. ghcr.io/chaosandmajesty/site:${{ github.sha }} \
  86. --tag ghcr.io/chaosandmajesty/site:prod
  87. - name: Deploy over SSH
  88. uses: appleboy/ssh-action@v1
  89. with:
  90. host: ${{ secrets.VPS_HOST }}
  91. username: ${{ secrets.VPS_USER }}
  92. key: ${{ secrets.VPS_SSH_KEY }}
  93. script: /opt/chaosandmajesty/bin/deploy.sh ghcr.io/chaosandmajesty/site:prod
  94. </code></pre>
  95. <blockquote>
  96. <p>Swap in your namespace, and tighten permissions/secrets before enabling prod.</p>
  97. </blockquote>
  98. <h2>Container Image Strategy</h2>
  99. <ul>
  100. <li>The current <code>Dockerfile</code> expects <code>site-output/</code> to exist; ensure the Action runs <code>./build-site.sh</code> before <code>docker build</code> so the static bundle is in place.</li>
  101. <li>Stick with the unprivileged Nginx base image; it listens on 8080 internally, which plays well with an upstream Nginx reverse proxy on the host. Mount <code>/var/www/html/dav</code> into <code>/usr/share/nginx/html/dav</code> when deploying so WebDAV remains on the host filesystem.</li>
  102. <li>Use image labels (<code>org.opencontainers.image.*</code>) for traceability; they surface in GHCR UI and <code>docker inspect</code>.</li>
  103. <li>Consider a second build stage (FROM node:18-alpine) to compile <code>site-output/</code> inside the Docker build for reproducibility. If you switch to that, <code>docker build</code> no longer depends on CI running <code>./build-site.sh</code> first.</li>
  104. </ul>
  105. <h2>Registry &amp; Secrets Checklist</h2>
  106. <ul>
  107. <li><code>CR_PAT</code>: a GitHub personal access token or GitHub Actions OIDC with <code>packages:write</code> to push to GHCR.</li>
  108. <li><code>VPS_HOST</code>, <code>VPS_USER</code>, <code>VPS_SSH_KEY</code>: credentials for SSH access. Use a deploy-only user on the server.</li>
  109. <li>Optional <code>NGINX_RELOAD_CMD</code> secret (e.g., <code>sudo systemctl reload nginx</code>) if you want the Action to refresh Nginx after updating upstreams.</li>
  110. <li>Store environment-specific toggles (e.g., basic auth) as Action secrets; never commit them to <code>smoke-test.yaml</code>.</li>
  111. </ul>
  112. <h2>VPS Preparation</h2>
  113. <ol>
  114. <li>Install Docker Engine + Compose plugin (<code>apt-get install docker-ce docker-compose-plugin</code>).</li>
  115. <li>Create a non-root <code>deploy</code> user, add to the <code>docker</code> group, and secure SSH access with the CI public key.</li>
  116. <li>Lay down a runtime directory, e.g., <code>/opt/chaosandmajesty/</code>, containing:<ul>
  117. <li><code>docker-compose.prod.yml</code></li>
  118. <li><code>nginx/default.conf</code> (for reference)</li>
  119. <li><code>bin/deploy.sh</code> – a script that pulls the image, runs <code>docker compose up -d</code>, prunes old images, and emits a health check.</li>
  120. </ul>
  121. </li>
  122. <li>Keep <code>/var/www</code> as the Nginx document root but proxy traffic into the container.</li>
  123. <li>Ensure outbound traffic from the VPS can reach GHCR (<code>docker login ghcr.io</code>).</li>
  124. </ol>
  125. <h3>Example <code>docker-compose.prod.yml</code></h3>
  126. <pre><code class="language-yaml">services:
  127. site:
  128. image: ghcr.io/chaosandmajesty/site:prod
  129. container_name: cm-prod
  130. restart: unless-stopped
  131. ports:
  132. - &quot;127.0.0.1:8080:8080&quot;
  133. healthcheck:
  134. test: [&quot;CMD&quot;, &quot;wget&quot;, &quot;--no-verbose&quot;, &quot;--tries=1&quot;, &quot;--spider&quot;, &quot;http://localhost:8080/health&quot;]
  135. interval: 30s
  136. timeout: 5s
  137. retries: 3
  138. </code></pre>
  139. <h3>Example <code>/opt/chaosandmajesty/bin/deploy.sh</code></h3>
  140. <pre><code class="language-bash">#!/usr/bin/env bash
  141. set -euo pipefail
  142. IMAGE_NAME=${1:?&quot;Usage: deploy.sh &lt;image&gt;&quot;}
  143. ​
  144. /usr/bin/docker login ghcr.io -u chaosandmajesty -p &quot;$CR_PAT&quot;
  145. /usr/bin/docker compose -f /opt/chaosandmajesty/docker-compose.prod.yml pull
  146. /usr/bin/docker compose -f /opt/chaosandmajesty/docker-compose.prod.yml up -d
  147. /usr/bin/docker image prune -f --filter label=chaosandmajesty.prod=true
  148. /usr/bin/curl --fail http://127.0.0.1:80/health
  149. </code></pre>
  150. <p>Add execution permissions (<code>chmod +x</code>). Inject the token via an environment file or SSH agent forwarding; avoid hard-coding secrets.</p>
  151. <h2>Nginx Integration on the VPS</h2>
  152. <ul>
  153. <li>Keep <code>/etc/nginx/sites-available/default</code> (or your site block) as the public entry point.</li>
  154. <li>Proxy to the container listening on localhost:8080:<pre><code class="language-nginx">server {
  155. listen 80;
  156. server_name chaosandmajesty.com;
  157. ​
  158. location / {
  159. proxy_pass http://127.0.0.1:8080;
  160. proxy_set_header Host $host;
  161. proxy_set_header X-Real-IP $remote_addr;
  162. proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  163. proxy_set_header X-Forwarded-Proto $scheme;
  164. }
  165. }
  166. </code></pre>
  167. </li>
  168. <li>Reload Nginx after the first successful container start: <code>sudo systemctl reload nginx</code>.</li>
  169. <li>Keep TLS termination on the host (e.g., Certbot) so certificate renewals remain unchanged.</li>
  170. </ul>
  171. <h2>Deployment Options</h2>
  172. <h3>Option A – GitHub Action + SSH (recommended)</h3>
  173. <ul>
  174. <li><strong>Flow:</strong> Action builds/pushes the image, uses <code>appleboy/ssh-action</code> (or <code>rschwoebel/ssh-exec</code>) to run the deploy script.</li>
  175. <li><strong>Pros:</strong> No additional infrastructure, auditable; reuse Compose health checks, easy rollback via <code>docker compose up -d IMAGE=previous-tag</code>.</li>
  176. <li><strong>Cons:</strong> Requires SSH key distribution; CI must reach the VPS.</li>
  177. </ul>
  178. <h3>Option B – Self-hosted Runner on the VPS</h3>
  179. <ul>
  180. <li><strong>Flow:</strong> Install a GitHub Actions runner on the VPS. The workflow builds the image locally and runs <code>docker compose up -d</code> without SSH.</li>
  181. <li><strong>Pros:</strong> Avoids SSH keys; large artifacts never leave the server.</li>
  182. <li><strong>Cons:</strong> Runner downtime blocks deploys; runner needs system updates and isolation to avoid interfering with the live container.</li>
  183. </ul>
  184. <h3>Option C – Pull-Based Deployment (Watchtower or Cron)</h3>
  185. <ul>
  186. <li><strong>Flow:</strong> CI pushes the image and tags <code>prod</code>. The VPS runs Watchtower or a cron job (<code>docker compose pull &amp;&amp; docker compose up -d</code>) that polls GHCR.</li>
  187. <li><strong>Pros:</strong> Decouples release initiation from CI connectivity; easier blue/green experiments.</li>
  188. <li><strong>Cons:</strong> Adds latency between <code>git push</code> and release; relies on server-side automation you must monitor.</li>
  189. </ul>
  190. <h2>Rollback Plan</h2>
  191. <ol>
  192. <li>List images: <code>docker images ghcr.io/chaosandmajesty/site</code>.</li>
  193. <li>Re-run the deploy script with a prior tag (e.g., <code>prod-2024-07-01</code>).</li>
  194. <li>If the container fails health checks, <code>docker compose logs -f</code> and keep the previous container running (<code>docker compose up</code> keeps the last healthy container until the new one passes).</li>
  195. <li>As a last resort, revert the Nginx proxy to serve the legacy <code>/var/www</code> build while triaging the container.</li>
  196. </ol>
  197. <h2>Operational Tips</h2>
  198. <ul>
  199. <li>Run <code>./build-site.sh</code> locally before tagging a release; stash the output for PR reviewers.</li>
  200. <li>Set up uptime monitoring against <code>https://chaosandmajesty.com/health</code> (proxying to container <code>/health</code>).</li>
  201. <li>Rotate SSH keys and GHCR tokens quarterly; document expiration dates alongside the secrets in 1Password or Vault.</li>
  202. <li>Capture the workflow URL and container digest in release notes for traceability.</li>
  203. </ul>
  204. <p>With these pieces in place, the <code>prod</code> branch becomes the single source of truth for what runs in production, while the VPS keeps its existing networking footprint.</p>
