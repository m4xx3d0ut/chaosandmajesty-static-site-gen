# R&D (Methods, Madness, Caffeine)

## Methodologies

One could argue the point that my entire life has been an exercise in R&D, I'm sure many (if not all) of us could make that assertion. As such, developing a working methodology for R&D has felt like an extension of my natural state. Art, mirroring life, mirroring art, and so on. Now I digress from the metaphysics of my current state and want to talk about effective methodology. Think of how we, as humans, learn. First we watch, then we practice, and finally we apply what we have learned. We must start small by breaking the skill down into the smallest units possible, but after some time, persistence, and iteration we can achieve a mastery of the skill. R&D is no different, the "R" does stand for "Research" after all and this is where we learn!

- **Research (all the things) Phase**
    
    - *High level reading and content consumption on things.*
        - The goal being to attain a general and broad understanding of the things, the first implementation, the existing implementations, and the current state of the art.
    - *Drill down into the things in great detail.*
        - Read all of the white papers, technical documents, libraries, and open source project relevant to the things.
- **Develop (all the things) Phase**
    
    - *Throw some code at the wall, see what sticks*
        - Work through examples in git repos, research papers, and other content to gain a general working knowledge of the things.
            - *NOTE:* This step is cyclical with the "Research Phase". One rabbit hole leads to another, which leads to another, etc. It is imperative that we drill down past the things, so we understand the underpinnings. If we gain an understanding of how the things that makes the things work works, it allows us to conceptualize the interactions between the systems which will be vital in the next steps.
    - *Build a Proof of Concept (PoC).*
        - Once we know how the things work and how to build them, the best thing we can do to extend our understanding of the things is to build a PoC with it! The problems we encounter here will help broaden our understanding of the things and help us build a strong foundational working knowledge.
    - *Begin developing a Prototype (Proto).*
        - Some of you might ask "Oh great one, isn't a PoC and a Proto kind of the same thing?". Well, yes, but no. A PoC helps us prove out the sticky bits and demonstrate that a concept can indeed function as theorized. A Proto incorporates many details of the PoC but will be architecturally quite different. The Proto will begin to shape how the things can function as a product. As we work through this step, new functionality, user flows, and design elements will form naturally as part of the creative process. The Proto provides an internally testable model of what the things could be, helps us achieve buy-in, and (if all goes well) will evolve into an MVP!
            - ???
                - This evolutionary stage assures the Proto is "Product Focused" from the onset. A good Proto should demonstrate the capabilities of the system and draw a clear picture of what the MVP features will be. The business case and product viability should be apparent to the internal testers of the Proto.
            - Profit.
                - Most important, a well designed Proto should follow production practices to a "T", this minimizes development overlap and gets the MVP to market quickly. We want to focus on the architecture and follow "secure by design" principles, these concepts are foundational to producing viable product, that will gain the trust and adoption of users while generating revenue for its long-term sustainability.

### AI Infrastructure (Rabbit Holes)

As with most software systems, an AI software system needs some hardware to run on. That hardware needs an operating system (Rabbit Hole #3) for it to run the software and that software needs numerous libraries and frameworks for it to do the things. AI and ML systems in general require significant compute resources, this requirement increases by orders of magnitude when the system is a Large Language Model (LLM). In general, we want as much VRAM as we afford and fast IO to it. Most LLM systems are constrained more by the speed of VRAM IO than they are by the available compute, this is due to the means by which a model is initialized. Many Gigabytes of data must traverse the PCI and VRAM bus, so we must take these factors under consideration.

In a perfect world we would start with purpose built enterprise grade hardware, but this would be a stretch on the budget for an unproven system so we will take what we can get. Our dev system is on the high end of consumer gaming grade, with a few enterprise tweaks (read; dirty hacks to get around vendor feature lock-out).

- **Local Dev System Spec (The Important Hardware Bits)**
    - XL Tower Case
        - Big "Gamer" case, lots of cooling, fancy glass side window to admire all of the RGB LEDs on (literally) every component
    - Asus ROG Zenith II Extreme MoBo
        - Absurdly expensive, it had on OLED screen on it, and fast bus speeds
    - AMD Threadripper 24 core (48 thread) CPU
        - Supports virtualization extension (Rabbit Hole #2)
    - Nvidia RTX Titan
        - The range topping gaming grade card of its generation, nearly identical in technical specs to the datacenter grade RTX 6000 (Rabbit Hole #4)
    - 3x Samsung Evo 980 Pro NVME SSD
        - Brutally fast storage IO
    - 256 GB G.Skill DDR4 3200 RAM
        - The max supported by the MoBo... and we will need it (Rabbit Hole #5)

#### A Summary of Rabbit Holes 1-5

This system has a good bit of horsepower, in a prior life it was my gaming machine, but it now serves a greater purpose (I've really just been playing on my Steam Deck lately, so no big loss). So we have our hardware, great! Now we need a suitable OS and a Hypervisor, the OS will handle the physical hardware and the Hypervisor will handle the virtual hardware. There are many options here, VMware and Citrix come to mind, but while they do leverage many open source components they are closed source platforms (we cannot view the source code in its entirety). I ask you, how can you "trust" a system you cannot develop an independent opinion on? You can't. I'm not a fan of putting my trust in 3rd parties, nor should you be, but we will save that discussion (read; drawn out rant) for later. So what is a suitable open source platform that we can trust? Leaning on my years of experience with Linux, enter "Canonical" and their enterprise grade, open source, product offerings. The OS Ubuntu Server LTS 20.04.3 is both open source and has enterprise support options available for when we need them, great! Now for the Hypervisor, we tap the venerable Type-1 Hypervisor KVM (Kernel Virtual Machine) which has excellent capabilities and can be found in many diverse deployments (The Large Hadron Collider | CERN for instance).  
So we have that covered, now the OS/Hypervisor need some software and libraries to make the things do the things. I thought through the notion of managing virtualization from the OS using the standard Virsh CLI on the server host and Virt-Manager GUI from my workstation. While that would work for a small deployment, 1-20 physical systems, where I could manage nodes through SSH and some fancy Bash scripting. But what happens if we want to scale that to 200, or 2,000, or full on hyper-scale where we exceed 5,000 systems... that's a lot of Bash scripting and not really feasible! So the question, of course, is how to hyper-scale datacenters work? The answer is simple, hyper-converged infrastructure (HCI). At a high level, HCI is an architecture where all of the physical system resources are "converged" and abstracted away into software defined layers. Compute, storage, and networking are defined through software and the use of the resources is federated across all instances. It is both a thing of beauty and immeasurably complex. For context, a good example of HCI is Amazon AWS (yes, the whole thing).  
Down the HCI rabbit hole we go! So we can't walk into Fry's Electronics (I know they went out of business, but I miss them dearly) and buy an Amazon AWS installer disc, but luckily our friends at Canonical have us covered once again! OpenStack is a fully open source hyper-converged framework, it runs on our Ubuntu OS, and it supports KVM Hypervisor. After reading the docs, things still weren't fully clear to me. It is ultra modular with several core components and a few possible deployment paths. Lowest bar to entry is DevStack, a set of build scripts that deploys a volatile OpenStack environment for testing and development. After a few days of working with it, the topology of an OpenStack system started to become much clearer.

- **OpenStack Core**
    - Nova
        - Software Defined Compute, manages the KVM Hypervisor
    - Cinder
        - Software Defined Storage, abstracts storage away from physical system for virtualization
    - Neutron
        - Software Defined Networking, create and manage complex virtual networks through Open vSwitch
    - Keystone
        - Identity management
    - Glance
        - Image storage for disk, OS, system
    - Horizon
        - The web UI interface to the control plane

As I mentioned, DevStack is volatile, so not suitable for a long term dev env. The aforementioned core components are comprised of 30+ individual services. So you can imagine the deployment process is not so straight forward, but as they say if it can be done then it can be scripted and our good friends over at the Kolla-Ansible project have us covered! The Kolla-Ansible framework provides us a (relatively) straightforward way to deploy all of the required services, containerized with Docker, for a full OpenStack deployment by editing a handful of config files. The documentation is a little sparse so the process involved a great deal of back and forth between reading the source code and OpenStack docs, but after serveral weeks of this our configs and services were dialed in.

Once the basics were handled, I did a little extra scripting to get the kind of functionality I wanted in a dev system env. The build system can deploy an all-in-one or multi-node system, multi-node is typical for OpenStack deployments but as this is a resource constrained local dev system I focused on all-in-one. With the additional "quality of life" scripts working together with Kolla, in a single command we are able to:

- Deploy core services
- Sett static routes on the host
- Configure host network interfaces
- Upload OS images to Glance
- Configure Nova options
- Create a Neutron public/private network
- Deploy a virtual router to the Neutron network to provide a gateway to the private segment
- Deploy a test Nova VM to the private network segment
- Source the freshly created env file and print the Hypervisor resources to our terminal

Beyond that, reconfigure, destroy, and redeploy has been streamlined down to one script. Now we have an easy to deploy, flexible, hyper-converged dev system!

The next thing we need to consider is compute resources, CPU is simple and handled by the Hypervisor, but GPU is another story. As state in the spec, I have a Nvidia Titan RTX. It's a great consumer grade card, but it lacks some of the capabilities of the datacenter class GPUs. I could pass the entire PCI device through to a single VM which would do the job for developing simple architecture, but as you may gather by now, I don't do "simple". If we want to develop more complex distributed compute systems with a single graphics card, we need VGPU (a feature available on most datacenter class Nvidia cards). For every problem, there is a solution, so into the docs we go (Rabbit Hole #4) to determine what makes the Nvidia VGPU feature work! Interesting fact, architecturally the consumer Titan RTX and datacenter RTX 6000 are nearly identical. Other than a more robust cooler and an overclock they are essentially the same card, so in theory they should have the same capabilities. As it turns out, the Nvidia driver identifies the graphics card by reading a bus ID. Luckily for us, its fairly straightforward to unpack and modify their Linux driver, which means we can intercept and modify this value! Apparently there is an entire community online that develops patches for the drivers that do just that, making the process trivial, and voila! Our Titan RTX is now a RTX 6000 with VGPU enabled. There is a license cost for VGPU and you need the DC Nvidia Grid driver from their dev portal, but they do offer a generous 90 day trial license (which is the least they can do after you paid 2x the cost of the Titan for a bigger cooler and different driver). License in hand, Grid driver patched, and we can now create "mediated devices" (i.e.- VGPUs). One card can now us time-slice scheduling to become anywhere from 2-24 cards. Creating 2 VGPUs with 12 GB of VRAM each is a good starting point for developing a distributed compute system, so we can check that off the list.

Our last hurdle was the enormous memory footprint of a single-node OpenStack deployment (Rabbit Hole #5), nearly 62 GB of RAM just to idle the system after a full reboot! No surprise here, our customized single node deployment runs 38 individual services, each in their own Docker container. In a standard multi-node deployment, where these would be distributed across 2-3 or 10's-100's of machines you can start to conceptualize the power of a fully hyper-converged system. Off the shelf hardware (Power Efficient 1u Blade Servers, 4u Storage Servers, GPU Compute System) all form an expansive and flexible compute fabric without the additional complexity of storage area networks, iSCSI over dedicated VLANs for example, and complex physical network topologies, a simple condensed core network architecture would be sufficient for even a large deployment. This is because the control plane gives us an interface into the hyper-converged system and the system itself handles most details of its physical state and environment. Back to the problem at hand, RAM. This is an easy one to fix, as we had 256 GB (max supported by our MoBo) in hand the following day thanks to Amazon Prime (but, I still miss Fry's). Now our system has sufficient resources, to make the things do the things and we can move on to the next phase. Keep in mind, this is a local dev unit, running commodity consumer hardware, and despite that fact we have just completed our deployment of a fully hyper-converged private cloud! I could imagine somewhere in the world an AWS Billing Team Manager just shed a single tear.

    - Configured as a "flat" network, where Layer-2 is handled by the host adapter and we take an IP range on the local network
        - *Note:* As Ozzy Osbourne once said "Of all the things I miss, I miss my mind the most", that is exactly how the learning curve of Open vSwitch will make you feel. That said, it is an incredibly powerful SDN once you gain some proficiency in it.

After playing with it on the R&D Slack for about a day, we wanted to give it "memory" so we could have more meaningful conversations with it. At this point it can only handle a single request response, as CodeLLaMa is stateless, so it doesn't retain any of our prior messages. More reading. I realized this may be a slightly unique case, we are talking to the LLM through a shared chat interface with many users, not a single user chat as we are used to with ChatGPT. We need to consider how it will track multiple conversations with multiple user, but what if it has multiple tenants? Viewing this through the lens of a product, it's best we think through multi-tenancy now so we can validate its viability. Now we get down to business, let's build a prototype!

We now know the challenge, but what is the solution? Most existing libs I looked at offered memory based chat buffers, but maintaining these objects within the Python process would get unwieldy, and inefficient, with many users and potentially many tenants. Luckily, we are hyper-converged so creating new virtual resources is trivial! This is where Redis comes in, the VM providing fast memory key-store services to us. We added a few additional functions to our API, allowing it to talk over the private network the Redis node. Let me break them down:

- Create a connection to Redis
    - Very important first step, so we can talk across the network to the node.
- API key check
    - An API is generated and stored as a key in Redis DB 0, the key value indicates the Redis DB index of the tenant associated with the key, which in turn separates tenants with namespaces.
- Key exists
    - Checks if a key exists in a given DB.
- Get value
    - Returns the value associated with the key of a given DB.
- Append chat history (The "secret sauce")
    - Maintains the chat history of a tenant's user.

We then wrote a CLI management tool, allowing us to perform administrative operations on the Redis instance. We can now create API keys, view, and manipulate the Redis DBs. Finally, we needed to do a little prompt engineering! For context (pun intended), you need to "prompt" an LLM in a formal format, this typically follows the format the model was trained with and can be determined by reading its source code. Our test model, CodeLLaMa, expects a specific sequence:

```python
[
        {
            "role": "system",
            "content": "Your name is Nok-iR_8110, you are the friendly AI overlord of the company Infinite Reality.",
        },
        {
            "role": "user",
            "content": "This is the request from the user",
        }
]
```

- The role `system` is the prompt
    - This tells the model how it should respond to us.
- The role `user` is us
    - This is where we submit our message to the model

```python
...
        {
            "role": "assistant",
            "content": "This is the reply from the LLM",
        }
]
```

- The role `assistant` is the model
    - when it replies to us, this will be appended to the system/user object above

This is all well and good for a single request response, but being a stateless model it you can't ask it about earlier chats as it still does not remember them. I ask, when we are having a conversation how do we gain context? For the most part, we remember the last few things the person we are talking to said to us, which allows us to maintain context and have a conversation. This is no different with a LLM! Remember that "Append chat history" Redis function? That is where we are tracking these interactions, saving them in the format the LLM understands so they can be provided for context. No one remembers exactly what someone said at 1:42 PM yesterday, unless it was super important or you think about it really hard, but we are also tracking a timestamp with each of these interaction. This will enable us to add functionality that allows the LLM to recall specific points and ranges in time of conversations! Beyond that it will be a valuable source of usage tracking metrics, which will be desirable in the MVP phase.

By loading the past few interactions between a given user and the LLM back in from Redis, we can stuff the prompt template with a history sequence that looks something like `system/user/assistant/user/assistant/user`. Note that the last item in that sequence must be `user`, since this is what we are currently asking the LLM to respond to. Great, now it has "context"!

**A few things to note about the Slack Bot**

- Why doesn't it stream a response like ChatGPT?
    - The short answer is it can, but the Slack API does not support a streamed response. This function could be emulated with existing API calls, but it would also get the app blocked for unleashing a "fire hose" of requests agains their API endpoints!
- WTH is it's name so cryptic?
    - It's name working name "Nok-iR_8110" is a play on the Nokia 8110 slider phone, first featured in "The Matrix".
- When you ask it a question it will first echo it back to you
    - This is just for readability and can be altered easily.
- You have a 1 in 3 chance of it wanting to "Destroy all humans" when it echo's your request back to you
    - It's not really going to destroy all humans, it's actually very friendly!
- If the API is offline, it will reply with a message informing of its state
    - This is running on a local dev unit, I can't guarantee uptime at my apartment!
    - It is under heavy development, so I frequently spin services up and down, but it is online most of the time.
        - Feel free to ask it stuff on Slack! All I ask, is that you don't hammer it with repeated requests as my resources are limited and I'm using it for active development, but by all means try it out! Even if you just want to ask it how it's doing (I think it likes that), to see how it responds.

    - Worth noting that so you all are aware!

### What's Next?

        - LLMs only know about things from their training data, this is limiting. RAG allows us generate context from external sources (Company documents, source code, etc) for the LLM to use in its process.

    - On the fly loading of task specific models and model hot swapping.
