# 1) Image build (multi-stage)

Create `docker/capacitor-next/Dockerfile`:

```Dockerfile
# docker/capacitor-next/Dockerfile
# Build a small image that embeds the Capacitor Next binary (next-v0.5.0)

FROM debian:bookworm-slim AS builder
ARG CAP_VERSION=next-v0.5.0
RUN apt-get update && apt-get install -y --no-install-recommends \
    ca-certificates wget curl bash && rm -rf /var/lib/apt/lists/*
WORKDIR /work
# The official installer drops a binary named "next" into the CWD
RUN curl -fsSL https://gimlet.io/install-capacitor | bash -s -- ${CAP_VERSION}

# ---
FROM gcr.io/distroless/base-debian12
COPY --from=builder /usr/local/bin/next /usr/local/bin/next
USER 65532:65532
EXPOSE 3333
ENTRYPOINT ["/usr/local/bin/next"]
CMD ["--port","3333","--auth","static"]
```

Optional `.dockerignore` (same folder):

```gitignore
# docker/capacitor-next/.dockerignore
*
!Dockerfile
```

**Build & push** (from repo root):


## 2a) ServiceAccount & RBAC

By default we bind **read-only** (ClusterRole `view`). Change to `admin` if you want full control.

```yaml
# gitops/apps/capacitor-next/sa-rbac.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: capacitor-next
  namespace: flux-system
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: capacitor-next-view
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: view
subjects:
  - kind: ServiceAccount
    name: capacitor-next
    namespace: flux-system
```

> **Why RBAC?** In `auth=static` mode, Capacitor Next serves the UI and proxies requests using the pod’s ServiceAccount. Binding to `view` keeps it safe in a homelab; bump to `edit`/`admin` if you want write actions.

# 1) Create the Secret (SOPS-friendly)

`gitops/apps/capacitor-next/secret-auth.yaml`

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: capacitor-next-auth
  namespace: flux-system
type: Opaque
stringData:
  AUTH: static
  # One user per line: email:bcrypt-hash
  USERS: |
    admin@example.com:$2y$12$REPLACE.ME.REPLACE.ME.REPLACE.ME
    # viewer1@example.com:$2y$12$REPLACE.ME.REPLACE.ME.REPLACE.ME
```

Generate a bcrypt hash (example command you shared):

```bash
htpasswd -bnBC 12 x 'mypassword' | cut -d: -f2
```

Paste the hash(s) into the `USERS:` block (one **email\:hash** per line).
Then encrypt in-place with SOPS (age):

```bash
sops -e -i gitops/apps/capacitor-next/secret-auth.yaml
```

> YAML tip: using a **block scalar** (`|`) avoids any quoting issues with `:` and `$` in bcrypt.

# 3) How to model “admin” vs “view-only” in static mode

In `auth=static`, **every logged-in user ultimately acts with the Deployment’s ServiceAccount RBAC**, since there’s no per-user impersonation. So:

* If you want different privileges, run **two instances**:

  * **Admin UI**: SA bound to `admin` (or a narrow set you choose), Secret has your admin(s).
  * **Viewer UI**: SA bound to `view`, Secret has viewer accounts.
  * Give each a distinct host (e.g., `cap-next.core.home.arpa` and `cap-next-view.core.home.arpa`), or keep the viewer instance internal only.

This keeps RBAC enforcement server-side and avoids relying on just “hiding buttons” in the UI.

If later you want **true per-user RBAC**, switch that instance to the OIDC/impersonation setup we sketched before.

Short answer: **yes**—you can drop `AUTH` and `USERS` from the secret **as long as nothing else reads them**. From the manifests you uploaded, nothing does: your `Deployment` only uses `envFrom` (which blindly injects *all* keys), and your `Ingress` currently has **no** auth annotations—so those two keys aren’t doing anything for you.

Two quick fixes to make this clean and to actually get Basic Auth working:

## 1) Keep only the `auth` key in the Secret (for NGINX)

Your SOPS-encrypted secret can safely be trimmed to just the `auth` key (htpasswd format). Leave the `sops:` block untouched.

```yaml
# gitops/apps/capacitor-next/secret-auth.yaml
apiVersion: v1
kind: Secret
metadata:
  name: capacitor-next-auth
  namespace: flux-system
type: Opaque
stringData:
  auth: |               # htpasswd lines; NGINX expects the key to be literally "auth"
    admin:$2y$05$REDACTEDREDACTEDREDACTED
# (sops block unchanged)
```

## 2) Remove the secret from your Pod env entirely (more secure)

Since the app doesn’t use those creds, stop injecting them into the container:

```diff
# gitops/apps/capacitor-next/deploy.yaml
@@
       containers:
         - name: app
@@
-          envFrom:
-            - secretRef:
-                name: capacitor-next-auth
```

(Leaving the env var there is harmless functionally, but it leaks your htpasswd into the pod’s environment for no reason.)

## 3) Add NGINX Ingress basic-auth annotations

This is why you “don’t see a basic auth flow”: your `Ingress` doesn’t reference the secret yet.

```yaml
# gitops/apps/capacitor-next/ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: capacitor-next
  namespace: flux-system
  annotations:
    nginx.ingress.kubernetes.io/auth-type: basic
    nginx.ingress.kubernetes.io/auth-secret: capacitor-next-auth
    nginx.ingress.kubernetes.io/auth-realm: 'Authentication Required'
spec:
  rules:
    - host: <your.host>
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: capacitor-next
                port:
                  number: 3333
```
