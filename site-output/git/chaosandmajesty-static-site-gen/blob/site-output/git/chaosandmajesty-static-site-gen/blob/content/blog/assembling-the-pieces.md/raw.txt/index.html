  14. ## TLDR;
  15. ​
  16. The “Assembling the Pieces” lab is a miniature red-team engagement. These enriched notes trace the full path captured in the raw journal so you can reproduce it intentionally.
  17. ​
  18. ### External Recon & Entry
  19. ​
  20. - Identify exposed hosts (`MAILSRV1`, `WEBSRV1`) with `nmap -sV -p 25,80,443`. Document banner versions and TLS posture.
  21. - Enumerate WordPress on `WEBSRV1` with `wpscan --enumerate ap,vt --plugins-detection aggressive` ➜ vulnerable plugin leads to file upload RCE.
  22. - Capture web shell callback details (timestamp, source IP, credentials harvested).
  23. ​
  24. ### Establish Internal Foothold
  25. ​
  26. - Pivot through VPN/SSH using stolen credentials; log connection method.
  27. - Run situational awareness: `whoami`, `ipconfig`, `net view`, `arp -a`, `nltest /dclist`.
  28. - Map internal subnets and note interesting services (SQL, SMB shares, RDP gateways).
  29. ​
  30. ### Credential Escalation
  31. ​
  32. - Phish internal user (e.g., `mike`) using crafted email + `.library-ms` payload. Record mail logs and the time of execution.
  33. - Kerberoast service accounts: `Invoke-Kerberoast` ➜ crack `backupuser` password.
  34. - Leverage captured credentials to access `CLIENT75`, dump additional hashes (`mimikatz sekurlsa::logonpasswords`).
  35. ​
  36. ### Lateral Movement & Domain Control
  37. ​
  38. - Relay Net-NTLMv2 to escalate privileges (`ntlmrelayx.py`).
  39. - RDP into `DC01` as `backupuser`, collect domain admin privileges, create shadow copy for data access.
  40. - Document each pivot with proof commands and note cleanup actions (delete payloads, remove scheduled tasks).
  41. ​
  42. ### Reporting Narrative
  43. ​
  44. 1. Initial compromise via WordPress plugin upload.
  45. 2. Credential harvesting through phishing ➜ reuse on internal hosts.
  46. 3. Kerberoast ➜ `backupuser` ➜ domain admin privileges.
  47. 4. Data access via shadow copies and share enumeration.
  48. ​
  49. Pair each step with evidence (hashes, command output, screenshots) and remediation guidance (patch plugin, enforce MFA, monitor Kerberos events, restrict shadow copy permissions).
  50. ​
  51. Module 24 proves whether your process scales. Keep the timeline tight, note decision points, and show defenders exactly how to close the gaps you exploited.

  64. #### 24.1 Enumerating the Public Network
  66. - Enumerate machines on a public network.
  67. - Obtain useful information to use for later attacks.
  68. ​
  69. ##### MAILSRV1
  70. ​
  71. Before starting a pentest we want to setup and structure our environment as we will collect a huge amount of information in due course.
  72. ​
  73. *Structuring and isolating data and settings for multiple penetration tests can be quite the challenge. By reusing a Kali VM we could accidentally expose previous-client data to new networks. Therefore, it is recommended to use a fresh Kali image for every assessment.*
  74. ​
  75. We will create our main directory `/home/$USER/OffSec/beyond` and two sub-directories for each target we currently have access to. We will also create a `creds.txt` file to keep track of valid creds and users.
  76. ​
  77. ```bash
  78. ┌──(operator㉿labhost)-[~/OffSec/beyond]
  79. └─$ tree ../beyond
  80. ../beyond
  81. ├── creds.txt
  82. ├── mailsrv1
  83. └── websrv1
  84. ```
  85. ​
  86. Now that we setup our work env, we are ready to enum our first target MAILSRV1.
  87. ​
  88. *Documenting our findings is a crucial process for every penetration test. For this Module, we'll store results in the basic work environment we just set up. However, Markdown editors, such as Obsidian, have become quite popular for documenting findings and data in real assessments as they are application-independent and contain functions that will simplify report writing and collaboration.*
  89. ​
  90. Start with a portscan of MAILSRV1 using Nmap, this is often the first active info gathering method we perform to get an overview of ports/services accessible to us.
  91. ​
  92. *In a real penetration test, we would also use passive information gathering techniques such as Google Dorks and leaked password databases to obtain additional information. This would potentially provide us with usernames, passwords, and sensitive information.*
  93. ​

  258. WordPress plugins and themes, often written by the community, often feature improperly patched vulnerabilities or ones that are simply never fixed. This makes themes and plugins a prime target.
  259. ​

  264. - Plugin detection `aggressive`
  265. - Enum popular plugins `--enumerate p`
  266. - Output file `-o`
