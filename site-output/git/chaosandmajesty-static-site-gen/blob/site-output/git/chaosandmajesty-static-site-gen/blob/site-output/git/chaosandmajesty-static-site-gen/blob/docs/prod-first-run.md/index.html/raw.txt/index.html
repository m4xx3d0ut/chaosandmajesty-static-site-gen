  14. <h1>Prod Deployment – Initial VPS Bring-Up</h1>
  15. <p>This runbook walks through preparing the Linode VPS (<code>chaosandmajesty.com</code>) for the
  16. containerised Chaos &amp; Majesty site, performing the first Ansible-driven release,
  17. and validating the Gitea workflow.</p>
  18. <blockquote>
  19. <p><strong>Scope:</strong> host runs Docker, deploys https via the containerised Nginx, keeps the
  20. existing <code>/var/www/html/dav</code> WebDAV share, and reuses the Let&#39;s Encrypt material
  21. already managed on the VPS.</p>
  22. </blockquote>
  23. <h2>1. Prerequisites</h2>
  24. <ul>
  25. <li>Docker Engine + Compose plugin installed on the VPS (<code>docker --version</code>,
  26. <code>docker compose version</code>).</li>
  27. <li><code>deploy</code> user created, part of the <code>docker</code> group, with your CI/public key in
  28. <code>~deploy/.ssh/authorized_keys</code> (already completed).</li>
  29. <li>Existing certificates under <code>/etc/letsencrypt/</code> (Certbot-managed).</li>
  30. <li>Gitea runner with Docker access (self-hosted) – required for the workflow.</li>
  31. <li>Secrets staged in the repository settings (see §4).</li>
  32. </ul>
  33. <h2>2. One-Time VPS Preparation</h2>
  34. <p>Login as root (or a sudoer) and run:</p>
  35. <pre><code class="language-bash"># ensure runtime directories exist
  36. install -d -o deploy -g deploy -m 755 /opt/chaosandmajesty
  37. install -d -o root -g root -m 755 /var/www/letsencrypt
  38. install -d -o root -g root -m 755 /var/www/letsencrypt/.well-known/acme-challenge
  39. install -d -o root -g root -m 775 /var/www/html/dav
  40. install -d -o deploy -g deploy -m 700 ~deploy/.ssh
  41. cat &lt;&lt;&#39;PUBKEY&#39; &gt;&gt; ~deploy/.ssh/authorized_keys
  42. ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIGbN0ZidnAYvD7hMBZV/sdvFg9S1iHK/ExBgCHCClMgw gitea-ci-deploy (prod)
  43. PUBKEY
  44. chmod 600 ~deploy/.ssh/authorized_keys
  45. ​
  46. # confirm Docker permissions for deploy user (newgrp required for current session)
  47. id deploy
  48. </code></pre>
  49. <p>Append the CI user&#39;s public key to <code>~deploy/.ssh/authorized_keys</code> if you
  50. haven&#39;t already (replace <code>&lt;deploy-public-key&gt;</code> in the snippet above), then
  51. <code>chmod 600</code> the file.</p>
  52. <blockquote>
  53. <p>Renewal tip: keep your existing Certbot cron/systemd timer. If it uses the
  54. webroot plugin, point it at <code>/var/www/letsencrypt</code> so challenges land in the
  55. mounted directory (<code>certbot renew --webroot -w /var/www/letsencrypt</code>).</p>
  56. </blockquote>
  57. <h3>SSH Known Hosts</h3>
  58. <p>From the CI runner (or your workstation), prime the known_hosts entry so
  59. Ansible/SSH skip the prompt:</p>
  60. <pre><code class="language-bash">ssh-keyscan -H chaosandmajesty.com &gt;&gt; ~/.ssh/known_hosts
  61. </code></pre>
  62. <p>Paste this output into the <code>KNOWN_HOSTS</code> secret if you prefer the workflow to
  63. skip dynamic key scanning.</p>
  64. <h2>3. Dry-Run the Playbook Locally (optional but recommended)</h2>
  65. <p>From this repository on your workstation:</p>
  66. <pre><code class="language-bash">ansible-galaxy collection install -r ansible/requirements.yml
  67. export ANSIBLE_HOST_KEY_CHECKING=false # or manage known_hosts as above
  68. ansible-playbook -i ansible/inventory/hosts.ini ansible/deploy.yml \
  69. -e &quot;registry_username=${REGISTRY_USERNAME}&quot; \
  70. -e &quot;registry_password=${REGISTRY_PASSWORD}&quot; \
  71. --check
  72. </code></pre>
  73. <p>Use <code>--check</code> for a read-only preview; drop it for the actual deployment once the
  74. workflow succeeds.</p>
  75. <h2>4. Configure Gitea Secrets</h2>
  76. <p>Populate these secrets in <strong>Repository → Settings → Secrets → Actions</strong> before
  77. pushing to <code>prod</code>. Create or update each entry individually so you can test the
  78. workflow as you go.</p>
  79. <h3>Pick a public registry</h3>
  80. <p>The prod workflow runs on a VPS that cannot reach your lab-only registry
  81. (<code>reg.microk8s.core.home.arpa:32000</code>). Push your production image to a public
  82. registry instead. Any of the following work well:</p>
  83. <ul>
  84. <li><strong>GitHub Container Registry (GHCR)</strong> – Anonymous pulls allowed, currently no
  85. storage or bandwidth fees for public images. Uses <code>ghcr.io/&lt;owner&gt;/&lt;image&gt;</code>.
  86. Docs: <a href="https://docs.github.com/packages/working-with-a-github-packages-registry/working-with-the-container-registry">https://docs.github.com/packages/working-with-a-github-packages-registry/working-with-the-container-registry</a></li>
  87. <li><strong>Docker Hub</strong> – Widely supported; anonymous pulls are rate limited for free
  88. plans. Docs: <a href="https://docs.docker.com/docker-hub/usage/pulls/">https://docs.docker.com/docker-hub/usage/pulls/</a></li>
  89. <li><strong>GitLab Container Registry</strong> – Good fit if you already have GitLab tooling
  90. in place. Docs: <a href="https://docs.gitlab.com/user/packages/container_registry/">https://docs.gitlab.com/user/packages/container_registry/</a></li>
  91. <li><strong>Quay.io</strong> – Mature hosted registry with strong org features. Docs:
  92. <a href="https://www.redhat.com/en/technologies/cloud-computing/quay">https://www.redhat.com/en/technologies/cloud-computing/quay</a></li>
  93. <li><strong>Amazon ECR Public</strong> – CDN-backed distribution and generous public tiers for
  94. high-traffic images. Docs: <a href="https://aws.amazon.com/ecr/public/">https://aws.amazon.com/ecr/public/</a></li>
  95. </ul>
  96. <p>For this project, GHCR is usually the smoothest option: your runner already has
  97. internet access, the CI only pushes on release, and the VPS pulls occasionally,
  98. so the anonymous pull policy is more than enough.</p>
  99. <h3>Secret checklist</h3>
  100. <ol>
  101. <li><strong><code>REGISTRY_HOST</code></strong> – Hostname of your container registry. For GitHub
  102. Container Registry use <code>ghcr.io</code>; for Gitea Container Registry use the
  103. domain of your instance (e.g. <code>gitea.chaosandmajesty.com</code>). This must be
  104. reachable from the public VPS — unlike the dev workflow’s
  105. <code>reg.microk8s.core.home.arpa:32000</code> NodePort, which lives only on the lab
  106. network.</li>
  107. <li><strong><code>REGISTRY_NAMESPACE</code></strong> – Namespace/owner portion of the image path. For
  108. GHCR this matches your GitHub user/org (e.g. <code>chaosandmajesty</code>). Leave blank
  109. only if the registry expects images at the root.</li>
  110. <li><strong><code>IMAGE_NAME</code></strong> – Repository name portion of the image path (for example
  111. <code>cm-site</code>). The workflow tags every prod deploy with <code>prod</code> and
  112. <code>prod-&lt;sha&gt;</code>.</li>
  113. <li><strong><code>REGISTRY_USERNAME</code> / <code>REGISTRY_PASSWORD</code></strong> – Credentials with push
  114. permission to the registry. For GHCR create a fine-grained PAT with <code>read</code>
  115. and <code>write:packages</code> scopes. For self-hosted registries, use a robot/service
  116. account. Paste the username as-is; paste the token/password exactly, without
  117. extra whitespace.</li>
  118. <li><strong><code>VPS_HOST</code></strong> – Public hostname or IP for the VPS. Use
  119. <code>chaosandmajesty.com</code> unless you are targeting a different environment.</li>
  120. <li><strong><code>VPS_USER</code></strong> – SSH username the playbook uses. This repository assumes the
  121. <code>deploy</code> user exists and has passwordless sudo for the managed services.</li>
  122. <li><strong><code>SSH_PRIVATE_KEY</code></strong> – Private key that matches the public key installed on
  123. the <code>deploy</code> account. Copy the key contents (including the <code>-----BEGIN</code> and
  124. <code>-----END</code> lines) directly into the secret. Ensure the key is not protected
  125. by a passphrase; the workflow cannot prompt for one.</li>
  126. <li><strong><code>KNOWN_HOSTS</code></strong> <em>(optional)</em> – Pre-seeded line from <code>ssh-keyscan -H chaosandmajesty.com</code>. Run the command locally and paste the output to avoid
  127. first-connection prompts. If omitted, the workflow will scan the host at
  128. runtime.</li>
  129. </ol>
  130. <p>After saving each secret, use the <strong>Test secret</strong> button (if available in your
  131. Gitea version) or re-run the <code>prod</code> workflow to confirm the value is
  132. accessible.</p>
  133. <h3>Example: wiring GHCR</h3>
  134. <ol>
  135. <li>Create a GitHub Personal Access Token with <code>write:packages</code> and
  136. <code>read:packages</code> scopes (classic PAT) or a fine-grained token scoped to your
  137. container packages.</li>
  138. <li>Populate the secrets above with:<ul>
  139. <li><code>REGISTRY_HOST=ghcr.io</code></li>
  140. <li><code>REGISTRY_NAMESPACE=&lt;your GitHub username or org&gt;</code></li>
  141. <li><code>IMAGE_NAME=cm-site</code> (or your preferred image name)</li>
  142. <li><code>REGISTRY_USERNAME=&lt;same GitHub account&gt;</code></li>
  143. <li><code>REGISTRY_PASSWORD=&lt;the PAT&gt;</code></li>
  144. </ul>
  145. </li>
  146. <li>Push to <code>prod</code>; the workflow logs in to GHCR, builds, and tags:<ul>
  147. <li><code>${REGISTRY_HOST}/${REGISTRY_NAMESPACE}/${IMAGE_NAME}:prod</code></li>
  148. <li><code>${REGISTRY_HOST}/${REGISTRY_NAMESPACE}/${IMAGE_NAME}:prod-&lt;short-sha&gt;</code></li>
  149. </ul>
  150. </li>
  151. </ol>
  152. <p>Skip GHCR only if you need extremely high anonymous throughput with regional
  153. mirrors—in that case consider Amazon ECR Public and adjust the secrets to match
  154. its host, namespace, and credentials.</p>
  155. <h2>5. First Managed Deployment</h2>
  156. <ol>
  157. <li><p>Commit the latest CI/CD and Ansible changes to <code>prod</code> (merge from <code>main</code>).</p>
  158. </li>
  159. <li><p>Push to <code>prod</code>; the workflow <code>.github/workflows/prod-deploy.yml</code> triggers.</p>
  160. </li>
  161. <li><p>Monitor the job in Gitea – it should:</p>
  162. <ul>
  163. <li>install dependencies &amp; run <code>./build-site.sh</code></li>
  164. <li>build &amp; push <code>prod</code> and <code>prod-&lt;sha&gt;</code> tags</li>
  165. <li>stop the host <code>nginx</code> service via Ansible</li>
  166. <li>render <code>/opt/chaosandmajesty/docker-compose.yml</code></li>
  167. <li>start the container exposing 80/443 and mount <code>/var/www/html/dav</code>,
  168. <code>/etc/letsencrypt</code>, <code>/var/www/letsencrypt</code></li>
  169. <li>probe <code>http://127.0.0.1:80/health</code></li>
  170. </ul>
  171. </li>
  172. <li><p>Validate on the VPS:</p>
  173. </li>
  174. </ol>
  175. <pre><code class="language-bash">sudo systemctl status nginx # should be inactive
  176. sudo docker ps # cm_site container up
  177. sudo docker logs cm-prod # optional – confirm no TLS errors
  178. curl -kI https://chaosandmajesty.com/health
  179. </code></pre>
  180. <ol start="5">
  181. <li>Validate WebDAV: ensure <code>/var/www/html/dav</code> contents are still present and
  182. reachable from your Joplin client.</li>
  183. <li>If you relied on non-www subdomains previously handled by the host nginx,
  184. extend <code>nginx/default.conf</code> and redeploy to add the necessary proxy blocks.</li>
  185. </ol>
  186. <h2>6. Troubleshooting &amp; Rollback</h2>
  187. <ul>
  188. <li>To revert quickly, re-enable the system nginx service:
  189. <code>sudo systemctl enable --now nginx</code>.</li>
  190. <li>Redeploy the previous container tag:
  191. <code>docker compose -f /opt/chaosandmajesty/docker-compose.yml up -d</code> after editing
  192. <code>.current-image</code> with the prior tag (or run the playbook with <code>image_tag=prod-&lt;sha&gt;</code>).</li>
  193. <li>Health check failures usually indicate certificate mount/permissions or WebDAV
  194. temp directory issues – inspect <code>docker logs cm-prod</code> and
  195. <code>/opt/chaosandmajesty/docker-compose.yml</code>.</li>
  196. </ul>
  197. <p>With the first deployment complete, future pushes to <code>prod</code> should cycle through
  198. image build, push, and automated rollout without manual intervention.</p>
