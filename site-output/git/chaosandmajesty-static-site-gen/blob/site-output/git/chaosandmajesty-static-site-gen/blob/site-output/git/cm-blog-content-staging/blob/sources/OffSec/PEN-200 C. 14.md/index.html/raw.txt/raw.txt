<h2>14.1 Antivirus Software Key Components and Operations</h2>

<h3>Known vs Unknown Threats</h3>
<p>Originally AV was based on signatures.  Signature languages are unique to each AV engine.  The signature languages vary, on one engine the signature may analyze the malware&#39;s signature on disk where another may analyze it&#39;s network traffic.</p>
<p>In 2014 a sig language called YARA was open-sourced, allowing researchers to query the VirusTotal platform, even integrating their own signatures into AV products.</p>
<ul>
<li>VirusTotal is an AV search engine<ul>
<li>search known malware</li>
<li>submit samples and test against known</li>
</ul>
</li>
</ul>
<p>Signatures are written based on known threats, initially AV could only detect malware that had already been documented.  Modern AV, including Win Defender, integrate a Machine Learning engine that is called whenever an unknown file is discovered on the system.  ML Engines, operate in the cloud, and require an internet connection, which is often not an option on internal enterprise servers.  AV engines should not borrow too much resource from the system.</p>
<p>To overcome the limits, Endpoint Detection and Response (EDR) have been evolving.  The EDR generates security event telemetry and forwards it to the SIEM.  The SIEM is monitored by teams of analysts, giving them a full overview of the org, any past or ongoing attack.</p>
<p>AV and EDR are not mutually exclusive, they compliment each other.  Their deployment is based on internal network arch.</p>
<h3>AV Engines and Components</h3>
<p>Modern AV relies on signature updates, retrieved from the vendor&#39;s DB, over the internet.  The signatures are stored in a local sig DB, where they are utilized by the engine components;</p>
<ul>
<li>File Engine<ul>
<li>responsible for scheduled and real-time file scans<ul>
<li>scheduled scan<ul>
<li>parses the entire file system, sending each files metadata to the sig engine</li>
</ul>
</li>
<li>real-time<ul>
<li>detecting and possibly reacting to any new file action, i.e. downloading malware from a website</li>
<li>IDs events a the kernel level via special mini-filter driver<ul>
<li>This is why modern AV operates in Kernel and User land to validate the entire OS scope</li>
</ul>
</li>
</ul>
</li>
</ul>
</li>
</ul>
</li>
<li>Memory Engine<ul>
<li>Inspects each processes mem space at runtime for well-known binary sigs and suspicious API call that may result in mem injection attacks</li>
</ul>
</li>
<li>Network Engine<ul>
<li>inspects incoming and outgoing network traffic on the local net iface</li>
<li>when a sig is matched, the net eng may attempt to block malware from comm with it&#39;s C2 server</li>
</ul>
</li>
<li>Disassembler<ul>
<li>translates machine code into asm</li>
<li>reconstructing the original code section</li>
<li>IDs encode/decode routines</li>
</ul>
</li>
<li>Emulator/Sandbox<ul>
<li>Isolate and load malware for analysis<ul>
<li>once loaded and running in the emulated sandbox it is thoroughly analyzed against known sigs</li>
</ul>
</li>
</ul>
</li>
<li>Browser Plugin<ul>
<li>browsers are protected by a sandbox, modern AV uses browser plugins to get visibility and detect mal content exec in browser</li>
</ul>
</li>
<li>Machine Learning Engine<ul>
<li>vital part of modern AV, enables the detection of unknown threats by relying on cloud enhanced computing resources</li>
</ul>
</li>
</ul>
<p>These engines work in concert with the sig DB to rank events as benign, malicious, or unknown.</p>
<h3>Detection Methods</h3>
<p>AV sig syntax and scope differs based on the engine they are built for, but serve the same purpose.  Detection methodologies;</p>
<ul>
<li>Signature-based Detection<ul>
<li>restricted list technology</li>
<li>scans for known sigs</li>
<li>sigs can be a file hash, set of patterns, specific binary vals and strings belonging to each specific malware</li>
<li>Weak method, changing a single bit results in a completely diff hash</li>
</ul>
</li>
<li><a href="https://en.wikipedia.org/wiki/Heuristic_analysis">Heuristic-based Detection</a><ul>
<li>relies on rules and algorithms to make determination</li>
<li>steps through instruction set of binary file or decompile/analyze the source code to map the program.</li>
</ul>
</li>
<li><a href="https://pdfs.semanticscholar.org/08ec/24106e9218c3a65bc3e16dd88dea2693e933.pdf">Behavioral Detection</a><ul>
<li>dynamically analyzes the the behavior of a binary file </li>
<li>achieved by exec in sandbox and searching for behavior considered malicious</li>
</ul>
</li>
<li><a href="https://i.blackhat.com/us-18/Thu-August-9/us-18-Parikh-Protecting-the-Protector-Hardening-Machine-Learning-Defenses-Against-Adversarial-Attacks.pdf">Machine Learning Detection</a><ul>
<li>uses ML algorithms to detect unknown threats</li>
<li>collects and analyzes metadata</li>
<li>Example; Win Defender has 2 ML components<ul>
<li>client ML engine<ul>
<li>creates ML models and heuristics</li>
</ul>
</li>
<li>cloud ML engine<ul>
<li>analyze submitted samples against cloud DB of metadata based models of other submitted samples</li>
<li>When client ML is unable to determine benign or not, it passes it to the cloud ML for final response</li>
<li>Doesn&#39;t require sigs and can detect unknown threats</li>
<li>methods differ by AV vendor and results differ as well</li>
</ul>
</li>
</ul>
</li>
</ul>
</li>
</ul>
<p>To demonstrate this, we will scan a Metasploit payload.  Using Msfvenom we will generate a standard Win PE containing our payload, a simple TCP rev shell.
<em>The PE file format is used on Windows operating systems for executable and object files. The PE format represents a Windows data structure that details the information necessary for the Windows Loader7 to manage the wrapped executable code including required dynamic libraries, API import and export tables, etc.</em></p>
<p>Before generating a payload, make sure Kali and MSF are up to date.  MSF is updated frequently and AV sigs change as well.  The intrinsic delay in AV sign updates may give a fresh version of MSF an edge against stale AV sigs during a pentest.</p>

<h2>14.1 Bypassing Antivirus Detections</h2>

<h3>On-Disk Evasion</h3>
<ul>
<li>Modern malware obfuscation takes many forms</li>
<li>one of the earliest methods is the use of <a href="https://en.wikipedia.org/wiki/Executable_compression">packers</a><ul>
<li>designed to reduce size of executable</li>
<li>generate an exe that is smaller, functionally equivalent, with a new binary structure</li>
<li>Has a new hash sig and can bypass older AV methods based on file sig</li>
<li>Modern malware uses variations, <a href="https://upx.github.io/">UPX</a> and other packers alone are not enough to evade modern AV</li>
</ul>
</li>
<li>Obfuscators<ul>
<li>mutate code making it harder to reverse-engineer</li>
<li>replaces instructions with semantic equiv</li>
<li>insert <a href="https://en.wikipedia.org/wiki/Dead_code">dead code</a></li>
<li>split/reorder funcs</li>
<li>primarily used by software developers to protect their IP</li>
<li>marginally effective against sig based AV methods</li>
<li>modern obfuscators have runtime in-mem capabilities, hinder AV detection further</li>
</ul>
</li>
<li>Crypter<ul>
<li>cryptographically alters exe</li>
<li>adds decrypt stub that restore OG code on exec</li>
<li>decrypt happends in mem, leaving encrypted code on disk</li>
<li>foundational in modern malware as one of the most effective evasion techniques</li>
</ul>
</li>
</ul>
<p>Effective evasion requires a combination of techniques and more advanced methods;</p>
<ul>
<li>anti-reversing</li>
<li>anti-debugging</li>
<li>VM emulation detection</li>
<li>Software protectors<ul>
<li>designed for legit purposes, but can be used to bypass AV</li>
</ul>
</li>
</ul>
<p>There are several actively-maintained free tools that provide adequate AV evasion.  Commercial tools, such as <a href="http://www.enigmaprotector.com/en/home.html">The Enigma Protector</a>, can bypass many AV products.</p>
<h3>In-Memory Evasion</h3>
<ul>
<li><a href="https://www.endgame.com/blog/technical-blog/ten-process-injection-techniques-technical-survey-common-and-trending-process">In-Memory Injections</a><ul>
<li>aka PE Injection</li>
<li>popular technique for bypassing AV on Win</li>
<li>focuses on manipulation of volatile mem</li>
<li>does not write to disk<ul>
<li>common focus of most AV solutions</li>
</ul>
</li>
</ul>
</li>
<li><a href="https://blog.f-secure.com/memory-injection-like-a-boss/">Several evasion techniques</a> do not write to disk</li>
<li>Remote Process Memory Injection<ul>
<li>injects payload into a benign PE</li>
<li>common method leverages <a href="https://en.wikipedia.org/wiki/Windows_API">Win APIs</a></li>
<li>To achieve;<ul>
<li><a href="https://docs.microsoft.com/en-us/windows/desktop/api/processthreadsapi/nf-processthreadsapi-openprocess">OpenProcess</a><ul>
<li>obtain valid <a href="https://en.wikipedia.org/wiki/Handle_(computing)">HANDLE</a> of target process</li>
</ul>
</li>
<li>Allocate mem in the context of that process by calling WIN API such as;<ul>
<li><a href="https://docs.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualallocex">VirtualAllocEx</a></li>
</ul>
</li>
<li>Copy payload into alloc mem<ul>
<li><a href="https://docs.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-writeprocessmemory">WriteProcessMemory</a></li>
</ul>
</li>
<li>Exec in mem<ul>
<li><a href="https://docs.microsoft.com/en-us/windows/desktop/api/processthreadsapi/nf-processthreadsapi-createremotethread">CreateRemoteThread</a></li>
</ul>
</li>
</ul>
</li>
<li>Though complex, Powershell can do the heavy lifting in most cases</li>
</ul>
</li>
<li>Reflective DLL Injection<ul>
<li>Unlike regular DLL injection, where the DLL is loaded from disk using the LoadLibrary API, this method attempts to load a DLL stored by the attacker in process memory<ul>
<li>challenge being LoadLibrary does not support loading a DLL from memory<ul>
<li>Win also does not expose and API that can handle this</li>
</ul>
</li>
<li>Attacker must write their own version of the API that does not require disk based DLL loading</li>
</ul>
</li>
</ul>
</li>
<li>Process Hollowing<ul>
<li>FIrst launch a benign process in a suspended state</li>
<li>Once launched, the image of the proc is removed from mem and replaced with mal exec image</li>
<li>Finally, process is resumed and mal code is executed in place of legit proc</li>
</ul>
</li>
<li>Inline Hooking<ul>
<li>modify memory to introduce a hook (instruction redirecting code for exec)</li>
<li>upon redirection and exec of mal code the the flow returns back to the modified func appearing as only the legit code had executed</li>
<li>Often employed by rootkits<ul>
<li>stealthy malware, provide author with persistent dedicated access to the target system</li>
<li>modifies system components in;<ul>
<li>user space</li>
<li>kernel</li>
<li>lower OS protection rings<ul>
<li>boot</li>
<li>hypervisor</li>
</ul>
</li>
</ul>
</li>
<li>Need admin privs<ul>
<li>often installed from an elevated shell or by privesc</li>
</ul>
</li>
</ul>
</li>
</ul>
</li>
</ul>

<h3>Testing for AV Evasion</h3>
<p>SecOps; joint collab between enterprise IT and SOC, goal is to provide continuous detection/protection against well-known and novel threats.  As a pentester you have to have an understanding of the implications dealing with SecOps teams.</p>
<p>Example;</p>
<ul>
<li>VirusTotal can give us an idea of how stealthy our malware is</li>
<li>The platform sends all samples to AV vendors subscribed to their platform<ul>
<li>Therefore shortly after submitting a sample, AV vendors can run the mal in their sandbox and ML engines to build detection sigs</li>
<li>Rendering the mal unusable</li>
</ul>
</li>
<li><a href="https://antiscan.me/">AntiScan.Me</a> scans against 30 diff AV engines and claims to not divulge samples to 3rd parties<ul>
<li>This is a last resort when we don&#39;t know the target&#39;s AV vendor</li>
</ul>
</li>
<li>If we know the target&#39;s AV vendor<ul>
<li>we should build a VM similar to the target env</li>
</ul>
</li>
</ul>
<p>Regardless of AV product we are testing, we should disable sample submission to prevent the same drawback as virus total.  In Win Defender;</p>
<ul>
<li>Windows Security</li>
<li>Virus &amp; Thread Protection</li>
<li>Manage Settings<ul>
<li>Deselect automatic sample submission</li>
<li>Only enable it when we are confident in our bypass method and if the target has it enabled in their env</li>
<li><em>Since both Windows Defender cloud protection and automatic sample submission require internet connectivity, we should first verify that this is reflected in our target environment: some company policies mandate limited internet access to some production servers and as a consequence, some advanced AV features are inhibited.</em></li>
</ul>
</li>
</ul>
<p>As a rule of thumb, always prefer custom code when developing bypasses.  AV signatures are extrapolated from the malware sample, the more novel the code, the lower the likelihood of detection.</p>
<h3>Evading AV with Thread Injection</h3>
<p>Finding a universal solution to bypass all AV engine is difficult, time consuming, and possibly impossible.  It is far more effective to target the specific AV solution deployed by the target.</p>
<p>In our examples, we will interact with <em>Avira Free Security version 1.1.68.29553</em> on a Win 11 client.  As a first step in working with AV, make sure the system is working as intended by testing it with the basic Msfvenom PE we created earlier.  </p>
<p>Depending on how restricted the target env is, we may be able to bypass the AV product with PowerShell.  This example will utilize the <strong>remote process memory injection</strong> technique, similar to what we described previously, but we will target the currently executing process (x86 PowerShell interpreter).</p>
<p>PowerShell can interact with the <a href="https://blogs.technet.microsoft.com/heyscriptingguy/2013/06/25/use-powershell-to-interact-with-the-windows-api-part-1/">Windows API</a>, allowing us to implement in-memory injection using a PowerShell script.  It&#39;s harder for AV to determine if a script is malicious compared to a PE, the script itself is not exec code and runs in the interpreter.  AV solutions handle mal script detection with varying degrees of success.</p>
<p>In the event the script is marked as mal, it can be easily altered.  AV will often review the variable names, comments, and logic which can be altered without the need to recompile.</p>
<p>To demonstrate, we will analyze a well-known version of a memory injection PowerShell script and test it against it with Avira.  The basic template for memory injection;</p>
<pre><code>$code = &#39;

[DllImport(&quot;msvcrt.dll&quot;)]
public static extern IntPtr memset(IntPtr dest, uint src, uint count);&#39;;

$winFunc = 
  Add-Type -memberDefinition $code -Name &quot;Win32&quot; -namespace Win32Functions -passthru;

[Byte[]];
[Byte[]]$sc = &lt;place your shellcode here&gt;;

$size = 0x1000;

if ($sc.Length -gt 0x1000) {$size = $sc.Length};

$x = $winFunc::VirtualAlloc(0,$size,0x3000,0x40);

for ($i=0;$i -le ($sc.Length-1);$i++) {$winFunc::memset([IntPtr]($x.ToInt32()+$i), $sc[$i], 1)};

$winFunc::CreateThread(0,0,$x,0,0,0);for (;;) { Start-sleep 60 };
