<h1>Service Level Indicators &amp; Service Level Objectives</h1>
<p>SLIs, SLOs and SLAs aren’t just useful abstractions. Without them you cannot know if your system is reliable, available, or even useful. If they don’t tie explicitly back to your business objectives then you have no idea if the choices you make are helping or hurting your business. You also can’t make honest promises to your customers.  If you’re building a system from scratch, make sure that SLIs, SLOs and SLAs are part of your system requirements. If you already have a production system but don’t have them clearly defined then that’s your highest priority work.</p>
<ul>
<li>If you want to have a reliable service, you must first define “reliability.” In most cases that actually translates to availability.</li>
<li>If you want to know how reliable your service is, you must be able to measure the rates of successful and unsuccessful queries; these will form the basis of your SLIs.</li>
<li>The more reliable the service, the more it costs to operate. Define the lowest level of reliability that you can get away with, and state that as your Service Level Objective (SLO).</li>
<li>Without an SLO, your team and your stakeholders cannot make principled judgements about whether your service needs to be made more reliable (increasing cost and slowing development) or less reliable (allowing greater velocity of development).</li>
<li>If you’re charging your customers money you&#39;ll probably need an SLA, and it should be a little bit looser than your SLO.</li>
</ul>

<h2>SLI Equation</h2>
<p><code>SLI = (good events / valid events) * 100%</code></p>
<ol>
<li>SLIs fall between 0% and 100%.
0% means nothing works, 100% means nothing is broken.
This scale is intuitive and directly translates to percentagereliability SLOs and error budgets.</li>
<li>SLIs have a consistent format.
Consistency allows common tooling to be built around SLIs.
Alerting logic, error budget calculations, and SLO analysis
and reporting tools can all be written to expect the same
inputs: good events, valid events, and an SLO threshold.</li>
</ol>
<p>Events can be prevented from counting against an error budget either by
including them in the numerator or by excluding them from the denominator. The former is achieved by classifying some events good, the
latter by classifying some events invalid.</p>

<h2>SLI Types</h2>
<h3>Availability</h3>
<h4>Request / Response</h4>
<p>The proportion of valid requests served successfully.</p>
<p>What requests this system serves are valid for the SLI?
What makes a response successful?</p>
<h3>Latency</h3>
<h4>Request / Response</h4>
<p>The proportion of valid requests served faster than a threshold.</p>
<p>What requests this system serves are valid for the SLI?
When does the timer measuring the request latency start and stop?</p>
<h3>Quality</h3>
<h4>Request / Response</h4>
<p>The proportion of valid requests served without degrading quality.</p>
<p>What requests this system serves are valid for the SLI?
How to determine whether the response was served with degraded quality?</p>
<h3>Freshness</h3>
<h4>Data Processing</h4>
<p>The proportion of valid data updated more recently than a threshold.</p>
<p>What data this system processes are valid for the SLI?
When does the timer measuring the freshness of data start and stop?</p>
<h3>Coverage</h3>
<h4>Data Processing</h4>
<p>The proportion of valid data processed successfully.</p>
<p>What data this system processes are valid for the SLI?
How to determine whether the processing of a particular piece of data was successful?</p>
<h3>Correctness</h3>
<h4>Data Processing</h4>
<p>The proportion of valid data producing correct output.</p>
<p>What data this system processes are valid for the SLI?
How to determine the correctness of output records?</p>
<h3>Throughput</h3>
<h4>Data Processing</h4>
<p>The proportion of time where the data processing rate is faster than a threshold.</p>
<p>What is the units of measurement for your data processing rate?</p>

<h2>Example SLO</h2>
<br>

<p><strong>User Journey:</strong> Home Page Load</p>
<p><strong>SLI Type:</strong> Latency</p>
<p><strong>SLI Specification:</strong></p>
<ul>
<li>Proportion of home page requests served in &lt; 100ms<ul>
<li>SLI equation; <code>Requests served in &lt; 100ms / Requests</code></li>
</ul>
</li>
</ul>
<p><strong>SLI Implementations:</strong></p>
<ul>
<li>Proportion of home page requests served in &lt; 100ms<ul>
<li>Measured from server log request latency values<ul>
<li>This will miss requests that don&#39;t reach the backend</li>
</ul>
</li>
</ul>
</li>
<li>Proportion of home page requests served in &lt; 100ms<ul>
<li>Measured by probe executing JS in VM browser<ul>
<li>This will catch errors when requests cannot reach our network, but may miss issues affecting a subset of users</li>
</ul>
</li>
</ul>
</li>
</ul>
<p><strong>SLO:</strong>
99% of home page request in the past 28 days served in &lt; 100ms.</p>
