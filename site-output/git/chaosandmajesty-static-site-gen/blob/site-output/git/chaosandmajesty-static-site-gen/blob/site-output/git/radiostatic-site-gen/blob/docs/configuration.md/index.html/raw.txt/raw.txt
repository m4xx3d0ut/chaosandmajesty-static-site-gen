        <h1>Configuration Reference</h1>
<p>Use this document to map YAML keys to the templates and behaviours produced by RadioStatic. The examples below mirror the bundled demo (<code>smoke-test.yaml</code>).</p>
<h2>Top-Level Keys</h2>
<table>
<thead>
<tr>
<th>Key</th>
<th>Purpose</th>
</tr>
</thead>
<tbody><tr>
<td><code>title</code></td>
<td>Default site title. Rendered in the <code>&lt;title&gt;</code> tag alongside the page title.</td>
</tr>
<tr>
<td><code>description</code></td>
<td>Plain-text description used in meta tags.</td>
</tr>
<tr>
<td><code>assets</code></td>
<td>Folder containing CSS, JS, images, and metadata files. Copied verbatim to the output.</td>
</tr>
<tr>
<td><code>templates</code></td>
<td>Directory of EJS templates. Defaults to <code>static-sitegen/templates/</code>.</td>
</tr>
<tr>
<td><code>styles</code></td>
<td>Array of CSS paths (relative to the generated HTML). <code>assets/modern.css</code> is auto-added.</td>
</tr>
<tr>
<td><code>extraCopies</code></td>
<td>Array of <code>{from, to}</code> entries for copying additional directories into the output.</td>
</tr>
<tr>
<td><code>theme</code></td>
<td>Object with <code>mode</code>, <code>primary_color</code>, <code>secondary_color</code>. Consumed by templates as CSS variables.</td>
</tr>
<tr>
<td><code>logo</code></td>
<td>Path to the logo image displayed in the header.</td>
</tr>
<tr>
<td><code>favicon</code></td>
<td>Optional favicon path. Falls back to the logo when omitted.</td>
</tr>
<tr>
<td><code>meta</code></td>
<td><code>description</code> and <code>keywords</code> fields override the default meta tags per page.</td>
</tr>
<tr>
<td><code>social_preview_image</code></td>
<td>Path to an image used for social sharing metadata.</td>
</tr>
<tr>
<td><code>analytics_id</code></td>
<td>Placeholder for analytics tooling. Included in templates for future extensions.</td>
</tr>
</tbody></table>
<h2>Terminal Console Options</h2>
<p>To enable the terminal-style hero on a page, set the following keys either at the site level or per page/section:</p>
<table>
<thead>
<tr>
<th>Key</th>
<th>Description</th>
</tr>
</thead>
<tbody><tr>
<td><code>useCmHead</code></td>
<td>Includes <code>partials/cm-head.ejs</code>. Loads fonts, console CSS, and <code>terminal-console.js</code>.</td>
</tr>
<tr>
<td><code>useCmConsole</code></td>
<td>Injects the console markup (<code>partials/cm-console.ejs</code>).</td>
</tr>
<tr>
<td><code>cmTitle</code></td>
<td>Heading displayed above the console.</td>
</tr>
<tr>
<td><code>cmTagline</code></td>
<td>Subheading displayed under the heading.</td>
</tr>
<tr>
<td><code>cmImage</code></td>
<td>Optional illustration rendered above the console (e.g., <code>assets/static/img/site-icon-512.png</code>).</td>
</tr>
<tr>
<td><code>cmFooterText</code></td>
<td>Footer text rendered by <code>partials/cm-footer.ejs</code>.</td>
</tr>
</tbody></table>
<blockquote>
<p>These keys retain the historical <code>cm</code> prefix for compatibility. The next iteration will introduce <code>terminal*</code> aliases.</p>
</blockquote>
<h2><code>index</code> Block</h2>
<p>Defines the home page when present.</p>
<pre><code class="language-yaml">index:
  title: Home
  useCmConsole: true
  hideTitle: true
  contentFont: modern-mono
  terminalStyle: true
  tagline: &quot;Spin up the demo, then swap in your own assets.&quot;
  content: |
    Markdown or HTML rendered within the page body.
  cta:
    label: Visit the Blog
    href: blog.html
</code></pre>
<p><code>content</code> supports Markdown and inline HTML. <code>cta</code> is optional and renders a single button.</p>
<h2><code>sections</code></h2>
<p>Each section becomes a standalone page under <code>sections/{id}.html</code> and can be linked from navigation or internal CTAs.</p>
<pre><code class="language-yaml">sections:
  - id: features
    heading: Features
    useCmHead: true
    cmImage: assets/static/img/hero-cards.svg
    content: |
      ## What Ships in the Demo
      ...
    columnLayout:
      enabled: true
      ratio: &quot;15/85&quot;
      leftContent: |
        ### Quick Links
        - [Blog](../blog.html)
      rightContent: |
        ## Customize Anything
        ...
</code></pre>
<p><code>columnLayout</code> is optional. When enabled, the template renders the <code>leftContent</code> and <code>rightContent</code> blocks side by side.</p>
<h2><code>pages</code></h2>
<p>Additional standalone pages (other than the index and sections) can be defined under <code>pages</code>. The structure mirrors the <code>index</code> block, supporting <code>title</code>, <code>slug</code>, <code>content</code>, images, <code>cta</code>, and console flags.</p>
<h2>Header &amp; Footer</h2>
<pre><code class="language-yaml">header:
  links:
    - label: Home
      href: index.html
    - label: Blog
      href: blog.html
    - label: Stagit Demo
      href: stagit/index.html

footer:
  text: &quot;© 2025 RadioStatic Demo.&quot;
  links:
    - label: GitHub
      href: https://github.com/example
</code></pre>
<p>Links are rendered in order. Relative URLs are rewritten automatically for section pages.</p>
<h2>Blog Configuration</h2>
<pre><code class="language-yaml">blog:
  enabled: true
  title: &quot;RadioStatic Blog&quot;
  postsDir: content/blog
  outputDir: blog
  fragmentDir: blog/fragments
  indexTemplate: blog/index.ejs
  postTemplate: blog/post.ejs
  fragmentTemplate: blog/fragment.ejs
  index:
    heroTitle: &quot;RadioStatic Blog&quot;
    heroTagline: &quot;Stories from the sample authors&quot;
    defaultPostPath: content/blog/default-post.md
  authors:
    - id: alex-lee
      name: &quot;Alex Lee&quot;
      avatar: assets/static/img/avatar-alex.svg
      bio: &quot;Designs interfaces for docs and guides.&quot;
</code></pre>
<p>Important details:</p>
<ul>
<li><code>postsDir</code> points to Markdown files with YAML front matter. Each post supports fields such as <code>title</code>, <code>slug</code>, <code>author</code>, <code>summary</code>, <code>heroImage</code>, <code>publishedAt</code>, <code>updatedAt</code>, <code>readingMinutes</code>, <code>tags</code>, and <code>seoDescription</code>.</li>
<li><code>defaultPostPath</code> populates the initial feature post on the blog landing page.</li>
<li><code>authors</code> defines reusable metadata for each author referenced in front matter.</li>
<li>Generated HTML pages land under <code>outputDir</code> with fragments stored in <code>fragmentDir</code>.</li>
</ul>
<h2>Sitemap</h2>
<p>Use the <code>sitemap</code> key to control the generated sitemap page (not the XML sitemap). Common flags mirror the section configuration (<code>useCmHead</code>, <code>hideTitle</code>, etc.).</p>
<h2>Copying Additional Directories</h2>
<p>Use <code>extraCopies</code> when you want to mirror folders that are not referenced through the normal asset pipeline. Each entry expects a <code>from</code> (source directory relative to the repo) and <code>to</code> (target directory inside the output):</p>
<pre><code class="language-yaml">extraCopies:
  - from: examples/demo-site/stagit/html
    to: stagit
</code></pre>
<p>During the build the generator copies <code>examples/demo-site/stagit/html</code> to <code>site-output/stagit/</code>. This is how the demo ships a placeholder stagit mirror alongside the core site.</p>
<h2>Environment Variables</h2>
<ul>
<li><code>RADIOSTATIC_CONFIG</code> / <code>SITEGEN_CONFIG</code>, <code>RADIOSTATIC_OUTPUT</code> / <code>SITEGEN_OUTPUT</code>, <code>RADIOSTATIC_VERBOSE</code> / <code>SITEGEN_VERBOSE</code> – consumed by <code>build-site.sh</code> and <code>make build-local</code>.</li>
<li><code>ENABLE_DOOM_BUILD</code> – optionally runs <code>scripts/build-doom.sh</code> before generating the site.</li>
</ul>
<h2>Tips</h2>
<ul>
<li>Asset paths in YAML are relative to the project root at build time. When you deploy, they become relative to the generated HTML.</li>
<li>Use <code>../</code> prefixes inside Markdown when referencing assets from section pages (the generator resolves them automatically for blog posts).</li>
<li>Keep filenames kebab-cased to match template expectations and avoid surprises on case-sensitive filesystems.</li>
</ul>
<p>Have a configuration question that is not covered here? Add an example to this document as you extend the generator.</p>
