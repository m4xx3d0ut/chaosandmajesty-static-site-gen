  93. ​
  94. Learn how to methodically map such an attack surface using both passive and active means, and understand how to leverage this information during the entire penetration test lifecycle.

  96. ##### 6.1 The Penetration Testing Lifecycle
  97. ​
  98. - Understand the stages of a Penetration Test.
  99. - Learn the role of Information Gathering inside each stage.
  100. - Understand the differences between Active and Passive Information Gathering.
  101. ​
  102. To keep a company's security posture as tightly controlled as possible, we should conduct penetration testing on a regular cadence and after every time there's a significant shift in the target's IT architecture.
  103. ​
  104. A typical penetration test comprises the following stages:
  105. ​
  106. - Defining the Scope.
  107. - Information Gathering.
  108. - Vulnerability Detection.
  109. - Initial Foothold.
  110. - Privilege Escalation.
  111. - Lateral Movement.
  112. - Reporting/Analysis.
  113. - Lessons Learned/Remediation.
  114. ​
  115. The scope of a penetration test engagement defines which IP ranges, hosts, and applications should be test subjects during the engagement, as compared to out-of-scope items that should not be tested.
  116. ​
  117. To begin information gathering, we typically perform reconnaissance to retrieve details about the target organization's infrastructure, assets, and personnel. This can be done either passively or actively. While the former technique aims to retrieve the target's information with almost no direct interaction, the latter probes the infrastructure directly. Active information gathering reveals a bigger footprint, so it is often preferred to avoid exposure by gathering information passively.
  118. ​
  119. ##### 6.2 Passive Information Gathering
  120. ​
  121. - Understand the two different Passive Information Gathering approaches.
  122. - Learn about Open Source Intelligence (OSINT)
  123. - Understand Web Server and DNS passive information gathering.
  124. ​
  125. [Open-source Intelligence (OSINT)](https://en.wikipedia.org/wiki/Open-source_intelligence) the process of collecting openly-available information about a target, generally without any direct interaction with that target.
  126. ​
  127. **Strict interpretation** we never communicate with the target directly. For example, we could rely on third parties for information, but we wouldn't access any of the target's systems or servers. Using this approach maintains a high level of secrecy about our actions and intentions, but can also be cumbersome and may limit our results.
  128. ​
  129. **Loose** interpretation, we might interact with the target, but only as a normal internet user would. For example, if the target's website allows us to register for an account, we could do that. However, we would not test the website for vulnerabilities during this phase.
  130. ​
  131. - Cyclical process rather than linear.
  132. - "next step" depends on "previous step".
  133. - Obtain info that clarifies/expands [attack surface](https://en.wikipedia.org/wiki/Attack_surface)
  134. - Help conduct phishing campaign.
  135. - Supplements other steps, i.e. password guessing which can lead to account compromise.
  136. ​
  137. **Real World Example:**
  138. Several years ago, the team at OffSec was tasked with performing a penetration test for a small company. This company had virtually no internet presence and very few externally-exposed services, all of which proved to be secure. There was practically no attack surface to be found. After a focused passive information gathering campaign that leveraged various Google search operators, connected bits of information "piped" into other online tools, and a bit of creative and logical thinking, we found a forum post made by one of the target's employees in a stamp-collecting forum:
  139. ```
  140. Hi!
  141. I'm looking for rare stamps from the 1950's - for sale or trade.
  142. Please contact me at david@company-address.com
  143. Cell: 999-999-9999
  144. ```
  145. We used this information to launch a semi-sophisticated client-side attack. We quickly registered a stamps-related domain name and designed a landing page that displayed various rare stamps from the 1950's, which we found using Google Images. The domain name and design of the site definitely increased the perceived reliability of our stamp trading website.
  146. ​
  147. Next, we embedded some nasty client-side attack exploit code in the site's web pages, and called "David" during the workday. During the call, we posed as a stamp collector that had inherited their Grandfather's huge stamp collection.
  148. ​
  149. David was overjoyed to receive our call and visited the malicious website to review the "stamp collection" without hesitation. While browsing the site, the exploit code executed on his local machine and sent us a reverse shell.
  150. ​
  151. This is a good example of how some innocuous passively-gathered information, such as an employee engaging in personal business with his corporate email, can lead to a foothold during a penetration test. Sometimes the smallest details can be the most important.
  152. ​
  153. While "David" wasn't following best practices, it was the company's policy and lack of a security awareness program that set the stage for this breach. Because of this, we avoid casting blame on an individual in a written report. Our goal as penetration testers is to improve the security of our client's resources, not to target a single employee. Simply removing "David" wouldn't have solved the problem.

  249. ###### Google Hacking
  250. ​
  251. The term "Google Hacking" was popularized by Johnny Long in 2001.
  252. - [Wiki](https://en.wikipedia.org/wiki/Google_hacking)
  253. - [Google Hacking for Penetration Testers](https://www.amazon.com/Google-Hacking-Penetration-Testers-Johnny/dp/0128029641/ref=dp_ob_image_bk)
  254. - How search engines, like Google, can be used to uncover crit info, vulns, and misconfigured websites.
  255. - Utilizes clever search string and [operators](https://support.google.com/websearch/answer/2466433?hl=en)
  256. - Most of which work with a variety of search engines.
  257. - Iterative process.
  258. - Begin with broad search.
  259. - Narrow using operators to sift out irrelevant results.
  260. ​
  261. **Common Operators**
  262. - The **site** operator limits searches to a single domain.
  263. - Used to gather a rough idea of org web presence.
  264. - Example: `site:megacorpone.com`
  265. - Additional operators used to narrow results.
  266. - Locate txt files.
  267. - Example: `filetype:txt`
  268. ​
  269. - **Example:** `site:megacorpone.com filetype:txt`
  270. - Returns interesting result, `robots.txt`
  271. ```
  272. User-agent: *
  273. Allow: /
  274. Allow: /nanites.php
  275. ```
  276. The robots.txt file instructs web crawlers, such as Google's search engine crawler, to allow or disallow specific resources. In this case, it revealed a specific PHP page (/nanities.php) that was otherwise hidden from the regular search, despite being listed allowed by the policy.
  277. ​
  278. - The **ext** operator.
  279. - Examples: `ext:php`, `ext:xml`, `ext:py`
  280. - Will find indexed PHP Pages, XML, and Python pages, respectively.
  281. ​
  282. - Operators can be modified with **-** to exclude results.
  283. - Example `site:megacorpone.com -filetype:html`
  284. - Excludes HTML pages from results! **Very interesting!**.
  285. - May return web directory indices.
  286. ​
  287. - The **intitle** operator.
  288. - Find pages that return a string in title.
  289. - Example: `intitle:"index of" "parent directory"`
  290. - Find pages that contain "index of" in title and "parent directory" in page.
  291. - The output refers to [directory listing](https://cwe.mitre.org/data/definitions/548.html) pages.
  292. - List the file contents of the directories without index pages.
  293. - Misconfigurations like this can reveal interesting files and sensitive information.

  351. ###### Security Headers and SSL/TLS
  352. ​
  353. - Several other specialty websites that we can use to gather information about a website or domain's security posture.
  354. - Some blur the line between passive and active information gathering.
  355. - **key point** for our purposes is that a **third-party is initiating any scans or checks**.
  356. - [Security Headers](https://securityheaders.com/)
  357. - Search `www.megacorpone.com`
  358. - Missing several defensive headers.
  359. - Content-Security-Policy.
  360. - An effective measure to protect your site from XSS attacks. By whitelisting sources of approved content, you can prevent the browser from loading malicious assets.
  361. - X-Frame-Options.
  362. - Tells the browser whether you want to allow your site to be framed or not. By preventing a browser from framing your site you can defend against attacks like clickjacking. Recommended value "X-Frame-Options: SAMEORIGIN".
  363. - X-Content-Type-Options.
  364. - Stops a browser from trying to MIME-sniff the content type and forces it to stick with the declared content-type. .
  365. - The only valid value for this header is `X-Content-Type-Options: nosniff`
  366. - Referrer-Policy.
  367. - Is a new header that allows a site to control how much information the browser includes with navigations away from a document and should be set by all sites.
  368. - Permissions-Policy.
  369. - Is a new header that allows a site to control which features and APIs can be used in the browser.
  370. - Missing headers are not necessarily vulnerabilities in and of themselves, but they could indicate web developers or server admins that are not familiar with [server hardening](https://csrc.nist.gov/publications/detail/sp/800-123/final)
  371. - Server hardening is the overall process of securing a server via configuration. This includes processes such as disabling unneeded services, removing unused services or user accounts, rotating default passwords, setting appropriate server headers, and so forth. We don't need to know all the ins and outs of configuring every type of server, but understanding the concepts and what to search for can help us determine how best to approach a potential target.
  372. - [SSL Server Test](https://www.ssllabs.com/ssltest/) from Qualys SSL Labs.
  373. - Shows that the server supports TLS versions such as 1.0 and 1.1.
  374. - Deemed legacy as they implement insecure cipher suites.
  375. - This ultimately suggests that our target is not applying current best practices for SSL/TLS hardening.
  376. - [Disabling the TLS_DHE_RSA_WITH_AES_256_CBC_SHA](https://msrc-blog.microsoft.com/2013/11/12/security-advisory-2868725-recommendation-to-disable-rc4/) suite has been recommended for several years.

  389. ###### DNS Enumeration
  390. ​
  391. The [Domain Name System (DNS)](https://en.wikipedia.org/wiki/Domain_Name_System) is a distributed database responsible for translating user-friendly domain names into IP addresses.
  392. ​
  393. Common types of DNS records include:
  394. - NS: Nameserver records contain the name of the authoritative servers hosting the DNS records for a domain.
  395. - A: Also known as a host record, the "a record" contains the IPv4 address of a hostname (such as www.megacorpone.com).
  396. - AAAA: Also known as a quad A host record, the "aaaa record" contains the IPv6 address of a hostname (such as www.megacorpone.com).
  397. - MX: Mail Exchange records contain the names of the servers responsible for handling email for the domain. A domain can contain multiple MX records.
  398. - PTR: Pointer Records are used in reverse lookup zones and can find the records associated with an IP address.
  399. - CNAME: Canonical Name Records are used to create aliases for other host records.
  400. - TXT: Text records can contain any arbitrary data and be used for various purposes, such as domain ownership verification.
  401. ​
  402. **Examples:**
  403. ​
  404. Using `host` command to find IP address of target
  405. ```bash
  406. kali@kali:~$ host www.megacorpone.com
  407. www.megacorpone.com has address 149.56.244.87
  408. ```
  409. ​
  410. Default, the host command searches for an A record. To query other fields, such as MX or TXT records, specify the record type in our query using the -t option. **NOTE:** Lowest priority best.
  411. ```bash
  412. kali@kali:~$ host -t mx megacorpone.com
  413. megacorpone.com mail is handled by 10 fb.mail.gandi.net.
  414. megacorpone.com mail is handled by 20 spool.mail.gandi.net.
  415. megacorpone.com mail is handled by 50 mail.megacorpone.com.
  416. megacorpone.com mail is handled by 60 mail2.megacorpone.com.
  417. ```
  418. ​
  419. TXT records
  420. ```bash
  421. kali@kali:~$ host -t txt megacorpone.com
  422. megacorpone.com descriptive text "Try Harder"
  423. megacorpone.com descriptive text "google-site-verification=U7B_b0HNeBtY4qYGQZNsEYXfCJ32hMNV3GtC0wWq5pA"
  424. ```
  425. ​
  426. determine if megacorpone.com has a server with the hostname "idontexist"
  427. ```bash
  428. kali@kali:~$ host idontexist.megacorpone.com
  429. Host idontexist.megacorpone.com not found: 3(NXDOMAIN)
  430. ```
  431. Indicates a public DNS record does not exist for that hostname. Since we now understand how to search for valid hostnames, we can automate our efforts.
  432. ​
  433. **DNS brute-forcing techniques**
  434. Automate the forward DNS-lookup of common hostnames using the host command in a Bash one-liner. Build a list of possible hostnames.
  435. ```bash
  436. kali@kali:~$ cat list.txt
  437. www
  438. ftp
  439. mail
  440. owa
  441. proxy
  442. router
  443. ```
  444. ​
  445. Bash one-liner to attempt to resolve each hostname.
  446. ```bash

  603. ###### TCP/UDP Port Scanning Theory
  604. ​
  605. The process of inspecting TCP or UDP ports on a remote machine with the intention of detecting what services are running on the target and what potential attack vectors may exist.
  606. - Please note that port scanning is not representative of traditional user activity and could be considered illegal in some jurisdictions. Therefore, it should not be performed outside the labs without direct, written permission from the target network owner.
  607. ​
  608. - Implications of port scanning.
  609. - Large amount of traffic.
  610. - Intrusive nature.
  611. - Running them blindly can have adverse effects on systems/network.
  612. - Overloading switch/servers/links.
  613. - Trigger IDS/IPS.
  614. ​
  615. **Proper Port Scanning Methodology**
  616. - Do not run full scan against network.
  617. - Scan for ports 80, 443.
  618. - Return web servers.
  619. - Run full port scan against web servers.
  620. - Dynamic and iterative process.
  621. ​
  622. **TCP Scanning Techniques**
  623. - Simplest form, the CONNECT scan.
  624. - Takes advantage of [3-way TCP handshake](http://support.microsoft.com/kb/172983)
  625. - Host sends TCP SYN packet to server on dest port.
  626. - If dest port is open, the server responds with SYN-ACK packet.
  627. - Closed ports actively reject the connection attempt via a RST-ACK packet.
  628. - Client responds with ACK to complete handshake.
  629. - If the 3-way handshake completes successfully the port is considered open.
  630. ​
  631. Demonstrate by running a **TCP Netcat port scan** on ports 3388-3390. We'll use the -w option to specify the connection timeout in seconds, as well as -z to specify zero-I/O mode, which is used for scanning and sends no data. Netcat closes successful connection by sending a FIN-ACK packet
  632. ```bash
  633. kali@kali:~$ nc -nvv -w 1 -z 192.168.50.152 3388-3390
  634. (UNKNOWN) [192.168.50.152] 3390 (?) : Connection refused
  635. (UNKNOWN) [192.168.50.152] 3389 (ms-wbt-server) open
  636. (UNKNOWN) [192.168.50.152] 3388 (?) : Connection refused
  637. sent 0, rcvd 0
  638. ```
  639. ​
  640. **UDP Scanning**
  641. - UDP is stateless and does not involve a three-way handshake, the mechanism behind UDP port scanning is different from TCP.
  642. - Simple UDP scan.
  643. - Send empty UDP packet to port.
  644. - If port is open, packet will be passed to application layer.
  645. - Response depends on on the application is programmed.
  646. - If port is closed, target should respond with ICMP Port unreachable.
  647. - Sent by UDP/IP stack of target system.
  648. - Most scanners rely on ICMP Port unreachable to infer status of target port.
  649. - Often unreliable, firewalls/routers may drop ICMP packets.
  650. - This can lead to false positives.
  651. - Using protocol specific UDP port scanners yield better results.
  652. - UDP scans generate less traffic than TCP scans.
  653. ​

  1337. ###### SNMP Enumeration
  1338. ​
  1339. **Treasure Trove of Easy Data**
  1340. - Simple Network Management Protocol (SNMP) is not well-understood by many network administrators.
  1341. - Results in SNMP misconfigurations.
  1342. - Result in significant information leaks.
  1343. - SNMP is based on UDP.
  1344. - Stateless proto.
  1345. - Susceptible to IP spoofing and replay attacks.
  1346. - Proto 1, 2, 2c offer no traffic encryption.
  1347. - SNMP info can be easily intercepted over a local network.
  1348. - Weak auth schemes.
  1349. - Commonly left configured with default public and private community strings.
  1350. - Until recently, SNMPv3, which provides authentication and encryption, has been shipped to support only DES-56, proven to be a weak encryption scheme that can be easily brute-forced. A more recent SNMPv3 implementation supports the AES-256 encryption scheme.
  1351. - **Main Feature:** SNMP MIB Tree.
  1352. - SNMP Management Information Base (MIB) is a database containing information usually related to network management.
  1353. - Tree structure.
  1354. - Branches represent different organizations or network functions.
  1355. - Leaves (final endpoints) correspond to specific variable values.
  1356. - Accessible and can be probed by external user.
  1357. - [IBM Knowledge Center on MIB Tree](https://www.ibm.com/support/knowledgecenter/ssw_aix_71/commprogramming/mib.html)
  1358. ​
