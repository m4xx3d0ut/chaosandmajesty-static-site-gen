# Platform Config: MicroK8s + Gitea (+ Actions) → Export → GitOps

This repo captures how we deploy Gitea on MicroK8s, add a Gitea Actions runner, create our configuration repo in Gitea, and export the cluster/node config back into this repo (with Secrets encrypted). It also outlines the next steps toward GitOps, including Flux wiring, ValidatingAdmissionPolicy-based guardrails, and our **capacitor-next** admin & read‑only service accounts.

> **Assumes**
>
> * MicroK8s with `ingress`, `dns`, and `metallb` (or equivalents) enabled.
> * `helm` (or `microk8s helm3`) available.
> * cert-manager installed and a **selfsigned Issuer** in `git-local`.
> * `ingress-nginx` present and listening for **TCP services** (SSH on `32222`).
> * Tools on the node/admin box: `jq`, `yq` (v4), `sops` (v3.10+), `age`.
> * Repo layout already initialized (this repo) with `tools/export-all.sh`.
>
> **Tip:** we export *live* state. That’s great for disaster‑recovery and drift audit. For GitOps, we later carve out **intent** manifests/values from those exports.

## 6) Deploy Gitea via Helm

Use chart values that **mount your existing PVC** (let the chart manage the `data` volume). For chart v12+, the key is `persistence.claimName` (not `existingClaim`) and `create: false`.

**`helm-gitea-test/values.yaml` (relevant bits):**

```yaml
namespace: git-local

persistence:
  enabled: true
  create: false          # do not create new PVC
  claimName: git-repos-pvc
  storageClass: ""
  accessModes: [ReadWriteMany]
  size: 20Gi
  mountPath: /data

service:
  http: { type: ClusterIP, port: 3000 }
  ssh:  { type: ClusterIP, port: 22 }

gitea:
  config:
    server:
      PROTOCOL: http
      DOMAIN: gitea.core.home.arpa
      ROOT_URL: https://gitea.core.home.arpa/
      SSH_DOMAIN: gitea.core.home.arpa
      SSH_PORT: 32222
      START_SSH_SERVER: true
      LFS_START_SERVER: true
    actions:
      ENABLED: true
  admin:
    username: core_admin
    password: <redacted>
    email: you@example.com

ingress:
  enabled: true
  className: nginx
  annotations:
    cert-manager.io/issuer: selfsigned-issuer
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
  hosts:
  - host: gitea.core.home.arpa
    paths:
    - path: /
      pathType: Prefix
  tls:
  - secretName: gitea-core-tls
    hosts: [gitea.core.home.arpa]
```

Install:

```bash
helm repo add gitea-charts https://dl.gitea.com/charts || true
helm repo update
helm upgrade --install gitea gitea-charts/gitea -n git-local -f helm-gitea-test/values.yaml

kubectl -n git-local rollout status deploy/gitea
kubectl -n git-local get pods,svc,ingress
```

HTTP/Ingress quick check:

```bash
curl -I https://gitea.core.home.arpa/
```

> If you used a cert-manager **Certificate** for SANs, wait for it to be Ready and ensure `gitea.core.home.arpa` is present.

## 7) Deploy the Gitea Actions runner

The runner uses a separate chart. We register with the instance token from the Gitea UI.

```bash
# In the Gitea UI: Site Admin → Actions → Runners → Registration Token (instance-level)
export GITEA_INSTANCE_REG_TOKEN="<paste-from-ui>"

# Secret for runner registration
kubectl -n git-local create secret generic gitea-runner-token \
  --from-literal=GITEA_RUNNER_REGISTRATION_TOKEN="$GITEA_INSTANCE_REG_TOKEN" \
  --dry-run=client -o yaml | kubectl apply -f -
```

Create values for the runner (includes optional CA mount for TLS):

```bash
cat > actions.values.yaml <<'EOF'
enabled: true
existingSecret: "gitea-runner-token"
existingSecretKey: "GITEA_RUNNER_REGISTRATION_TOKEN"
giteaRootURL: "https://gitea.core.home.arpa"

statefulset:
  actRunner:
    # remove 'insecure: true' once CA trust is wired
    config: |
      log:
        level: info
      cache:
        enabled: false
      runner:
        # insecure: true

  # Ensure the DinD sidecar trusts the same CA before dockerd starts
  dind:
    command:
      - sh
      - -c
      - |
        update-ca-certificates
        exec dockerd-entrypoint.sh "$@"
      - --

# Trust the same certificate the ingress serves
extraVolumes:
  - name: gitea-cert
    secret:
        secretName: gitea-tls
        items:
          - key: ca.crt
            path: gitea-root.crt
  extraVolumeMounts:
    - name: gitea-cert
      mountPath: /etc/ssl/certs/gitea-root.crt
      subPath: gitea-root.crt
      readOnly: true
EOF
```

Install runner:

```bash
git clone https://gitea.com/gitea/helm-actions.git
helm -n git-local upgrade --install gitea-actions ./helm-actions -f actions.values.yaml

kubectl -n git-local rollout status sts/gitea-actions-act-runner
```

Runner should show up in Gitea UI under **Site Admin → Actions → Runners**.

## 9) Export live cluster state back into this repo

### 9.1 SOPS setup (Age)

Generate an age key (one time):

```bash
mkdir -p ~/.config/sops/age
age-keygen -o ~/.config/sops/age/keys.txt
grep "# public key:" ~/.config/sops/age/keys.txt
```

Put the **public** key into `.sops.yaml` at repo root:

```yaml
creation_rules:
  - path_regex: ^live-export/secrets/.+\.ya?ml$
    encrypted_regex: '^(data|stringData)$'
    age: 'age1your_public_key_here'
```

> **Important:** `age:` should be a **single string**, not a YAML list.

### 9.2 Run the exporter

From repo root:

```bash
chmod +x tools/export-all.sh
./tools/export-all.sh --helm --include-crds --encrypt-secrets
```

What it does:

* Exports **cluster‑scoped** and **namespaced** objects (cleaned of server‑managed fields) under `live-export/kubernetes/...`
* Exports Helm `values.yaml`, `values-all.yaml`, and rendered `manifest.yaml` under `live-export/helm/<ns>/<release>/`
* Exports all CRDs into `live-export/kubernetes/cluster-scoped/crds/all-crds.yaml`
* Moves all Secrets to `live-export/secrets/<ns>/<name>.yaml` and **SOPS‑encrypts** them
* Prints a summary and cleans `.tmp/`

Verify Secrets are encrypted:

```bash
grep -RIn --include='*.yaml' '^sops:' live-export/secrets && echo "OK: encrypted"
```

Commit the export:

```bash
git add -A
git commit -m "Live export: k8s + helm (+crds); secrets encrypted"
git push
```

# Part 2 — Flux GitOps wiring

We manage the cluster via Flux, with a tidy **root → folder of child Kustomizations → per‑area Kustomizations** pattern.

## 10) Bootstrap Flux to this repo

```bash
flux bootstrap git \
  --url=ssh://git@gitea.core.home.arpa:32222/<ORG_OR_USER>/platform-config.git \
  --branch=main \
  --path=gitops/clusters/microk8s-prod
```

This creates `GitRepository/platform-config` and a starter `Kustomization`. We then layer our own structure.

## 11) Root Kustomization that *tracks the folder of child CRs*

> Flux won’t “discover” a new Kustomization CR from git unless the CR itself is applied once or a parent already manages that folder. We use a one‑time `kubectl apply` for the parent CR below.

```yaml
# gitops/clusters/microk8s-prod/flux-system/cluster-root.yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: cluster-root
  namespace: flux-system
spec:
  interval: 10m
  prune: true
  wait: true
  path: ./gitops/clusters/microk8s-prod/kustomizations
  sourceRef:
    kind: GitRepository
    name: platform-config
    namespace: flux-system
```

Apply once and reconcile:

```bash
kubectl apply -f gitops/clusters/microk8s-prod/flux-system/cluster-root.yaml
flux reconcile source git platform-config -n flux-system
flux reconcile kustomization cluster-root -n flux-system
```

## 12) Index of child Kustomizations

```yaml
# gitops/clusters/microk8s-prod/kustomizations/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - apps.yaml
  - infra-core.yaml
  - infra-crds.yaml
  - infra-policies.yaml
```

Each of the above files is a **Flux Kustomization CR** that points at a repo sub‑path. Example for **infra‑policies**:

```yaml
# gitops/clusters/microk8s-prod/kustomizations/infra-policies.yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: infra-policies
  namespace: flux-system
spec:
  interval: 10m
  prune: true
  wait: true
  path: ./gitops/infra-policies
  sourceRef:
    kind: GitRepository
    name: platform-config
    namespace: flux-system
  dependsOn:
    - name: infra-core   # if your policies depend on core infra existing first
```

> If a child isn’t showing up in `kubectl -n flux-system get kustomizations`, either the **root CR isn’t applied** yet or the **index file** above doesn’t list it.

# Part 3 — Admission guardrails (ValidatingAdmissionPolicy)

We use a ValidatingAdmissionPolicy (VAP) to ensure the **read‑only** capacitor service account cannot perform write‑like or attach/exec operations, even if RBAC appears permissive.

> **Prereq:** Your API server must expose `ValidatingAdmissionPolicy` (K8s ≥1.30). Check:
>
> ```bash
> kubectl api-resources | grep -i ValidatingAdmissionPolicy
> ```

## 13) Policy and Binding (scoped to write‑like ops)

```yaml
# gitops/infra-policies/deny-capacitor-ro-writes.yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: deny-capacitor-ro-writes
spec:
  failurePolicy: Fail
  matchConstraints:
    operations: ["CREATE","UPDATE","DELETE","CONNECT"]
    resourceRules:
      - apiGroups: ["", "apps", "batch"]
        apiVersions: ["*"]
        resources:
          - pods
          - pods/exec
          - pods/ephemeralcontainers
          - pods/attach
          - deployments
          - replicasets
          - statefulsets
          - daemonsets
          - jobs
          - cronjobs
  validations:
    - expression: request.userInfo.username != "system:serviceaccount:flux-system:capacitor-next-ro"
      message: "capacitor-next-ro is view-only; write-like operations are blocked by policy."
```

```yaml
# gitops/infra-policies/deny-capacitor-ro-writes-binding.yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: deny-capacitor-ro-writes-binding
spec:
  policyName: deny-capacitor-ro-writes
  validationActions: [Deny]
  # Optional namespace scoping:
  # matchResources:
  #   namespaceSelector:
  #     matchLabels:
  #       kubernetes.io/metadata.name: flux-system
```

Apply (via Flux or directly for a first test):

```bash
kubectl apply -f gitops/infra-policies/deny-capacitor-ro-writes.yaml
kubectl apply -f gitops/infra-policies/deny-capacitor-ro-writes-binding.yaml
```

Verify:

```bash
kubectl get validatingadmissionpolicies
kubectl get validatingadmissionpolicybindings
```

## 14) Test the policy with impersonation

```bash
POD=$(kubectl -n flux-system get pod -o name | head -n1)

# should be DENIED by the policy
kubectl -n flux-system delete $POD \
  --as=system:serviceaccount:flux-system:capacitor-next-ro \
  --as-group=system:serviceaccounts \
  --as-group=system:serviceaccounts:flux-system \
  --as-group=system:authenticated
```

> `kubectl auth can-i` may still say **yes** (RBAC) — *admission* is what blocks the actual call.

# Part 4 — Capacitor service accounts & test deployments

We keep two identities in `flux-system`:

* **`capacitor-next`** – admin/service identity (broad write access). Start with `cluster-admin` for simplicity; scope down later.
* **`capacitor-next-ro`** – read‑only identity. Gets `view` cluster‑role; admission policy above prevents write/exec even if something sneaks through.

## 15) RBAC

```yaml
# gitops/infra-core/capacitor-rbac.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: capacitor-next
  namespace: flux-system
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: capacitor-next-ro
  namespace: flux-system
---
# Admin: broad access (start with cluster-admin; refine later)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: capacitor-next-admin
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
  - kind: ServiceAccount
    name: capacitor-next
    namespace: flux-system
---
# Read-only: standard view across cluster
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: capacitor-next-ro-view
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: view
subjects:
  - kind: ServiceAccount
    name: capacitor-next-ro
    namespace: flux-system
```

> To scope admin more tightly, swap `cluster-admin` for a custom `ClusterRole` granting only what the workload needs (configmaps/secrets in `flux-system`, etc.).

## 16) (Stub) Deployments that use the SAs

These are **test pods** to verify identity and the admission policy. Replace the image/command with the real capacitor workload later.

```yaml
# gitops/infra-core/capacitor-deployments.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: capacitor-next
  namespace: flux-system
spec:
  replicas: 1
  selector:
    matchLabels: { app: capacitor-next }
  template:
    metadata:
      labels: { app: capacitor-next }
    spec:
      serviceAccountName: capacitor-next
      containers:
        - name: main
          image: ghcr.io/fluxcd/flux-cli:2.3.0
          command: ["sh","-c","sleep infinity"]
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: capacitor-next-ro
  namespace: flux-system
spec:
  replicas: 1
  selector:
    matchLabels: { app: capacitor-next-ro }
  template:
    metadata:
      labels: { app: capacitor-next-ro }
    spec:
      serviceAccountName: capacitor-next-ro
      containers:
        - name: main
          image: ghcr.io/fluxcd/flux-cli:2.3.0
          command: ["sh","-c","sleep infinity"]
```

Reconcile the Kustomization that includes these files (e.g., `infra-core`).

### Validate

```bash
# As RO SA, exec should be denied by the VAP (CONNECT op)
kubectl -n flux-system exec deploy/capacitor-next-ro -- \
  --as=system:serviceaccount:flux-system:capacitor-next-ro -- id || true

# As admin SA (impersonation), exec should work
kubectl -n flux-system exec deploy/capacitor-next -- \
  --as=system:serviceaccount:flux-system:capacitor-next -- id
```

# Troubleshooting

* **SOPS error `cannot unmarshal !!seq into string`**
  In `.sops.yaml`, make `age:` a **string**:

  ```yaml
  age: 'age1...'
  ```

  not a YAML list.

* **Runner TLS verification fails**
  Ensure your cert contains `gitea.core.home.arpa` SAN and the runner trusts the CA:

  * Create a cert‑manager `Certificate` with the right DNS names.
  * Mount the CA into the runner (`extraVolumes`/`extraVolumeMounts`).
  * Remove `insecure: true` from runner config once CA is trusted.

* **Ingress SSH (32222) not reachable**
  Confirm `ingress-nginx-tcp` ConfigMap has `32222: "git-local/gitea-ssh:22"` and the controller has `--tcp-services-configmap` arg.

* **VAP resources show “No resources found”**
  Your API server doesn’t expose VAP; either upgrade Kubernetes/MicroK8s or fall back to stricter RBAC with admission‑webhook alternatives.

* **`infra-policies` missing in Flux**
  Ensure the **root** `cluster-root.yaml` was applied once, and that `gitops/clusters/microk8s-prod/kustomizations/kustomization.yaml` lists `infra-policies.yaml`.

# Repo structure (quick reference)

```
live-export/
  helm/<ns>/<release>/{values.yaml,values-all.yaml,manifest.yaml}
  kubernetes/
    cluster-scoped/<kind>/<name>.yaml
    namespaces/<ns>/<kind>/<name>.yaml
  secrets/<ns>/<secret>.yaml  # SOPS-encrypted
apps/
  gitea/app.ini               # only if tuned in-pod
gitops/
  clusters/microk8s-prod/
    flux-system/
      cluster-root.yaml
    kustomizations/
      kustomization.yaml      # index of child Kustomizations
      apps.yaml               # (example) child Kustomization
      infra-core.yaml         # (example) child Kustomization
      infra-crds.yaml         # (example) child Kustomization
      infra-policies.yaml     # (child → ./gitops/infra-policies)
  infra-core/
    capacitor-rbac.yaml
    capacitor-deployments.yaml
  infra-policies/
    deny-capacitor-ro-writes.yaml
    deny-capacitor-ro-writes-binding.yaml
tools/
  export-all.sh               # one-button exporter (cleans .tmp on exit)
microk8s-host/
  args/ system/               # host-level tweaks (optional)
```
