Understanding Windows Privileges and Access Control Mechanisms

Win OS privs refer to the permissions of a specific account to perform system-related local operations, such as modding the FS or adding users. Win needs a control mechanism to grant/deny those ops by determining if the user privs are sufficient for the op. We will cover four different concepts/mechanisms:

  • Security Identifier (SID)
    • Win uses SID to identify entities
    • A SID is a unique value assigned to each entity, or principal, that can auth
      • Users
        • Windows uses only the SID, not usernames, to identify principals for access control management.
      • Groups
    • SID for local accounts and groups is generated by Local Security Authority (LSA)
    • SID for domain users and domain groups is generated by the Domain Controller (DC)
      • SID cannot be changed and is created at the time of User/Group creation
      • consists of segements delimited by -, structure like:
        • S-R-X-Y
          • S: string is SID
          • R: stands for revision, always set to 1 (overal structure of SID is v1)
          • X: identifier authority that issues SID
            • the most common identifier authority is 5 (NT Authority, local/domain users/groups)
          • Y: sub authorities of the identifier authority.
            • Every SID contains one or more sub authorities of the identifier authority
              • domain identifier
                • is the SID of the domain for domain users
                • is the SID of the local machine for local users
                • is 32 for built in principals
                • example SID of local user on Win sys:
                  • S-1-5-21-1336799502-1441772794-948155058-1001
                    • RID 1001
                      • RID starting at 1000 for majority principals, implys that this is the second local user created on the system, 1000 being the first
                      • SID with RID under 1000 are called well-known SIDs
                        • generic and built in groups and users instead of specific groups and users
                          • Useful well-known SIDs for PrivEsc
S-1-0-0                       Nobody        
S-1-1-0	                      Everybody
S-1-5-11                      Authenticated Users
S-1-5-18                      Local System
S-1-5-domainidentifier-500    Administrator

                    - relative identifier (RID)
                        - determines principals such as users or groups

Knowing how Win identifies principals is necessary for understanding access tokens and vital in Active Directory

  • access token
    • On user auth Win generates and access token and assigns it to the user
    • the token contains information that effectively describes the security context of a given user.
    • the security context is a set of rules/attributes currently in effect
      • the security context of a token consists of:
        • SID of user
        • SIDs of groups user is a member of
        • the user groups and privs
        • further info describing the token
    • when a user starts a process or thread a token is assigned to the object
      • known as a primary token
        • specifies the permissions the process/thread has when interacting with another object
        • is a copy of the access token of the user
      • a thread can also have an impersonation token assigned
        • provides a different security context than the owner process
        • the thread interacts with objects on behalf of the impersonation token, not the primary
  • Mandatory Integrity Controls
    • uses integrity levels to control access to securable objects
      • the levels are akin to hierarchies of trust Win has in a running app or securable object
    • when a proc starts or objects are created they receive the integrity level of the principal performing the op
      • Exception being is an executable has low file integrity level the process integrity level will be low
    • A principal with a lower integrity level cannot write to an object of a higher integrity level
      • even if permissions would normally allow them to do so
    • Since Win Vista processes run on five integraity levels:
- System: SYSTEM (kernel, ...)
- High: Elevated users
- Medium: Standard users
- Low: Very restricted rights often used in sandboxed[^privesc_win_sandbox] processes or for directories storing temporary data
- Untrusted: Lowest integrity level with extremely limited access rights for processes or objects that pose the most potential risk
  • We can display the integrity level of a proc with Process Explorer:
    • our current user with whoami/groups
    • for files with icacls
    • the following example shows two PowerShell procs
      • one started by reg User
      • another started as Admin

  • The PowerShell procs have the integrity levels of High and Medium
    • we can infer that the High level proc was started by admin
    • and the Medium level proc was started by the user
  • User Account Control (UAC)
    • Win security feature that protects the OS by running most applications and tasks with standard user privs
      • even if launched by an Administrator
        • For this, and admin user is assigned two access tokens after successful logon
          • the first token is a standard user token
            • aka filtered admin token
            • used to perform all non-priv ops
          • the second token is a regular admin token
            • used to perform privileged ops
            • requires UAC prompt confirmation for use

This introduction covers the basics of Win priv and access control mechanisms; SIDs, access tokens, integrity levels, and UAC. Win offers numerous other mechanisms to control access to securable objects, several of which we will discuss and demonstrate in this module.

Situational Awareness

With our basic understanding of Win privs we will cover various methods to get situational awareness on a system. Assume we used a client-side attack or exploited a vulnerability to access a Windows system as an unpriv user. Before we attempt to elevate privs we must obtain info about the system we are on.

This step is crucial to understand the nature of the compromised system as well as discover possible PrivEsc vectors. It is often skipped or minimized by inexperienced pen testers due to the nature of sifting through and interpreting large amounts of information. Experienced pentesters know that by gathering as much as possible, they obtain valuable information about the target system, which they can use to create various actionable vectors to elevate their privs.

The key info we should always obtain:

- Username and hostname
- Group memberships of the current user
- Existing users and groups
- Operating system, version and architecture
- Network information
- Installed applications
- Running processes
  • once we have performed enumeration and obtained this information we will have a solid understanding of our target sys

Information Goldmine PowerShell

We have seen how we can use sensitive info found in plain-text files to PriveEsc. Over the last decade IT security awareness has greatly improved via:

  • training

  • IT policies

  • threat of cyber attacks painted by media This has led to less sensitive info stored in notes and text files. Due to growing threat, additional defensive measures have been developed for clients/servers. One measure is improved logging of command execution, allowing IT staff to review and respond to threats. Service Binary Hijacking

Every Win service has an associated binary file that is exec when the service starts or transitions into a running state. Let's consider a scenario where a dev creates a program and installs an app as a Win service. The dev does not secure the perms of the prog at install, allowing full Read/Write access to all members of the Users group. Result, lower priv users could replace the prog with a malicious one and exec by restarting the service or starting it automatically when the machine is rebooted. Once the service starts, the mal bin is executed with the privs of that service, LocalSystem for example.

Service DLL Hijacking

Replacing the binary of a service is a very effective way to attempt PrivEsc on Win systems. Often our user does not have perms to replace the bins, we need to adapt to a more advanced method of Win service abuse.

  • Dynamic Link Libraries (DLL)
    • provide functionality to programs or the Win OS
    • contains code or resources
      • icon files
      • other exec files or objects
    • provide a way for devs to use and integrate existing functionality
  • Win uses DLLs to store func needed by several components
    • otherwise each component would need the func in their own source
  • On Unix systems these are called Shared Objects

There are several ways to exploit how DLLs work on Win which can be effective for PrivEsc.

  • Instead of overwriting the service bin we overwrite the DLL used by it
    • the service may not function as expected because intended DLL func is missing
    • still lead to code exec of DLL code, allowing us to create a local admin for instance
  • Another method, DLL search order
    • search order defined by MS
      • determines what to inspect first when searching for DLL
      • by default all Win versions have safe DLL search mode enabled
        • implemented by MS due to the high number of DLL hijacking vectors
          • ensure DLLs are more difficult to hijack
          • the standard search order from MS docs show below
1. The directory from which the application loaded.
2. The system directory.
3. The 16-bit system directory.
4. The Windows directory. 
5. The current directory.
6. The directories that are listed in the PATH environment variable.
  • Win first searched the app dir
  • interestingly, current dir is at pos 5
  • when safe DLL search mode is disabled, curr dir os pos 2, after app dir
  • a special case of this method is missing DLL
    • the bin attempts to load a DLL that isn't on the sys
      • result of flawed install proc
      • sometimes occurs after update
      • even with missing DLL app may still work with limited func
    • to exploit this case
      • we can place a mal DLL, named as missing DLL, in a DLL search order path
        • thus executing mal code when app is started

Before creating the DLL let's briefly review how attaching a DLL works and how it may lead us to code exec.

  • Each DLL can have an optional entry point function named DllMain
    • executed when process of threads attach the DLL
      • this function generally contains four cases named:
        • DLL_PROCESS_ATTACH
        • DLL_THREAD_ATTACH
        • DLL_THREAD_DETACH
        • DLL_PROCESS_DETACH
      • these cases handle DLL loading/unloading by proc/thread
      • commonly used for initialization or exiting tasks of the DLL
      • if a DLL doesn't have a DllMain entry point func it only provides resources
  • The following MS example shows us a basic C++ DLL containing the 4 cases
    • the DLL has the entry point func DllMain four cases in switch statement
      • depending on val of ul_reason_for_call one cases execs
        • all cases just use break in example
BOOL APIENTRY DllMain(
HANDLE hModule,// Handle to DLL module
DWORD ul_reason_for_call,// Reason for calling function
LPVOID lpReserved ) // Reserved
{
    switch ( ul_reason_for_call )
    {
        case DLL_PROCESS_ATTACH: // A process is loading the DLL.
        break;
        case DLL_THREAD_ATTACH: // A process is creating a new thread.
        break;
        case DLL_THREAD_DETACH: // A thread exits normally.
        break;
        case DLL_PROCESS_DETACH: // A process unloads the DLL.
        break;
    }
    return TRUE;
}
  • the MS comments state that DLL_PROCESS_ATTACH is used when a proc loads the DLL
    • since the target service bin proc tries to load a DLL, this is the case we want to use

Unquoted Service Paths

Another PrivEsc vector on Win OS is unquoted service paths. This can be used when we have Write perms to a service main dir or sub dir but cannot replace the files directly.

Each Win service maps an exec file that runs when the service is started. If the path of this file contains one or more spaces and is NOT enclosed in quotes, we may be able to leverage into a PrivEsc attack.

When a service is started and a proc is created:

  • func called CreateProcess
    • the first param of the func is IpApplicationName
      • used to specify the name of exec
      • optionally the path of exec
    • if the string contains spaces and is not enclosed in quotation marks
      • it is not clear to the func where the file name ends and arg begins
      • allowing various interpretations
        • the func starts interpreting the path from left to right until a space is reached
        • at each space in the path the func uses the preceding part as the file name by adding .exe and the rest as args
          • Example:
C:\Program.exe
C:\Program Files\My.exe
C:\Program Files\My Program\My.exe
C:\Program Files\My Program\My service\service.exe
  • this shows the order Win tries to interpret the service bin path to locate the exe
  • To exploit this:
    • we must create a mal exec and place it in a corresponding interpreted path
      • matching its name to an interpreted name
  • once the service starts, our our mal exec gets executed with the same privs as the service that starts it
    • often the LocalSystem account
      • resulting in successful PrivEsc
  • In the example context our exec could be named Program.exe
    • place it in C:\
  • Or names My.exe
    • place it in C:\Program Files\ or C:\Program Files\My Program\
  • the first two options would require perms we are unlikely to have
  • the third options is more likely as it is the software's main dir
    • if admin or dev set the perms for this dir too open we can place out mal bin there

Scheduled Tasks

Win uses Task Scheduler to automate various tasks.

  • clean-up activities
  • update management

Win terminology is Schedule Tasks or Tasks which are defined by one or more triggers. A trigger is used as a condition, when met causing one or more actions to exec.

  • Example; a trigger can be set
    • for a specific time and date
    • at startup
    • at log on
    • on a Win event

There are 3 vital pieces of info for identifying possible PrivEsc vectors from a scheduled task.

  • which user account/Principal does the task get exec?
  • what triggers are specified for the task?
  • what actions are executed for the task when one or more triggers are met?

User Account/Principal The first question helps us determine if we can abuse the task to lead to PrivEsc.

  • if the task is exec in context of current user
    • we cannot PrivEsc
  • if the task runs as NT AUTHORITY\SYSTEM or an admin user
    • a successful attack could lead to PrivEsc

Specified Triggers The second question tells us if the trigger was met in the past.

  • if the trigger was met
    • it will not run again, meaning it is not a viable target
  • if the task would run in the future beyond the duration of the engagement
    • we should search for another vector
      • we should however note this in our findings

Actions Executed When Triggers Met The answer to this determines how we can potentially perform a PrivEsc attack. In the majority of cases we can leverage familiar tactics:

  • replacing the binary
  • placing a missing DLL There are no service binaries with scheduled tasks, we do have programs and scripts specified by the actions.

Using Exploits

We have seen how to leverage sensitive info and abuse Win components to achieve PrivEsc, we'll now explore three different exploits that can lead to PrivEsc and show an example of one.

    1. application-based vulnerabilities
    • apps installed on Win systems may contain vulns
      • as learned in "Locating Public Exploits"
    • if apps run with administrative perms we can exploit a vuln that leads to code exec
      • which would successfully achieve PrivEsc
    1. exploit vulns in Windows Kernel
    • the vulns and research are very advanced
      • require extensive knowledge of the Win OS
    • for our purpose, it is enough to know they can be used to achieve PrivEsc
    • BEFORE using these exploits
      • consider they can easily crash a system
        • depending on engagement this may not be allowed
      • always have a clear understanding of assessment rules
    1. Win priv abuse
    • non-priv users with key assigned privs can abuse to perform PrivEsc
      • SeImpersonatePrivilege
        • possible to leverage a token with a different security context
        • perform ops in the context of another account
      • assigned by default to:
        • local Administrators
        • LOCAL SERVICE
        • NETWORK SERVICE
        • SERVICE accounts
      • MS implemented to prevent
        • unauthed user from creating a service or server app
        • server apps impersonating clients connecting to it
      • Example:
        • Remote Procedure Call (RPC)
        • named pipes

Other privileges that may lead to privilege escalation are SeBackupPrivilege, SeAssignPrimaryToken, SeLoadDriver, and SeDebug. In this section, we'll closely inspect privilege escalation vectors in the context of SeImpersonatePrivilege.

  • IRL it is rare to find standard users with this priv
    • however, we often find it when exploiting vulns in ISS we server apps
      • ISS will run as LocalService, LocalSystem, NetworkService, or ApplicationPoolIdentity
        • all having SeImpersonatePrivilege assigned
        • also applies to other Win service

Let's briefly discuss named pipes and how to leverage SeImpersonatePrinilege to impersonate a priv user account!

  • named pipe are one method for local or remote Inter-Process Communication (IPC)
    • offer func of two unrelated procs sharing/transfering data
    • a named pipe server can create a named pipe that a named pipe client can connect to via specified name
    • server/client do not need to be on the same sys
  • Once a client connects to a named pipe
    • server can leverage SeImpersonatePrivilege to impersonate this client
      • after capturing auth from the connection proc
  • To abuse, we need to coerce a priv proc to connect to a controlled named pipe
    • we can them impersonate the account connecting to the named pipe
    • performing actions in its security context

      • coerce NT AUTHORITY\SYSTEM into connecting to controlled named pipe
