13.1 Fixing Memory Corruption Exploits

  • Understand high-level buffer overflow theory
  • Cross-compile binaries
  • Modify and update memory corruption exploits

Buffer Overflow in a Nutshell

  • buffer
    • a memory area intended to hold content, sent by user, for later processing
  • Buffer Overflow
    • One of the earliest mem corruption exploits
      • circa late 1980s
    • Still relevant today despite mitigation
  • Occurs when user provided content goes beyond the stack limit and over-runs into adjacent mem space.
  • Example;
| 8-byte buffer                 | Overflow by 2-bytes |
| A | B | C | D | E | F | G | H | 0 | 1 |
  • A buffer designed to contain and 8 byte buffer, for a password of 8 chars
  • If password43 was sent, the buffer would overflow by 2 bytes 43
  • If not handled correctly, buffer-overflow may be possible
  • Although writing buffer overflow exploits is beyond the scope of the course, we're learning how they work so that we can understand when and how to adjust them whenever we encounter these attack vectors during an engagement.

This type of vuln can occur in heap or stack.

  • heap
    • dynamically managed
    • stores large chunks of global data
  • stack
    • stores local function data
    • size generally fixed
    • often contains;
      • local vars
        • integers
        • buffers
  • Example;
*buffer[64]*
...
strcpy(buffer, argv[1]);
  • a 64 char buffer declared
  • user command line argument copied in via strcpy
    • copies source string, second param
    • to buffer, first param
  • This function is unsafe;
    • it does not check the destination address to see if there is enough space to fit the source string.
  • The stack makes room for;
    • exact buffer space, 64 bytes for 64 chars
    • function params
    • return address
  • If the user input is bigger than the dest buffer space, they can overwrite the return address
    • When the function ends, it execs the ret address
      • loading the ret address inside EIP/RIP (the instruction pointer)
    • If you control the return address, you may be able to control program flow
  • A typical buffer overflow attack scenario involves overwriting the return address with a JMP ESP instruction, which instructs the program to jump to the stack and execute the shellcode that has been injected right after the beginning of the payload.

Mitigation

  • ASLR
  • Executable Space Protection

General Flow of Stack-Based Buffer Overflow

  1. Create large buffer to trigger overflow
  2. Overwrite return address by padding buffer with appropriate offset, taking control of EIP
  3. Include chosen payload in buffer prepended by an optional NOP sled
  4. Choose correct return address instruction to redirect exec flow to payload, JMP ESP or appropriate register
  • As we fix the exploit for our use, we may need to modify elements
    • file paths
    • IPs
    • ports
    • URLs
  • If those modifications alter the offset, we must adjust buffer length
    • ensuring we overwrite the ret address
  • It's always best to verify the return address ourselves
    • clone the target env locally in a VM
    • use a debugger to obtain the mem address of the return address instruction
  • We must also changes the payload contained in the OG Exploit
    • There is inherent danger in running unknown hex encoded payloads
    • Either decode and review or apply our own

Creating our own payloads

  • We include our IP address, port, and exclude bad chars
    • bad chars can be determined independently or gleaned from code
  • Bad Chars are ASCII or UNICODE chars that break the application when included in the payload
    • may be interpreted as control chars
      • null-byte \x00 is often a string terminator, which could truncate the attack buffer

Creating our own is advised when possible. In some cases the attack relies on the payload itself, in this case we must reverse engineer the payload to see what it is doing and if it is safe to exec.

Changing the Overflow Buffer

We know that we have an offset misalignment. Our padding buffer is all "A" chars, the call to malloc with size 780 creates it.

int initial_buffer_size = 780;
char *padding = malloc(initial_buffer_size);
  • Previously we established 780 as the byte offset required to overwrite the ret addr and take control of the EIP reg
  • malloc only allocates a block of mem
  • the buffer must be initialized with memset, called after malloc
memset(padding, 0x41, initial_buffer_size);
  • This fills the memory allocated with a char
    • 0x41, hex for A
  • On the next line, a call to memset sets the last byte to a NULL byte
memset(padding + initial_buffer_size - 1, 0x00, 1);
  • Here, the final buffer is created
char *buffer = malloc(buffer_length);
memset(buffer, 0x00, buffer_length);
strcpy(buffer, request_one);
strcat(buffer, content_length_string);
strcat(buffer, request_two);
strcat(buffer, padding);
strcat(buffer, retn);
strcat(buffer, shellcode);
strcat(buffer, request_three);
  • a memory block is allocated for the buffer with malloc
    • it gets filled with NULL bytes
  • next, the buffer is filled by copying contents of the other vars with strcpy and strcat
  • Knowing that the final buffer must be a string is important
    • In C there are NULL-terminated strings
    • The aforementioned functions determine the end/size of a string by searching for the first NULL byte occurrence
  • Our initial buffer of 780, with last byte set to 0x00 , our concat results in a string of ASCII A that is 779 bytes in len
    • this explains the misalignment
  • To fix; increase the requested size of inital_buffer_size variable by 1
    int initial_buffer_size = 781;
    char *padding = malloc(initial_buffer_size);
    memset(padding, 0x41, initial_buffer_size);
    memset(padding + initial_buffer_size - 1, 0x00, 1);
  • This time, when we set our breakpoint and run the exploit
    • We hit the breakpoint with the correct ret addr
    • Hit F9 to continue and we get a rev shell to our listener!

13.2 Fixing Web Exploits

  • Fix web application exploits
  • Troubleshoot common web application exploit issues

Considerations and Overview

  • Key questions when modding web exploits;
  • Does it initiate an HTTP or HTTPS connection?
  • Does it access a specific web application path or route?
  • Does the exploit leverage a pre-authentication vulnerability?
  • If not, how does the exploit authenticate to the web application?
  • How are the GET or POST requests crafted to trigger and exploit the vulnerability? Is there any HTTP method involved?
  • Does it rely on default application settings (such as the web path of the application) that may have been changed after installation?
  • Will oddities such as self-signed certificates disrupt the exploit? Be aware of measures such as ".htaccess" and WAF
