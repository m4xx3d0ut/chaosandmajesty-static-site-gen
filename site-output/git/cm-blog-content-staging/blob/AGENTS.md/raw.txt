# Repository Guidelines

## Project Structure & Module Organization
- `sources/` stores research notes grouped by topic (for example `sources/OffSec/`). Keep supporting images in `sources/_resources/` so they ship with the draft that references them.
- `content/` holds publish-ready Markdown ready to be formated for the static site generator, you can derive our "tone" and writing style from these works; place final posts under `blog/<slug>.md` and keep working copies elsewhere until the metadata is complete.
- `templates/blog-model.md` documents the downstream layout, required front matter, and generator inputs—treat it as the source of truth and update it if the build contract changes.

## Content Conversion Workflow
- Structure posts derived from `sources/` notes with a concise `## TLDR;` section followed by `## Working Notes... In Graphic Detail...` that preserves the primer detail.
- Sanitize workstation identifiers (`m4xx3d0ut`, `h4ckt0p`, etc.) and private addresses such as `192.168.29.0/24`, swapping in neutral stand-ins like `operator@labhost` or `192.0.2.0/24` before publishing.
- Trim the working notes before the final `#### Exercises` block unless the exercise content is intentionally part of the post.
- While polishing the working notes, expand shorthand lists into readable sentences and fix spelling/grammar where context makes the intention clear; leave ambiguous fragments untouched and flag them for review.


## Build, Test, and Development Commands
- `npx markdownlint-cli "sources/**/*.md" "content/**/*.md"` — run before every PR to catch heading levels, spacing, and trailing whitespace; install `markdownlint-cli` globally if you prefer.
- `make preview` (in the sibling `chaosandmajesty-static-site-gen` project) — launches the static-site preview with HTMX routing so you can validate navigation against your updates.
- `./build-site.sh` (same project) — produces the deployable HTML bundle; use it for pre-release smoke checks.

## Coding Style & Naming Conventions
- Front matter must follow the contract in `templates/blog-model.md`: include `title`, `slug`, `author`, `summary`, ISO 8601 `publishedAt`/`updatedAt`, `readingMinutes`, and optional `tags`/`heroImage`.
- Final filenames use lowercase, hyphenated slugs (e.g. `content/blog/offsec-labs-week-01.md`); avoid spaces or uppercase characters once a post leaves `sources/`.
- Prefer ATX headings (`##`), wrap prose near 100 characters, and annotate fenced code blocks with language hints to improve highlighted output.

## Testing Guidelines
- Linting plus preview clicks are the primary quality gates; there are no automated unit tests for this repository.
- Verify the generated list, article fragment, and hero media render correctly when running `make preview`.
- Use `<!-- TODO -->` markers only for short-lived follow-ups and convert them to tracked issues before merge.

## Commit & Pull Request Guidelines
- Write commits in imperative present tense ("Add OffSec chapter summaries") and group related asset updates with the content change they support.
- PRs should link the driving issue, summarise reader impact, and attach a screenshot or preview URL for visual tweaks.
- Request review from another content maintainer and note any deferred follow-up tasks in the PR description checklist.
