#### 22.1 Understanding Active Directory Authentication

- Understand NTLM Authentication.
- Understand Kerberos Authentication.
- Become familiar with cached AD Credentials.

In this Learning Unit, we'll discuss the details of [NTLM](https://en.wikipedia.org/wiki/NT_LAN_Manager) and [Kerberos](https://en.wikipedia.org/wiki/Kerberos_(protocol)) authentication. In addition, we'll explore where and how AD credentials are cached on Windows systems.

##### NTLM Authentication

We briefly discussed what NTLM is and how to recover its hashes in Password Attacks.  Now we will explore it in the context of AD.

[NTLM auth](https://blogs.msdn.microsoft.com/chiranth/2013/09/20/ntlm-want-to-know-how-it-works/) is used to auth a client to a server when connecting by IP address, instead of hostname, or if the user attempts to auth to a hostname that is not registered on the AD integrated DNS server.  Also, 3rd party apps may use NTLM instead of Kerberos.

The 7 steps of NTLM proto consist of:
![da83831f0dd967c8c67585fcd2110c12.png](../_resources/da83831f0dd967c8c67585fcd2110c12.png)

In the first step the system calculates the cryto hash, known as NTLM hash, from the user's password.  Next, the client computer sends the username to the server, which returns a "nonce" or challenge.  The client encrypts the none using the NTLM hash and sends it in the response to the server.

The server forwards the response with the username and nonce to the DC, which already knows the NTLM hash of all users.  The DC encrypts the nonce with the NTLM hash of the username and compares it to the response recieved from the server.  If equal, auth request succeeds.

NTLM cannot be reversed, but as it is a fast hashing algo short passwords can be cracked quickly using modest equipment.

*By using cracking software like Hashcat with top-of-the-line graphic processors, it is possible to test over 600 billion NTLM hashes every second. This means that eight-character passwords may be cracked within 2.5 hours and nine-character passwords may be cracked within 11 days.*

Even with the relative weakness of NTLM, disabling or blocking it requires extensive [planning and prep](https://techcommunity.microsoft.com/t5/ask-the-directory-services-team/ntlm-blocking-and-you-application-analysis-and-auditing/ba-p/397191), it's an important fallback and used by many 3rd party apps.  We will encounter NTLM auth in the majority of assesments.

Now that we have a general understanding of AD NTLM, we will explore Kerberos in the next section, the default auth proto in AD and for assocatied services.

##### Kerberos Authentication

MS Kerberos was adopted from Kerberos v5 created by MIT.  Kerberos has been the primary auth mechanism since Win Server 2003.  NTLM works via challenge/response, where Kerberos uses a ticket system.

In NTLM auth, the client starts the auth process with the app server itself, whereas in Kerberos auth the DC takes the role of a [Key Distribution Center (KDC)](https://blogs.msdn.microsoft.com/chiranth/2013/09/20/ntlm-want-to-know-how-it-works/).  The client starts the auth process with the KDC, not the app server.  A KDC service runs on each DC and is responsible for session tickets and temporary session keys to users and computers.

The client auth process at a high level:
![22acd580bc7d406fa3a4e26113a52ef3.png](../_resources/22acd580bc7d406fa3a4e26113a52ef3.png)

The process in detail; when a user logs in to a workstation, an Authentication Server Request (AS-REQ) is sent to the DC.  The DC acting as KDC also maintains the Auth Server Service.  The AS-REQ contains a timestamp encrypted using a hash derived from the password of the user and their username.

The DC receives the request and looks up the password hash associated with the specific user in the [ntds.dit](https://attack.mitre.org/techniques/T1003/003/) file and attempts to decrypt the timestamp.  If decryption succeeds and the timestamp is not a duplicate, the auth is successful.

*If the timestamp is a duplicate, it could indicate evidence of a potential replay attack.*

Next the DC replies the client with an Authentication Server Reply (AS-REP).  Kerberos is a stateless proto, the AS-REP contains a session key and a Ticket Granting Ticket (TGT).  The session key is encrypted with the user's password hash and can be decrypted by the client then reused.  the TGT contains info regarding the user, domain, timestamp, IP of the client, and the session key.

The TGT is encrypted by a secret key (NTLM hash of the [krbtgt](https://adsecurity.org/?p=483) account) known only by the KDC and cannot be decrypted by the client to avoid tampering.  After the client receives the session key and the TGT, the KDC considers the client auth complete.  The TGT will be valid for 10 hours by default, at which point a renewal occurs.  This does not require the user to enter a password.

When the user wants to access domain resources, network share or mailbox for example, it must again contact the KDC.

This time the client contructs a Ticket Granting Service Request (TGS-REQ) packet that consists of the current user and a timestamp encrypted with the session key, the name of the resource, and the encrypted TGT.

Next the ticket-granting service on the KDC receives the TGS-REQ, if the resource exists in the domain, the TGT is decrypted using the secret key known only to the KDC.  The session key is then extracted from the TGT and used to decrypt the username/timestamp of the request.  At this point the KDC performs a set of checks:
- The TGT must have a valid timestamp.
- The username from the TGS-REQ has to match the username from the TGT.
- The client IP address needs to coincide with the TGT IP address.
If successful, the ticket-granting service responds to the client with a Ticket Granting Server Reply (TGS-REP), which contains three parts:
- The name of the service for which access has been granted.
- A session key to be used between the client and the service.
- A service ticket containing the username and group memberships along with the newly-created session key.
The ticket's service name and session key are encrypted using the original session key associated with the creation of the TGT.  The service ticket is encrypted using the password hash of the service account registered with the service in question.

Once the auth process is completed by the KDC and the client has the session key and a service ticket, the service auth begins.

The client first sends the app server an Application Request (AP-REQ) including the username and a timestamp encrypted with the session key associated with the service ticket and the service ticket itself.

The app server decrypts the service ticket using the service acocunt password hash and extracts the username/session key.  It uses the latter to decrypt the username from the AP-REQ, if the username matches the on decrypted from the service ticket, the request is accepted.  Before granting access, the service inspects the group memberships in the service ticket and assigns the user perms, after which the user may access the requested service.

This proto may seem complex, but it was designed to mitigate various network attacks and prevent use of fake creds.  Next we will explore cahced cred storage and service account attacks.

##### Cached AD Credentials

We will first discuss the password hashes used in Kerberos and show how they are stored to lay the foundation of chached storage attacks and lateral movement vectors.

We covered some of this information in the Password Attacks module.  In this section we'll focus on cached credentials and tickets in the context of AD.

The MS implementation of Kerberos utilizes SSO, password hashes must be stored somewhere in order to renew a TGT request.

These hashes are stored in the [Local Security Authority Subsystem Service (LSASS)](https://en.wikipedia.org/wiki/Local_Security_Authority_Subsystem_Service) [memory space](https://adsecurity.org/?page_id=1821).

If we can access these hashes we could crack them to obtain cleartext passowrds or reuse them in attacks.

This is the end goal of our AD attack, but the process is not straightforward.  Since the LSASS process is part of the OS and runs as SYSTEM we must obtain SYSTEM (or local admin) perms to access the hashes stored on the target sys.

As such, we must first begin with PrivEsc in order to retrieve the hashes.  Adding to the complexity, the data structures that store the hashes in memory are not publicly documented and are encrypted with a LSASS-stored key.

Regardless of this, extraction of the cached creds is a big attack vector against Win/AD and several tools exist for this purpose.  The most popular is Mimikatz.

#### 22.2 Performing Attacks on Active Directory Authentication

- Use password attacks to obtain valid user credentials.
- Abuse enabled user account options.
- Abuse the Kerberos SPN authentication mechanism.
- Forge service tickets.
- Impersonate a domain controller to retrieve any domain user credentials.

##### Password Attacks

Previously we examined several password attacks on network services and hashed information, they are also a viable option to obtain AD user creds.

Before going into detail, we must account for one important factor.  When running brute force or wordlist attacks, we must be aware of account lockouts.  A number of failed logins may result in the account being blocked and possibly alert the SA.

To learn more about lockouts, review the domain account policy as domain user `jeff` on CLIENT75.  We can connect to the sys with password `HenchmanPutridBonbon11` via RDP, open PowerShell, and exec `net accounts` to obtain the account policy.
```powershell
PS C:\Users\jeff> net accounts
Force user logoff how long after time expires?:       Never
Minimum password age (days):                          1
Maximum password age (days):                          42
Minimum password length:                              7
Length of password history maintained:                24
Lockout threshold:                                    5
Lockout duration (minutes):                           30
Lockout observation window (minutes):                 30
Computer role:                                        WORKSTATION
The command completed successfully.
```
- Lockout threshold.
 - Limit of 5 login attempts before lockout.
  - We can safely attempt 4 logins before a lockout is triggered.
 - Lockout observation window.
  - 30 minutes after the last failed login we can make additional attempts.

This would allow us to attempt 192 logins in a 24 hr period against every domain user without triggering a lockout, assuming the actual users don't fail a login attempt.

This might consist of compiling a short list of very common passwords to leverage against a large amount of users.  This type of attack can reveal quite a few weak account passwords in the org.

This would also generate a huge amount of network traffic.  Let's review 3 kinds  of passowrd spraying attacks that have a higher chance of success in an AD env.

The first uses LDAP and ADSI to perform a "low and slow" password spray attack against AD users.  We previously performed queries against the DC as a logged-in user with [DirectoryEntry](https://docs.microsoft.com/de-de/dotnet/api/system.directoryservices.directoryentry?view=dotnet-plat-ext-6.0), but we can also make queries in the context of a different user by setting the DirectoryEntry instance.

In the AD Introduction and Enumeration module we used `DirectoryEntry` constructor without args, but we can provide 3, including the LDAP path to the DC, the username, and the password.
```powershell

Path              : LDAP://DC1.corp.com/DC=corp,DC=com
```
- As shown above, if the password of the user account is correct the object creation will be successful.

##### AS-REP Roasting

As we learned, the first step in the Kerberos auth process is to send an AS-REQ.  the DC can validate if the auth succeeds, if so the DC replies with a AS-REP containing the session key and TGT.  This step is also know as [Kerberos Preauthentication](https://social.technet.microsoft.com/wiki/contents/articles/23559.kerberos-pre-authentication-why-it-should-not-be-disabled.aspx) which prevents offline password guessing.

Without Kerberos preauthentication, an attacker could send an AS-REQ to the DC on behalf of an AD user.  Once the AS-REP has been obtained from the DC, the attacker could execute an offline password attack against the encrypted part of the response.  This is known as [AS-REP Roasting](https://harmj0y.medium.com/roasting-as-reps-e6179a65216b).

By default, the AD user account option *Do not require Kerberos preauthentication* is disabled, meaning Kerberos preauthentication is performed by all users.  However, it's possible to enable this account option manually.  During an assesment, we may find accounts with this option enabled as some apps and technologies require it to function properly.

Let's perform this attack from our Kali machine first, then from Win.  On Kali, we can utilize [impacket-GetNPUsers](https://github.com/SecureAuthCorp/impacket/blob/master/examples/GetNPUsers.py) to perform AS-REP roasting. ##### Kerberoasting

With Kerberos, when a user wants to access a SPN hosted resource, the client requests a service ticket generated by the DC.  The service ticket is decrypted and validated by the app server, since it was encrypted with the password hash of the SPN.

When the service ticket is requested from the DC, no checks are performed to confirm whether the user has any permissions to access the service hosted by the SPN.

These checks are only performed during the second step when connecting to the service itself, thus we can request a service ticket, provided we know what SPN we want to target, from the DC.

The service ticket is encrypted with the SPN's password hash, if we are able to request the ticket and decrypt it, via brute force or wordlist, we can use this info to crack the cleartext password of the service account, a technique known as [Kerberoasting](https://blog.harmj0y.net/redteaming/kerberoasting-revisited/).

As an example we will abuse a service ticket and attempt to crack the service account password.  Start by connecting to CLIENT75 via RDP as `jeff`.

We will use Rubeus again, specifying the `kerberoast` command, providing `hashes.kerberoast` as the `/outfile` arg to store the TGS-REP hash in.  Sine we exec Rubeus as an authenticated domain user, the tool will ID all SPNs linked with a domain user.

Note that during an assessment, we should delete the SPN once we obtain the hash to avoid adding vulnerabilities into client infrastructure.

##### Silver Tickets

We previously obtained and cracked a TGS-REP hash to retrieve the plaintext password of a SPN, we will further this by forging our own service tickets.

In Kerberos auth, the AS executing in the service account context checks the user perms from the group memberships included in the service ticket.  In the majority of envs the perms in the service ticket are not verified by the app, it blindly trusts the integrity of the service ticket as it has been encrypted with a password hash that, in theory, is only known to the service account and DC.

[Privileged Account Certificate (PAC)](https://docs.microsoft.com/en-us/openspecs/windows_protocols/ms-pac/166d8064-c863-41e1-9c23-edaaa5f36962) [validation](https://docs.microsoft.com/en-us/openspecs/windows_protocols/ms-apds/1d1f2b0c-8e8a-4d2a-8665-508d04976f84) between the SPN application and the DC is an optional verification process.  If enabled, the user authing to the service and their privs are validated by the DC.  Luckily, service apps rarely utilize PAC validation.

Example, if we auth against an IIS server running in the `iis_service` account context, the IIS app determines which perms we have on the IIS server based on the group membership present in the service ticket.

With a service account password or its NTLM hash on hand, we can forge service tickets to access the target resources, the IIS application in the case, with any perms we choose.  These custom forged tickets are known as a [silver ticket](https://adsecurity.org/?p=2011), if the service principal name is used on multiple servers, the silver ticket and be used against them all.

In this example, we'll create a silver ticket to access an HTTP SPN resource.  As we know, the `iis_service` account is mapped to the HTTP SPN, so the password hash of the user account is used to create its service tickets.  Let's assume we identified that the `iis_service` user has established a session on CLIENT75.

We would need to collect the following 3 pieces of info to create a silver ticket.
- SPN password hash.
- Domain SID.
- Target SPN.

##### Domain Controller Synchronization

In prod env, domains typically employ multiple domain controllers for redundancy.  [The Directory Replication Service (DRS) Remote Protocol](https://msdn.microsoft.com/en-us/library/cc228086.aspx) uses [replication](https://technet.microsoft.com/en-us/library/cc772726(v=ws.10).aspx) to syncronize redundant DCs.  A DC can request an update for a specific object, an account for example, using [IDL_DRSGetNCChanges](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-drsr/b63730ac-614c-431c-9501-28d6aca91894) API.

Conveniently, the DC that recieves the request to update does not check if the request came from a known DC, it only verifies that the associated SID has appropriate privs.  If we issue a rogue update request to a DC from a user with proper rights, it will succeed.

To start a replication, a user needs to have rights:
- Replicating Directory Changes.
- Replicating Directory Changes All.
- Replicating Directory Changes in Filtered Set.
*Members of Domain Admins, Enterprise Admins, and Administrators groups have them by default.*

If we obtain access to a user account in a group with these rights, we can perform a [dcsync](https://adsecurity.org/?p=2398#MimikatzDCSync) attack by impersonating a DC, allowing us to request any user creds from the domain.

To perform this attack, we use Mimikatz on a domain joined machine or [impacket-secretsdump](https://github.com/SecureAuthCorp/impacket/blob/master/examples/secretsdump.py) on a non-domain joined Kali system.
