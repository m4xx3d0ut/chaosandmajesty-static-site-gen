Private CA on MicroK8s (Flux GitOps)

cert-manager + trust-manager + CA Portal Final state: “Secure mode” (HTTPS + HSTS) with a clean base/overlays layout

0) What you get

  • Local Root CA (cert-manager) and ClusterIssuer for internal TLS
  • trust-manager bundle that fans the public root into labeled namespaces
  • CA Portal website to download the CA in PEM and DER, with install steps
  • Overlays: “bootstrap” (HTTP, no HSTS) and “secure” (HTTPS, HSTS). We run Secure in prod.

1) Prereqs

  • MicroK8s with NGINX Ingress enabled
  • Flux bootstrapped
  • DNS for portal (e.g., ca.core.home.arpa) → Ingress address
  • Repo layout under gitops/ (examples below)

2) Repository layout (final, cycle-free)

gitops/
└─ apps/
   └─ ca-portal/
      ├─ base/
      │  ├─ deploy.yaml
      │  ├─ ingress.yaml         # HTTP-only; overlays patch TLS/HSTS
      │  ├─ kustomization.yaml   # generates ConfigMap from site/index.html
      │  ├─ namespace.yaml
      │  └─ site/index.html
      └─ overlays/
         ├─ bootstrap/
         │  └─ kustomization.yaml   # references ../../base (no TLS)
         └─ secure/
            ├─ certificate.yaml     # cert-manager Certificate (org-ca)
            ├─ kustomization.yaml   # references ../../base + patches
            └─ patch-ingress-secure.yaml
└─ infra/
   ├─ cert-manager/      # ns, HelmRelease, CA bootstrap (root + ClusterIssuer)
   ├─ trust-manager/     # HelmRelease (install/upgrade CRDs = Create)
   └─ trust-bundle/      # Bundle CR in separate Kustomization (no race)
└─ clusters/microk8s-prod/kustomizations/
   ├─ infra-cert-manager.yaml
   ├─ infra-trust-manager.yaml
   ├─ infra-trust-bundle.yaml   # dependsOn: infra-trust-manager
   └─ apps-ca-portal.yaml       # path -> ./gitops/apps/ca-portal/overlays/secure

Why this shape? Keeping overlays outside the base prevents Kustomize parent/child cycles. Overlays point to ../../base.

gitops/infra/trust-bundle/bundle.yaml

apiVersion: trust.cert-manager.io/v1alpha1
kind: Bundle
metadata:
  name: org-root-bundle
  namespace: cert-manager
spec:
  sources:
    - secret:
        name: org-root-ca-secret
        key: tls.crt      # no namespace field here
  target:
    configMap: { key: ca.crt }
    namespaceSelector:
      matchLabels: { trust-bundle: "true" }

apiVersion: apps/v1
kind: Deployment
metadata: { name: ca-portal, namespace: ca-portal }
spec:
  replicas: 1
  selector: { matchLabels: { app: ca-portal } }
  template:
    metadata: { labels: { app: ca-portal } }
    spec:
      initContainers:
        - name: make-der
          image: alpine:3.20
          command: ["/bin/sh","-c"]
          args:
            - |
              set -euo pipefail
              apk add --no-cache openssl
              cp /ca/ca.crt /work/org-root-ca.crt
              openssl x509 -outform der -in /ca/ca.crt -out /work/org-root-ca.der
          volumeMounts:
            - { name: ca-bundle, mountPath: /ca }
            - { name: downloads, mountPath: /work }
      containers:
        - name: nginx
          image: ghcr.io/nginxinc/nginx-unprivileged:alpine
          ports: [ { containerPort: 8080 } ]
          volumeMounts:
            - { name: site, mountPath: /usr/share/nginx/html }
            - { name: downloads, mountPath: /usr/share/nginx/html/downloads }
      volumes:
        - name: site
          configMap: { name: ca-portal-site }
        - name: downloads
          emptyDir: {}
        - name: ca-bundle
          configMap:
            name: org-root-bundle
            items: [ { key: ca.crt, path: ca.crt } ]
---
apiVersion: v1
kind: Service
metadata: { name: ca-portal, namespace: ca-portal }
spec:
  selector: { app: ca-portal }
  ports: [ { port: 80, targetPort: 8080 } ]

After org-root-ca-secret is Ready:

12) Common pitfalls (and fixes)

  • Kustomize cycle: overlays must be sibling of base. In overlays’ kustomization.yaml, reference ../../base (not ../ nor ../../ pointing at the folder that contains overlays).
  • Bundle schema: don’t put namespace: under spec.sources.secret for trust-manager v0.10.0.
  • HSTS gotcha: if you ever served the portal with HSTS, Chrome can force HTTPS while in bootstrap. Clear chrome://net-internals/#hsts for the host, or use the bootstrap overlay hostname temporarily.
  • Nginx “Fake Certificate”: means the Ingress secret isn’t referenced/ready. Ensure certificate Ready, secret present, ingress.spec.tls[].secretName correct. If needed, rollout restart deploy/ingress-nginx-controller.

13) Cleanup

Remove app folders and Flux Kustomizations; Flux will prune:

git rm -r gitops/apps/ca-portal gitops/infra/trust-bundle gitops/infra/trust-manager gitops/infra/cert-manager
# and their cluster kustomizations
git commit -m "cleanup: remove private CA stack"
git push

Notes

  • The portal only ever mounts the public cert via ConfigMap; it never sees the private key.
  • For fleets, consider enabling Chrome/Chromium ImportEnterpriseRoots policy or importing your CA into NSS with certutil.
  • Prefer an offline root + in-cluster intermediate for long-term ops.

Extended: App TLS Setup & Troubleshooting

A) App TLS wiring pattern (the “one file per app” rule)

Goal: each app/hostname has a Certificate in the same namespace as the app/ingress, and the Ingress tls.secretName points to it. TLS terminates at ingress-nginx.

Template

gitops/apps/<app>/
  ├─ kustomization.yaml         # includes release/manifests + certificate
  ├─ release.yaml               # (if HelmRelease)
  ├─ ingress.yaml               # has tls[].secretName that matches the Certificate
  └─ certificate-<app>.yaml     # cert-manager Certificate for the host

Certificate (generic)

apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: <app>-tls
  namespace: <app-namespace>
spec:
  secretName: <app>-tls
  dnsNames: ["<host.example.local>"]
  issuerRef: { name: org-ca, kind: ClusterIssuer }
  privateKey: { algorithm: RSA, size: 2048 }
  # duration/renewBefore optional; cert-manager sensible defaults are fine

Ingress (generic)

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: <app>
  namespace: <app-namespace>
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"
spec:
  ingressClassName: nginx          # be explicit; avoids multi-controller surprises
  tls:
    - secretName: <app>-tls
      hosts: ["<host.example.local>"]   # must EXACTLY match rule host
  rules:
    - host: <host.example.local>
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: <svc>, port: { number: 80 } } }

Kustomization (generic)

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - release.yaml        # if HelmRelease is used
  - ingress.yaml
  - certificate-<app>.yaml

Namespace needs the trust bundle only if pods validate internal TLS

kubectl label namespace <app-namespace> trust-bundle=true --overwrite

Mount/use org-root-bundle only when workloads must trust other internal services. Ingress itself does not need this.

Heads-up: Ingress cert/secret updates do not roll your app Pods; nginx hot-reloads the secret.

C) Troubleshooting matrix (symptom → cause → fix)

1) Browser/openssl shows “Kubernetes Ingress Controller Fake Certificate”

Cause: nginx is not using your TLS secret (Ingress not admitted or host/secret mismatch). Fix:

# bind to the right controller
kubectl -n <ns> patch ingress <app> --type=merge -p '{"spec":{"ingressClassName":"nginx"}}'

# ensure TLS hosts EXACTLY match the rule host
kubectl -n <ns> patch ingress <app> --type=json \
  -p='[{"op":"replace","path":"/spec/tls/0/hosts","value":["<host>"]}]'

# nudge reload if needed
kubectl -n ingress-nginx rollout restart deploy/ingress-nginx-controller

2) curl works with -k but fails without it as “self-signed”

Cause (A): client doesn’t trust your org root. Install the CA. Cause (B): nginx is serving its default self-signed (see #1). Fix: For (A) import CA; for (B) fix Ingress admission/hosts/secret as above.

3) Certificate stuck READY=False or no Secret created

Cause: issuer not Ready, approver/controller stuck, or CSR sign error. Fix:

# describe shows exact reason
kubectl -n <ns> describe certificate <app>-tls
kubectl -n <ns> get certificaterequests \
  -l cert-manager.io/certificate-name=<app>-tls
kubectl -n <ns> describe certificaterequest <name>

# issuer + CA secret healthy?
kubectl get clusterissuer org-ca -o yaml | sed -n '1,120p'
kubectl -n cert-manager get secret org-root-ca-secret

# restart cert-manager if controllers look wedged
kubectl -n cert-manager logs deploy/cert-manager --tail=200

4) Certificate Ready but Secret looks wrong or nginx ignores it

Cause: stale/invalid secret data. Fix: delete secret + force re-issue (safe; pods won’t roll):

kubectl -n <ns> delete secret <app>-tls --ignore-not-found
kubectl -n <ns> annotate certificate <app>-tls \
  cert-manager.io/renewal-reason=force-rotate-$(date +%s) --overwrite
kubectl -n <ns> get certificate <app>-tls -w

5) Multiple Ingress controllers present

Cause: wrong controller picking (no default class). Fix: set spec.ingressClassName: nginx on every Ingress and verify DNS points to the nginx controller Service IP.

6) Hostname mismatch between rules[].host and tls[].hosts[]

Cause: SNI mismatch → default cert served. Fix: make them identical (string-equal).

7) HSTS forces HTTPS during bootstrap

Cause: browser cached HSTS from earlier. Fix: use the HTTP-only bootstrap overlay or clear HSTS (chrome://net-internals/#hsts).

D) Operations & hygiene

  • Names & shape: certificate-<app>.yaml, secret =<app>-tls, keep per-app in app namespace.

  • Rotation: instant re-issue:

    kubectl -n <ns> annotate certificate <app>-tls cert-manager.io/renewal-reason=force-$(date +%s) --overwrite

  • Secret recreation: delete the TLS secret to have cert-manager recreate it (safe for Ingress).

  • No pod restarts: Ingress terminates TLS; app pods unaffected by cert renewals.

  • Durations: leave defaults or set duration/renewBefore per app; central policy via Kustomize patches if desired.

  • Trust bundle: label namespaces that need to trust your internal root: kubectl label ns <ns> trust-bundle=true --overwrite

  • Flux ordering: cert-manager → trust-manager → trust-bundle → apps (use dependsOn in cluster Kustomizations).

F) “Why am I still seeing the fake cert?” (90-second checklist)

  1. kubectl -n <ns> get secret <app>-tls → exists and type=kubernetes.io/tls?

  2. kubectl -n <ns> get ingress <app> -o yaml → ingressClassName: nginx and exact host match under tls.hosts + rules.host?

  3. kubectl get ingressclass → do you have a default class? If not, step 2 is mandatory.

  4. kubectl -n ingress-nginx logs deploy/ingress-nginx-controller --tail=200 → any “secret not found/invalid” lines?

  5. Restart controller once to force reload:

    kubectl -n ingress-nginx rollout restart deploy/ingress-nginx-controller

Bonus: quick “SNI vs Secret” diff helper

HOST=<host.example.local>; NS=<ns>; SEC=<app>-tls
echo "== served cert =="
openssl s_client -connect ${HOST}:443 -servername ${HOST} </dev/null 2>/dev/null \
 | openssl x509 -noout -subject -issuer -fingerprint -sha256
echo "== secret cert =="
kubectl -n ${NS} get secret ${SEC} -o jsonpath='{.data.tls\.crt}' \
 | base64 -d | openssl x509 -noout -subject -issuer -fingerprint -sha256

If both fingerprints match, nginx is serving your secret. If not, fix the Ingress binding/hosts.
