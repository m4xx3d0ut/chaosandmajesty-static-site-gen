TLDR;

Lateral movement is about chaining the credentials you captured in Module 22. This update integrates the lab’s command sequences and persistence tricks.

Remote Execution Channels

# WMI exec

  • Log hostnames, credentials, commands executed, and artifacts left behind. Remove services and temp files when done.

Credential Replay Techniques

  • Pass-the-Hash: Use crackmapexec smb to test credentials across hosts quickly.
  • Overpass-the-Hash: Convert NTLM hash into Kerberos ticket and spawn cmd.exe with elevated context.
  • Pass-the-Ticket: Inject TGT/TGS with mimikatz kerberos::ptt. Save *.kirbi files as evidence.

Document which hosts allowed each method and why (protocol support, missing protections).

Persistence Mechanisms

  • Golden Tickets: mimikatz kerberos::golden /user:Administrator /domain:corp.local /sid:S-1-5-21-... /krbtgt:<hash> /id:500 /ptt. Only demonstrate under strict approval; highlight the need to rotate KRBTGT twice.
  • WMI Event Subscription: Create persistent commands triggered by process creation; log GUIDs for cleanup.
  • Scheduled Tasks: schtasks /create /sc minute /mo 5 /tn UpdateCheck /tr "powershell -File C:\Windows\Temp\check.ps1" /RU SYSTEM.
  • Shadow Copies: vssadmin create shadow /for=C: to preserve data access.

Session Tracking & Documentation

  • Maintain a table: Account ➜ Host ➜ Technique ➜ Evidence ➜ Cleanup?.
  • Capture proof commands after each hop (hostname, whoami, ipconfig).
  • Record lateral movement path visualisations (draw.io, BloodHound path exports) for the report.

Defensive Recommendations

  • Enforce credential hygiene (LAPS, tiered admin model, disabling local admin reuse).
  • Monitor WMI, WinRM, SMB400 event logs, and Sysmon events 1/3/7 for remote execution.
  • Audit scheduled tasks and WMI subscriptions regularly.

Lateral movement is where engagements are won or lost. Keep impeccable notes, clean up after yourself, and deliver defenders a clear picture of how you traversed their environment.

WMI and WinRM

The first lateral movement technique we will discuss is based on Windows Management Instrumentation (WMI), an object oriented feature facilitating task automation.

WMI can create processes with the Create method of the Win32_Process class, communicating over Remote Proceedure Calls (RPC), port 135 for remote access and 19152-65535 for session data.

To demonstrate, we will go over the recently deprecated wmic utlity and then discover how to conduct the same WMI attack via PowerShell.

To create a proc on the remote WMI target, we need creds for a member of the local Administrators group, which can also be a domain user. In the following example, we will perform the attack as user jen who is both a domain user and local admin for the target machines.

We previously encountered UAC remote restrictions in non-domain member systems in the Password Attacks Module, but this restriction does not apply to domain users, therefore we can utilize full privs while moving laterally with the techniques shown here.

wmic has historically been abused for lateral movement through CLI by specifying the target IP to arg /node:, user /user:, and password /password:. We'll instruct wmic to launch calculator with the process call create keywords, test the command by connecting as jeff on CLIENT74.

C:\Users\jeff>wmic /node:192.168.50.73 /user:jen /password:Nexus123! process call create "calc"

Out Parameters:

        ProcessId = 752;

The WMI job returned the PID of the new proc and ret val 0, which indicates the proc was successfully created.

System processes and services always run in session 0 as part of session isolation, which was introduced in Windows Vista. Because the WMI Provider Host is running as a system service, newly created processes through WMI are also spawned in session 0.

Adapting the attack to PowerShell requires a few additional steps.

  • Create a PSCredential object.
  • Store username/password.
  • Secure that password with ConvertTo-SecureString
  • Create a new PSCredential object with the username and secureString object.
$username = 'jen';
$password = 'Nexus123!';
$secureString = ConvertTo-SecureString $password -AsPlaintext -Force;
$credential = New-Object System.Management.Automation.PSCredential $username, $secureString;

Next we create a Common Information Model (CIM) with cmlet New-CimSession by first specifying the DCOM proto for the WMI session with the New-CimSessionOption cmdlet the creating a new session to our target IP, supplying the PSCredential object along with session options. Finally we set calc as the payload to be executed by WMI.

$options = New-CimSessionOption -Protocol DCOM
$session = New-Cimsession -ComputerName 192.168.50.73 -Credential $credential -SessionOption $Options 
$command = 'calc';

Finally we tie the args together by issuing the Invoke-CimMethod cmdlet, supplying the Win32_Process and Create as -ClassName and -MethodName.

Invoke-CimMethod -CimSession $Session -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine =$Command};

An alternative to WMI is WinRM, which can also be used for remote host management. WinRM is the MS version of the WS-Management proto. It uses XML messages via HTTP/HTTPS, using TCP port 5986 for HTTPS and port 5985 for HTTP.

WinRM is implemented in many built-in utils, winrs (Windows Remote Shell), in addition to the PowerShell implementation.

PsExec

PsExec, part of the SysInternals suite developed by Mark Russinovich, is an extremely versitile tool intended to replace telnet-like applications and provide remote execution of processes on other systems through interactive console.

Misusing the tool for lateral movement has several prerequisites.

  • The user authenticating to the machine must be in local Admin group.
  • The ADMIN$ share must be available.
  • File/printer sharing has to be turned on.
  • Default setting on modern Win servers.

To achieve remote command exec, PsExec performs the following:

  • Writes psexecsvc.exe into C:\Windows directory.
  • Creates/spawns a service on the remote host.
  • Runs the requested command as a child proc of psexecsvc.exe

Let's assume we have RDP access as local admin offsec on CLIENT74, we can run the 64-bit version of PsExec from C:\Tools\SysinternalsSuite.

To start an interactive session on the remote host we invoke PsExec64.exe with arg -i, followed by target hostname which is prepended with \\. Specify corp\jen as domain\username and Nexus123! as password with -u/-p. Finally we include the command for remote exec, a cmd shell in this case.

Pass the Hash

Pass the Hash (PtH) allows an attack to auth to a remote system/service utilizing the NTLM hash of a users's password instead of the associated plaintext password. This will not work for Kerberos auth, but only for servers/services using NTLM auth. This is a sub-technique mapped in the MITRE Framework, under the "User Authentication Material" general technique.

There are many 3rd party tools and frameworks that us PtH for both auth and code exec, including PsExec from Metasploit, Passing-the-hash toolkit, and Impacket. They each use similar mechanics, where the attacker connects to the target using SMB proto and performs auth using the NTLM hash.

Most tols built for PtH abuse can start a Win service, a CMD or PS instance, and communicate with it using Named Pipes, which is done though the Service Control Manager API.

Unless we want to gain remote code execution, PtH does not need to create a Windows service for any other usage, such as accessing an SMB share.

Similar to PsExec, PtH requires a SMB conn through the firewall, typically on port 445, and Win File and Printer sharing feature enabled, both of which are common in enterprise envs.

The technique also requires the admin share ADMIN$ to be available. To establish the conn to the admin share, the attacker must present valid creds with local admin perms, thus it requires local admin rights.

PtH uses the NTLM hash legitimately, the vuln lies in the fact that we gain unauthorized access to the password hash of a local admin.

DCOM

Next we will explore a recent lateral movement technique that exploits DCOM (Distributed Component Object Model) and learn how to abuse it for lateral movement.

COM (Component Object Model) is a system for creating software components that interact with each other. COM was created for same/cross process interaction, but it was extended to DCOM for multi-computer interactions over a network.

COM and DCOM are old tech dating back to the first Win edition. DCOM interactions are performed via RPC port TCP 135, local admin access is required to call the DCOM Service Control Manager, essentially an API.

Cyberreason documented a collection of DCOM lateral movement techniques which are covered here, including one from Matt Nelson.

The discovered DCOM lateral movement technique is based on the MMC (Microsoft Management Console) COM app for scripted automation of Win systems.

The MMC app class allows the creation of Application Objects and exposes the ExecuteShellCommand method under the Document.ActiveView property. As the name suggests, this method allows execution of any shell command as long as the authenticated user is authorized, the default for local admins.

We will demonstrate this lateral movement attack as the jen user logged in from the pre-compromised Win 11 CLIENT74 host.

  • Directory.

  • WindowState. We are only interested in the first and third params, for which we will provide cmd and /c calc respectively.

Golden Ticket

In Kerberos auth, when a user submits a request for a TGT, the KDC encrypts the TGT with a secret key known only to the KDCs of the domain. This key is actually the password hash of domain user account krbtgt.

If we obtain the krbtgt password hash, we can create our own crafted TGTs, known as golden tickets.

Though resembling the Silver Ticket, Golden Tickets are a more powerful attack vector. Silver Tickets forget a TGS ticket to access specific services, where Golden Tickets give us permission to access the entire domain's resources.

Example, we could create a TGT that states a non-rpiv user is a member of the Domain Admins group, the DC will trust it because it is encrypted correctly.

We must carefully protect stolen krbtgt password hashes because they grant unlimited domain access. Consider explicitly obtaining the client's permission before executing this technique.

This is a clean way of achieving persistence in an AD env, the biggest advantage is that the krbtgt account password is not changed automatically.

In fact the password is only changed when functional level of the domain is upgraded from a pre-2008 Win server, but not from a newer version, so it is not uncommon to find very old krbtgt password hashes.

The Domain Functional Level dictates the capabilities of the domain and determines which Windows operating systems can be run on the domain controller. Higher functional levels enable additional features, functionality, and security mitigations.

Shadow Copies

VSS (Volume Shadow Copy), also known as a Shadow Copy, is a MS backup technology that allows the creation of snapshots of files or entire volumes.

The MS signed binary vshadow.exe is availabel as part of the Windows SDK.

As a Domain Admin, we can abuse vshadow utility to create a Shadow Copy that will allow us to extract the AD Database NTDS.dit database file. Once we have a copy of the DB, we can extract every user cred offline on our Kali machine.

To start, connect as jeffadmin domain admin user to the DC1 domain controller and launch vshadow utility from an elevated prompt with the -nw option to disable writers, which speeds up backup creation and include the -p option to store the copy on disk. NOTE: Must use elevated CMD prompt, not PS
