PEN-200 Module 24 — Assembling the Pieces

TLDR;

The “Assembling the Pieces” lab is a miniature red-team engagement. These enriched notes trace the full path captured in the raw journal so you can reproduce it intentionally.

External Recon & Entry

  • Identify exposed hosts (MAILSRV1, WEBSRV1) with nmap -sV -p 25,80,443. Document banner versions and TLS posture.
  • Enumerate WordPress on WEBSRV1 with wpscan --enumerate ap,vt --plugins-detection aggressive ➜ vulnerable plugin leads to file upload RCE.
  • Capture web shell callback details (timestamp, source IP, credentials harvested).

Establish Internal Foothold

  • Pivot through VPN/SSH using stolen credentials; log connection method.
  • Run situational awareness: whoami, ipconfig, net view, arp -a, nltest /dclist.
  • Map internal subnets and note interesting services (SQL, SMB shares, RDP gateways).

Credential Escalation

  • Phish internal user (e.g., mike) using crafted email + .library-ms payload. Record mail logs and the time of execution.
  • Kerberoast service accounts: Invoke-Kerberoast ➜ crack backupuser password.
  • Leverage captured credentials to access CLIENT75, dump additional hashes (mimikatz sekurlsa::logonpasswords).

Lateral Movement & Domain Control

  • Relay Net-NTLMv2 to escalate privileges (ntlmrelayx.py).
  • RDP into DC01 as backupuser, collect domain admin privileges, create shadow copy for data access.
  • Document each pivot with proof commands and note cleanup actions (delete payloads, remove scheduled tasks).

Reporting Narrative

  1. Initial compromise via WordPress plugin upload.
  2. Credential harvesting through phishing ➜ reuse on internal hosts.
  3. Kerberoast ➜ backupuser ➜ domain admin privileges.
  4. Data access via shadow copies and share enumeration.

Pair each step with evidence (hashes, command output, screenshots) and remediation guidance (patch plugin, enforce MFA, monitor Kerberos events, restrict shadow copy permissions).

Module 24 proves whether your process scales. Keep the timeline tight, note decision points, and show defenders exactly how to close the gaps you exploited.

24.1 Enumerating the Public Network

  • Obtain useful information to use for later attacks.
MAILSRV1

Before starting a pentest we want to setup and structure our environment as we will collect a huge amount of information in due course.

Structuring and isolating data and settings for multiple penetration tests can be quite the challenge. By reusing a Kali VM we could accidentally expose previous-client data to new networks. Therefore, it is recommended to use a fresh Kali image for every assessment.

We will create our main directory /home/$USER/OffSec/beyond and two sub-directories for each target we currently have access to. We will also create a creds.txt file to keep track of valid creds and users.

└─$ tree ../beyond

Now that we setup our work env, we are ready to enum our first target MAILSRV1.

Documenting our findings is a crucial process for every penetration test. For this Module, we'll store results in the basic work environment we just set up. However, Markdown editors, such as Obsidian, have become quite popular for documenting findings and data in real assessments as they are application-independent and contain functions that will simplify report writing and collaboration.

Start with a portscan of MAILSRV1 using Nmap, this is often the first active info gathering method we perform to get an overview of ports/services accessible to us.

In a real penetration test, we would also use passive information gathering techniques such as Google Dorks and leaked password databases to obtain additional information. This would potentially provide us with usernames, passwords, and sensitive information.

The WordPress core often has vulns, but their dev team is quick to patch. This version was released in August of 2022.

WordPress plugins and themes, often written by the community, often feature improperly patched vulnerabilities or ones that are simply never fixed. This makes themes and plugins a prime target.

We can perform a scan on these components with WPScan, a vuln scanner for WordPress that requires an API token. A limited API key can be obtained for free by registering an account on the WPScan homepage. It can still be used effectively without an API key to enumerate WP instances.

To perform a scan without an API key:

  • Target URL --url
  • Plugin detection aggressive
  • Enum popular plugins --enumerate p
  • Output file -o
┌──(operator㉿labhost)-[~/OffSec/beyond]
└─$ wpscan --url http://192.168.247.244 --enumerate p --plugins-detection aggressive -o websrv1/wpscan

We will again use a custom query in BloodHound to review active sessions. In the Cypher Query Language we can build a relationship query with syntax:

(NODES)-[:RELATIONSHIPS]->(NODES)

The relationship for this case is [:HasSession], the first node specified by a property is (c:Computer), and the second is (m:User). Meaning the edge between the two nodes source is the computer object. We'll use p to store and display the data.

MATCH p = (c:Computer)-[:HasSession]->(m:User) RETURN p

    • CLIENTWK1 has an active session with user marcus
    • As expected.

    • Previously unknown admin account.
    • If we get privileged access to this machine we can potentially extract the NTLM hash of this user.
  • INTERNALSRV1 shows an active session as an SID.
  • BloodHound uses this representation of a principal when domain ID of the SID is from a local machine.
  • This means local Administrator (indicated by RID 500) has an active session.
